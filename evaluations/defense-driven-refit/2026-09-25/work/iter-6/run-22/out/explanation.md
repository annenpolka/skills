## 1. その場の回答

**この PR を採用してよいか**

このままでは採用できません。メンバー一覧のキャッシュが他組織のメンバーやメールアドレスを返す経路、改名マイグレーションがローリング更新中とロールバック後の旧版を壊す経路、同時に来た招待が席数の上限を超える経路を、資料の確認で見つけました。直し方と検証の計画は台帳にありますが、今回はコードを変えておらず、テストも実行していません。

### 構造

**キャッシュを置いたのはなぜか、遅さは解消するのか**
要求は「速くする」で手段の指定はなく、キャッシュはその手段の一つとして置きました。ただ、遅さの原因と改善量はまだ計測しておらず、キャッシュを残すかどうかは計測待ちです。今言えるのは、キャッシュに当たった再表示では DB を引かないことまでです。

**メールアドレス入りの一覧を Redis に置いてよいか**
この PR で、管理者向けの一覧がメールアドレスを含んだまま最大60秒 Redis に置かれるようになります。置いてよいかの規則は資料に無く、運用側の確認待ちです。キャッシュを外す判断になれば、この問いは消えます。

**ロゴをサーバーで取得して埋め込むのはなぜか**
要求はロゴの表示だけで、埋め込み方式を選ぶ根拠はまだ示せていません。サーバー側で取得すると、登録 URL への通信の制限、取得内容の検査、招待ごとの外部待ちが必要になります。そのため、メール側で URL を参照する形に寄せられるかを、配信サービスの対応で確かめるところです。

### 境界

**キャッシュキーは組織と権限を区別しているか**
していません。キーがページ番号だけなので、他組織の一覧や管理者向けのメールアドレスが別の利用者に返ります。キャッシュを残すなら、組織・メールを含めるか・ページの三つをキーに入れ、利用者をまたいで呼ぶテストで確かめます。

**列の改名は、配備中とロールバックのときに動くか**
動きません。適用から入れ替え完了までの数分間に残る旧版 Pod と、イメージを戻したロールバック後の旧版が、改名前の列を参照して失敗します。列の追加と同期を挟む二段階の移行に分け、旧列の削除は次のリリースに回します。

**ロゴの URL は、サーバーから取りに行ってよい場所か**
登録時は https で始まるかしか見ておらず、取得時はリダイレクトも追います。そのため、組織の管理者が内部向けの宛先を登録すると、その応答が招待メールで本人に届く経路があります。サーバー側取得を残すなら内部アドレスとリダイレクトを拒む制限を入れますが、実際に届く内部宛先があるかはネットワーク設定の確認待ちです。

**席数超過の 409 を、既存の一括招待画面は扱えるか**
409 は、規約が無い範囲で選んだ状態コードで、要求どおり超過を拒否します。一括招待の途中で 409 が返ったときに画面がどう表示し、残りを続けるのか止めるのかは、画面のコードが手元に無く未確認です。

**メンバー一覧 API の応答キー名は変わったか**
今の応答は display_name を返します。変更前のコードが手元に無いので、name から変わったかどうかは差分の確認待ちです。変わっていれば、既存の利用者のために旧キーを保ちます。

**招待は、招待する管理者の組織に閉じているか**
閉じています。管理者だけが招待でき、席数・ロゴ・挿入はすべてセッションの組織で絞っています。管理者判定は組織設定と同じです。

### 改修の計画（verification.plan の要約）

- **R-04** キーを `members:org={org_id}:email={include_email}:page={page}` の形にする。一つの FakeCache を共有したまま「組織 A の管理者 → 組織 B の一般メンバー」「同じ組織の管理者 → 一般メンバー」の順に呼び、後の呼び出しに他組織の行もメールも出ないことを確かめる。
- **R-05** display_name 列を追加して既存値を埋め、移行期間は name と同期させる。旧列の削除は別リリースに回す。ステージングで、旧イメージでの動作・RollingUpdate 中・旧イメージへのロールバックの三つを確かめる。
- **R-10** 組織行を `SELECT ... FOR UPDATE OF o` で取ってから数え、同じ組織の招待を直列化する。実 PostgreSQL の2接続で、残り1席に同時に招待して 201 と 409 が一つずつになることを確かめる。
- **R-06 / R-16 / R-11**（R-03 でサーバー取得を残す場合）取得先の制限（リダイレクト、内部アドレス、スキームとポート）、取得内容の制限（Content-Type、大きさ、全体の期限）、トランザクション外での取得。
- **R-14** Redis 例外をキャッシュミスとして扱い、DB から返す。
- **R-01 / R-03 / R-07 / R-08 / R-12 / R-13 / R-02** 計測、配信サービスの対応、画面の挙動、main との差分、要求の持ち主・運用側への確認。

## 3. 認める限界と見直す条件

### accepted（今回は直さないと決めたもの）

- **R-15** メンバーの増減や権限変更が、最大60秒一覧に出ない。60秒は鮮度の要求が無い範囲で選んだ任意の値で、唯一の正解とは主張しない。
  見直す条件: 鮮度についての要求や問い合わせが出たとき、または計測で TTL を変える理由が出たとき。（キャッシュを残すかが決まるまで、この判断も候補のまま）

### unverified（未確認のまま報告するもの）

- **R-01** 「応答を速くした」は計測で示していない。見直す条件: 計測結果が出たとき。
- **R-02** Redis 上の個人情報の扱いを確認していない。見直す条件: 運用側の回答が出たとき、またはキャッシュを外すと決めたとき。
- **R-03** 埋め込み方式を選ぶ根拠を示せていない。見直す条件: 配信サービスの対応が分かったとき。
- **R-05** 抜粋の外に users.name を参照するもの（他サービス、集計など）があるかは確認していない。見直す条件: リポジトリ全体と DB の利用者を検索した結果が出たとき。
- **R-06** API サーバーから到達できる内部宛先の有無と、ASVS をチームの規約として置けるかは確認していない。見直す条件: ネットワークの送信制限とセキュリティ規約を担当者に確認できたとき。
- **R-07** 既存の一括招待画面での 409 の扱いを確認していない。見直す条件: 画面のコード確認かステージングでの確認が済んだとき。
- **R-08** 応答キーが name から変わったかどうかを確認していない。見直す条件: main との差分を確認したとき。
- **R-10** 同じ組織で招待が同時に来る頻度は資料に無い。行ロックを入れると、送信がトランザクション内にある間は、同じ組織の招待がメール送信の待ち時間だけ直列に並ぶ。見直す条件: メール送信の位置（R-12）を決めたとき。
- **R-12** 部分失敗のときに招待とメールが食い違う経路は確認しておらず、失敗時の方針の根拠も無い。見直す条件: main との差分と配信サービスの仕様を確認したとき。
- **R-13** 重複招待が席を消費する経路の扱いが決まっていない。見直す条件: 要求の持ち主の回答が出たとき。
- **R-14** Redis が接続を受けたまま応答しない場合の待ち時間は確認していない。見直す条件: クライアントの既定のタイムアウトを一次資料で確認したとき。
- **R-16** ロゴ置き場が落ちているときは招待1件ごとに遅れ、一括招待では累積する。大きさと期限の上限値は任意の値にとどまる。見直す条件: 一括招待の所要時間についての要求や問い合わせが出たとき。
