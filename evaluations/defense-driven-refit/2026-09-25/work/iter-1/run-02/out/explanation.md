## 1. その場の回答

相手によって変えているのは長さと用語だけで、述べている事実・保留・限界は同じ。

### コードレビュアー向け

この PR は `users` 行を1文の DELETE で消し、関連行を外部キー定義に任せています。そのため ACC-88 で未決の注文履歴・法定保持・取り消し猶予を「注文ごと即時に消す」側へ先に決めてしまっており、削除方式はその決定を待って選び直し、それまでマージしません。削除は検索索引・CRM・分析基盤・バックアップに届かず、既発行のアクセストークンも最長24時間有効なまま残るうえ、`audit_logs` の外部キーに CASCADE が無いため監査ログを持つ利用者は削除が500で失敗し、いまのテストは DB を偽物に差し替えているのでそれを検出できません。

### プライバシー担当向け

今の実装は利用者テーブルの行を消すだけで、扱いが未決の注文履歴まで一緒に消してしまうため、削除方式は注文履歴・法定保持の対象と期間・取り消し猶予の決定を待って選び直し、それまでリリースしません。検索索引・CRM・分析基盤のスナップショット・バックアップには個人情報が残り、ログイン済みの端末の認証も最長24時間有効なままです。また監査ログのある利用者はそもそも削除に失敗し、いまのテストではそれが分かりません。

### 2.1 削除方式（構造）— 台帳 D-001, D-011, D-016

- 現状: `app/routes/account.py:11` が `DELETE FROM users WHERE id = %s` を1文だけ実行する。関連行は外部キーの定義で決まる: `orders` は `ON DELETE CASCADE`（`migrations/0007_orders.sql:3`）、`refresh_tokens` も CASCADE（`0004:3`）、`audit_logs` は ON DELETE 指定なし（`0012:3`）。
- 根拠:
  - 要求 `docs/tickets/ACC-88.md`「削除した利用者の個人情報は保持しない。ただし法令上保持が必要なものは除く（対象と期間は法務に確認中）」
  - 同「未決: 注文履歴の扱い（法務 佐藤・経理 李）」「削除の取り消し猶予期間を設けるか（PM 判断待ち）」
- 証拠: 無し（資料確認のみ）
- 答え: 現方式では未決の注文履歴（`total_yen` を含む）が不可逆に消え、猶予期間も持てない。方式を決める根拠は法務・経理・PM の判断にあり、資料からは決められない。決定が記録されるまで現方式ではマージしない（D-001, investigate）。
- 候補方式にも反例がある（D-011）。「行を残して個人情報列を消す」方式を採ると:
  - 既発行トークンの `PATCH /v1/me/profile` が表示名を書き戻し、`updated_at` の更新で検索索引にも再登録される。`POST /v1/orders` も通る（`app/auth.py:19-27` は users を参照しない）。
  - `crm_contact_id` まで消すと、次の `jobs/crm_sync.py:7` が置き換え後の email（`email` は `NOT NULL UNIQUE`）で CRM 連絡先を新規作成する。
  - この方式を採る場合は、削除済み状態をどこで拒否するか、どの列を残すかが成立条件になる。
- 問い合わせ経由の手動削除（ACC-88 背景、月200件超）の手順は資料に無い（D-016）。既存の運用が分かれば、それが削除範囲の退屈版になり根拠を継承できる。

### 2.3 削除後の認証（境界）— 台帳 D-003

- 根拠:
  - 要求「削除後、その利用者はログインできない」
  - 既存契約 `app/auth.py`: JWT の署名だけを検証し users を参照しない。アクセストークンの有効期間は24時間（`:9`）。更新は `refresh_tokens` で行い、`refresh_tokens` は users 削除で CASCADE（`0004:3`）。
- 証拠: 無し。
- 答え: 既発行のアクセストークンは削除後も最長24時間通る。現PRのままこのトークンを使うと次のとおり。
  - `GET /v1/orders` は空配列を返す。
  - `POST /v1/orders` と `PATCH /v1/me/profile` は外部キー違反で500になる。
- 要求が既発行トークンの失効まで含むかは資料に無いので、PM に確認する。ログイン処理とトークン更新処理は抜粋外で、削除済み利用者を拒否するかは未確認（investigate）。即時失効が要るなら、`current_user` を変える全APIの認証契約の変更になるので、範囲を分けて判断する。

### 2.4 削除そのものの失敗と部分失敗（手続き）— 台帳 D-004, D-015

- 根拠（既存契約）:
  - `audit_logs.user_id` は `NOT NULL REFERENCES users(id)` で、ON DELETE の指定が無い（`migrations/0012_audit_logs.sql:3`）。PostgreSQL 16 の既定は NO ACTION で、参照行が残っていれば削除はエラーになる（公式文書 ddl-constraints）。
  - `PATCH /v1/me/profile` は更新のたびに `audit.record` を呼ぶ（`app/routes/profile.py:15`, `app/audit.py:4-5`）。
- 証拠: 無し。
- 答え: プロフィールを一度でも更新した利用者は DELETE が外部キー違反になり、500で削除できない（D-004）。直し方は削除方式に依存するので、D-001 の決定後に確定する。
  - 行を残す方式なら、外部キーはそのまま満たされる。
  - 物理削除なら、`audit_logs` の外部キーを変えるマイグレーションが要る。
- 改修で削除が複数文や外部呼び出しになると、途中で失敗したときの状態が問題になる（D-015）。
  - `app/db.py:6` は autocommit の接続1本をプロセスで共有している。`def` のルートは FastAPI の外部スレッドプールで動く（公式文書）。
  - psycopg 3 では、同じ接続のカーソルは同じトランザクションを共有する（公式文書）。したがって共有接続の上で `transaction()` を張ると、並行する他の要求の文も同じトランザクションに入る。
  - 対応は、再実行で完了できる順序にするか、共有接続を使わずにトランザクションを張るか（暫定）。

### 2.5 監査記録（手続き、隣接APIとの差分）— 台帳 D-009

- 根拠: 既存契約。隣接API `PATCH /v1/me/profile` は、利用者の状態を変えたら `audit.record` を呼ぶ（`app/routes/profile.py:15`）。
- 証拠: 無し。
- 答え: 隣接APIに揃えて削除の記録を残す方向（remove_or_align、暫定）。ただし現方式ではこれを揃えられない。
  - 削除の後に記録すると外部キー違反になる。
  - 削除の前に記録すると、D-004 と同じ理由で削除が失敗する。
- 削除記録を残す要求は資料に無く、根拠は隣接APIとの整合だけ。残してよいかはプライバシー担当に確認する。

### 2.6 テストは何を示しているか — 台帳 D-010

- 証拠: `tests/test_account.py::test_delete_me_removes_user`。
  - `db.execute` を FakeDB に差し替え、SQL 文字列と引数が発行されたことだけを確認している（`:8-24`）。
  - これは現在値の主張なので、削除が正しいことの根拠にはならない。
- 反例: 現PRの実装そのものが、このテストに合格したまま次のように壊れる。
  - audit_logs 行を持つ利用者で500になる。
  - 注文を消す。
  - 複製先に個人情報を残す。
  - README の「全件成功」はこの範囲の事実にとどまる。
- 対応（未実施、暫定）: マイグレーション適用済みの実DBで、削除後の users・orders・audit_logs・refresh_tokens の状態と認証の結果を確かめるテストに置き換える。新しいテストが現PRの実装で落ちることを先に確認する。

### 2.7 確認して閉じた問い（境界）— 台帳 D-012, D-013

- 他人のアカウントを消せないか、CSRF は成り立たないか（D-012、done）:
  - 削除対象は `current_user` の id（トークンの sub）だけで、ルートはパスやボディで利用者IDを受け取らない。
  - 認証は Authorization ヘッダの Bearer トークンで、Cookie は使わない（`app/auth.py:1,19-27`）。
  - 追加の対策は求めない。
- 連打・再送したらどうなるか（D-013、done）:
  - 2回目は0行の DELETE で、204を返す。`db.execute` は影響行数を見ない（`app/db.py:21-23`, `account.py:11-12`）。
  - 404 にしないのは許容範囲内の選択（freedom）で、それ以上の理由は主張しない。
  - 複製先への削除を足した後の再実行は、改めて確認する。

### 2.8 どちらでもよい細部（今回のダイヤル外）— 台帳 D-014

- デコレータの `status_code=204` に加えて `Response(status_code=204)` を返している（`account.py:9,12`）。
- 隣接API（`orders.py:14-19`）はデコレータ指定だけ。どちらの書き方も許容範囲内。
- 細部層は今回確定しない。
