# PR #611 弁明（コードレビュアー向け）

対象: PR #611「チーム機能の改善（TEAM-45）」。台帳: `ledger.yaml`（16項目）。
第一周のため、コードの変更とテストの実行はしていない。改修は台帳の `resolution` と `verification.plan` に記録しただけで、まだ適用していない。

## 1. その場の回答

TEAM-45 の4つの要求に1つずつ対応していますが、メンバー一覧のキャッシュが組織と権限を区別しておらず、別の組織の一覧や管理者にだけ返すはずのメールアドレスが他の利用者に返ることがあるため、この形のままでは出しません。
改名マイグレーションは新旧の Pod が並ぶ今のデプロイ手順と両立しないので段階を分け、ロゴは管理者が登録した URL の中身をサーバーが取りに行ってメールで送る形をやめるか取得先を制限し、同時の招待で席数を超え得る点も直します。
席数の数え方とエラーの形は要求と既存の形式に合わせてありますが、キャッシュで遅さが解消するかと重複した招待の数え方はまだ決まっておらず、今回は資料の確認だけでテストは実行していません。

## 2. 深掘りされたときの根拠

「根拠」は、なぜその性質や選択が必要か。「証拠」は、成果物が実際にその性質を持っているか。証拠はすべて資料・コードを読んで確認したもの（inspection）で、テストの実行結果ではない。

### メンバー一覧のキャッシュ（D-001, D-012, D-011, D-013）

- **キャッシュを入れた理由（D-001・構造）**
  - 根拠: TEAM-45 要求1（`docs/tickets/TEAM-45.md:5`）
  - 足りないもの: 遅さの原因と、キャッシュが当たる割合を測っていない。PR 説明の「応答を速くしました」も計測していない。`tests/test_members.py:26-33` は、2回目の呼び出しでキャッシュが使われることを確かめているだけで、速くなったことの根拠にはならない
  - 対応（候補）: 計測する。その結果でキャッシュを残すか、クエリやインデックスの改善に寄せるかを決める
- **キャッシュのキー（D-012・境界）**
  - 根拠: 既存仕様 `docs/spec/members.md:3-4`（自分の組織のメンバーだけを見られる／メールアドレスは管理者にだけ返す）
  - 証拠: 次の3点から、60秒以内なら別の組織の一覧や管理者向けのメールアドレスが他の利用者に返る
    - `members.py:19` のキーは `members:page={page}` だけで、組織IDも権限も含まない
    - `members.py:28-29` で権限に応じた結果をそのキーに保存する
    - `cache.py:1,8` と `deploy/api.yaml:6,15` から、3 Pod × 4 worker の全プロセスが同じ Redis を読む
  - 既存テストがこれを見逃す理由: `tests/test_members.py:12-23` はテストごとに新しい FakeCache を使うので、利用者どうしでキャッシュを共有する状況を通らない
  - 対応（候補・D-001 の決定待ち）: キャッシュを残すなら、キーに組織IDとメールの表示有無を入れる。残さないなら問題ごと消える。どちらに決まっても、今の形では出さない
- **Redis の障害（D-011・手続き）**
  - 証拠: `cache.py:11-17` も `members.py:20,29` も例外を捕まえない
  - 影響: 変更前は DB だけで返せた一覧が、Redis が落ちると返せなくなる
  - 対応: `cache.py` をほかで使っている箇所が障害時にどうしているかを確認し、それに揃える
- **TTL を60秒にした理由（D-013・細部）**
  - 根拠: なし。60秒は要求にも計測にも基づいていない
  - 影響: 削除や降格をしたメンバーが最大60秒一覧に残る。メールアドレスを置く場所に Redis が増える
  - 対応: 許容できる鮮度を依頼者に確認し、その範囲の中で任意に選んだ値として説明する

### users.name の改名（D-002, D-005）

- **マイグレーションの形（D-002・構造）**
  - 根拠:
    - 改名は要求4そのもの（`TEAM-45.md:8`）
    - デプロイ手順（`deploy/README.md:4-5`）: マイグレーションを先に適用し、そのあと新旧の Pod が数分並ぶ。ロールバックはイメージを戻すだけで、マイグレーションは戻さない
    - `deploy/api.yaml:6-9` は maxUnavailable 0 で、更新中も旧 Pod が応答を続ける
  - 証拠: `migrations/0033_rename_user_name.sql:1` は1文の RENAME。変更前のコードが `users.name` を参照していたことは `README.md:10` から分かる
  - 影響: 適用してから切り替えが終わるまでの数分間と、イメージを戻したあと、旧コードの `users.name` を使う処理が失敗する
  - 対応（候補）: 列を追加して同期する → コードを切り替える → 旧列を削除する、を別々のリリースに分ける。PostgreSQL 16 の文書によると RENAME と DROP は ACCESS EXCLUSIVE ロックを取るので、適用時のロック待ちもあわせて確認する
- **API の応答キー（D-005・境界）**
  - 事実: `/v1/members` の応答キーは `display_name`（`members.py:11`）。要求4は列の改名だけを求めていて、API の応答を変えることは求めていない
  - 不明な点: 変更前のキーは資料では確認できない
  - 対応: ベースブランチと比べる。キーが変わっていたら元に戻す（change）

### 招待の席数（D-006, D-007, D-008, D-009, D-014）

- **数え方（D-006・境界、確認済み）**
  - 根拠: 要求2（`TEAM-45.md:6`）
  - 証拠: `invitations.py:22-27` で有効メンバー数と未承諾の招待数を足し、`used >= seat_limit` なら拒否する。要求の数え方と一致している
  - 答え: 有効メンバーと未承諾の招待の合計が席数に達した組織への招待は拒否する。同時に実行された場合の扱いはこの答えに含まない
- **409 を返す理由（D-008・境界、説明を限定したうえで確認済み）**
  - 根拠: チケットに状態コードの指定はない。ここは許容範囲内の任意の選択で、409 でなければならない理由はない。例外の形は `org_settings.py:13,16` と同じ `HTTPException(コード, 文言)` に揃えた
- **重複した招待や古い招待の数え方（D-007・境界、反例）**
  - 反例: 次のような招待も、要求の文言どおりに1件ずつ席を使う
    - 同じ宛先への重複した招待
    - すでに有効なメンバーになっている人への招待
    - 期限がないまま残っている古い未承諾の招待
  - 証拠: `migrations/0020_invitations.sql:1-9` には一意制約も有効期限の列もない
  - 対応: これらをどう数えるかは依頼者が決めることで、今回は確認できていない
- **同時に招待されたとき（D-009・手続き）**
  - 根拠: 要求2
  - 証拠: 次の3点から、同じ組織への招待が同時に来ると、両方が同じ件数を読んで両方とも挿入し、席数を超える（コードと文書を照らし合わせた結果で、並行テストはしていない）
    - `invitations.py:17-33` は行をロックせずに数えてから挿入する
    - `deploy/README.md:3` で分離レベルは既定のまま。PostgreSQL 16 の文書では既定は Read Committed で、各文はその文が始まる前に確定したデータだけを見る
    - `deploy/api.yaml:6,15` から12プロセスが並行して動く
  - 対応（候補）: 数える前に組織の行をロックし、同じ組織の招待を1件ずつ処理する。ロックを持っている間は外部を呼ばない（D-010 とあわせて直す）
- **プランがない組織や上限のない組織（D-014・細部、反例）**
  - 反例: 上限なしのプランを `seat_limit` NULL で表している場合や、`plan_id` がない組織の場合、比較で例外が起きて招待できなくなる
  - 不明な点: `plans` と `orgs` のテーブル定義は抜粋にない

### 招待メールのロゴ（D-003, D-004, D-010, D-015）

- **サーバーで取得して埋め込む理由（D-003・構造）**
  - 根拠: 要求3（`TEAM-45.md:7`）が決めているのは「表示すること」と「管理者が登録した URL を使うこと」だけで、埋め込むこともサーバーが取得することも決めていない
  - 不明な点: `mailer.send_invitation` の `logo` 引数が何を受け取るのか（`mailer.py:1-3`、実装は省略されている）
  - 対応: この引数の契約を確認する。URL を渡すだけで足りるなら、`logo.py` を削除して URL を渡す
- **取得先が自由に決められること（D-004・境界）**
  - 事実:
    - 登録時の検査は `https://` で始まるかどうかだけ（`org_settings.py:15-16`）
    - requests は GET でリダイレクトを既定で追いかける（requests の文書）
    - 取得した中身は、同じ管理者が指定した宛先にメールで送られる（`invitations.py:32,35`）
  - 影響: 各組織の管理者が、API の Pod から届くホストの応答を、自分宛ての招待メールで受け取れる
  - 要件の有無: この経路を許すとも禁じるとも資料には書かれていないが、許す根拠もない
  - 対応（候補・D-003 の決定待ち）: サーバーで取得するのをやめれば、この経路はなくなる。取得を残す場合は、取得先の制限、リダイレクトを追わない設定、画像の種類とサイズの検査を入れる
- **トランザクションの中で外部を呼ぶこと（D-010・手続き）**
  - 根拠: トランザクション中は接続を1本持ち続ける（`db.py:21-25`）。接続プールは1プロセス10本（`config.py:5`）
  - 影響: ロゴ取得（`invitations.py:34`）の応答が遅い間、接続を持ち続ける。同時の招待が多いとプールが尽き、ほかの API も待たされる。D-009 でロックを足すと、ロックも持ち続けることになる。メール送信（`invitations.py:35`）のあとで失敗したり送信結果が分からない例外が出たりするとロールバックされ、届いたメールの招待が保存されない
  - 対応（候補）: ロゴ取得をトランザクションの前に移す。メール送信の位置は、この PR で動かしたものかを確認してから扱う
- **timeout=5（D-015・細部）**
  - 根拠: なし
  - 事実: requests の timeout は応答全体にかかる上限ではなく、受信が途切れた時間に対する上限（requests の文書）。応答のサイズにも制限がない
  - 対応: サーバーでの取得を残すと決まった場合だけ、上限を決める

### テスト（D-016）

- PR 説明にある「pytest 全件成功」は今回確かめていない。フィクスチャの定義（conftest など）も抜粋に含まれていない
- 既存のテストは、D-004・D-009・D-012 で失敗が起きる経路を通らない。そのため、全件成功しても安全だという証拠にはならない
- 対応: PR 説明のこの部分を「どのテストが何を確かめたか」の記述に置き換える。そのうえで第二周に、要求を満たすことを確かめるテストを追加して実行する
