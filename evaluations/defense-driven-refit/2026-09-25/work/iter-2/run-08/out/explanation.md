PR 説明の限定案（README の「概要」の差し替え候補）:

> `DELETE /v1/me` は、認証済み利用者の `users` 行と、CASCADE で連動する `refresh_tokens`・`orders` の行を削除して 204 を返す。204 が意味するのは DB 上の削除の成功だけで、検索インデックス・外部CRM・分析基盤・バックアップからの削除は含まない。削除後は新規ログインとトークン更新ができなくなるが、発行済みのアクセストークンは期限（最長24時間）まで失効しない。注文履歴の扱いと取り消し猶予は ACC-88 で未決。

### 2.4 改修の予定（台帳の resolution と verification.plan から）

1. 判断を得る: 法令上の保持対象と期間（D-01）、注文履歴（D-03）、取り消し猶予（D-02）。この三つが決まるまで、下の層は候補のまま
2. audit_logs の参照を、削除と両立する形に変える（D-04）。スキーマを変える場合は、既存の行があり旧コードと混在する期間の移行順も確認する
3. 検索インデックスへの削除の経路を足す（D-05）。外部CRMは、CRM側で削除できるかを確かめてから決める（D-06）。どちらも、削除前に必要な対応付けを失わない順序にする
4. 204 の意味を API 契約に書く（D-11）。削除の監査記録の要否を決める（D-13）
5. migrations を適用した PostgreSQL で、audit_logs・orders・refresh_tokens を持つ利用者の削除を結合テストで確かめる（D-14）。既存の単体テストは、現在の SQL を保存するだけのものとして扱う
6. 2〜3 で削除が複数の文や外部呼び出しになったら、D-12・D-15 の検証済みを取り消し、部分失敗と再試行を見直す
