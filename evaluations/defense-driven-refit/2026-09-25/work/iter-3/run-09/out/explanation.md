## 1. その場の回答

### コードレビュアー向け

このPRは users 行を1文で物理削除するだけで、監査ログの外部キーが CASCADE でないため、プロフィールを更新したことのある利用者では削除が失敗し、成功した場合は注文履歴が CASCADE で即時に消えます。注文履歴の扱いと取り消し猶予はチケット上で未決なので、物理削除にするか匿名化にするかはその決定を待って選び直し、改修してから再レビューに出します。検索索引・外部CRM・分析基盤の日次出力・DBバックアップへの削除の伝播もまだ無く、分析基盤とバックアップに残る分はプライバシー担当の判断待ちです。

### プライバシー担当向け

今回の変更で消えるのは本番DBの利用者行と、それに連動する注文履歴・更新用トークンだけで、監査ログを持つ利用者ではその削除自体が失敗します。注文履歴を残すか、取り消し猶予を設けるかが未決のまま注文を即時に消す形になっているので、決定を待って方式を選び直します。管理画面検索の索引、外部CRM、分析基盤の日次スナップショット（無期限保持）、DBバックアップ（35日）には削除した利用者の個人情報が残り、そのうち分析基盤とバックアップを許容するか・どの期間かはご判断をお願いしたい点です。

## 2. 深掘りされたときの根拠

### 退屈版との比較

- 隣接ルート（`app/routes/profile.py`、`app/routes/orders.py`）と比べて、構造・境界は同形: `APIRouter` + `Depends(current_user)` + `db` 直呼び、`app/main.py` で `include_router`。ここは既定どおりで、逸脱の理由は要らない。
- 差分は一つだけ: 隣接の `profile.py:15` は利用者を変えた後に `audit.record` を呼ぶが、このPRは呼ばない（D-007）。今のスキーマではこれに揃えることもできない（`migrations/0012_audit_logs.sql:3`）。
- 同形でも、削除は影響領域に入るので、下の impact 項目で検査した。影響領域は成果物からではなく、ACC-88・migrations・config・jobs・ops・既存ルートから拾った。

### 方式の決定で変わる箇所

D-001 で「行を残して個人情報の列を消す」方式を選ぶと、次が変わる。

- D-006: 外部キーはそのまま成立し、削除の失敗は起きない。
- D-009: `updated_at` を更新すれば既存の索引ジョブが上書きする（最大5分の遅れ）。
- D-008: 古いトークンで注文作成とプロフィール更新が成功するようになり、書き戻した表示名が索引に再同期される。`current_user` で削除済み利用者を拒否する変更が必要になる。

物理削除を続ける場合は、D-006 で audit_logs の扱いを決め、同じトランザクションで削除する必要がある。`db.py` には複数文をまとめる手段がない（共有接続・autocommit）。どちらにするかは D-001 の決定待ちで、資料からは選べない。

### 改修の予定（第二周。上の層から確定する）

1. D-001: 注文履歴（法務・経理）と取り消し猶予（PM）の決定を得て方式を選ぶ。それまで本エンドポイントは本番で有効にしない（提案）。
2. D-002: 個人情報の所在一覧を PR 説明に載せ、抜粋外にほかの所在がないかをリポジトリ全体で探す。
3. D-006・D-007: 監査要件の持ち主を特定し、audit_logs の扱いを決めて削除が成立するようにする。
4. D-008: 要求「ログインできない」の解釈（PM）とトークンの exp の有無を確認し、必要なら削除済み利用者を拒否する。
5. D-009・D-010: 索引の文書と CRM の連絡先を削除する手順を入れる（CRM は削除手段を確認してから）。同期ジョブとの競合も扱う。
6. D-011・D-012: プライバシー担当・法務・DATA-12 の持ち主の判断を得る。対応は別チケットにして本PRと結ぶ。
7. D-013: 要求を確かめるテストを実スキーマの DB で書き、改修前に落ちることを確かめてから改修する。
8. D-004・D-005: 確定した手順に合わせて、応答コードの意味と「確認なしの即時削除」であることを API 説明・PR 説明に書く。
