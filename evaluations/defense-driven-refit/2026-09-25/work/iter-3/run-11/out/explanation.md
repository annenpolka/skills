---

## 1. その場の回答

年額更新ジョブは、今の2レプリカで同時に走る置き場所から月額と同じ単独起動の定期ジョブに移し、課金には購読と請求期間ごとに固定した冪等キーを付けて、二重課金を起動方式と決済APIの両方で防ぐ形に直します。
金額は月額と同じ「税込・通貨の最小単位の整数」の計算に揃え、共有の決済クライアントの自動再送はキーを渡す呼び出しだけに限って、対象外の月額ジョブの挙動は変えません。
いずれもまだ改修しておらず検証もしていません。PayCo のキー保持期間と、要求にある「前回更新日」の起算日は未確定として残します。

## 2. 深掘りされたときの根拠

根拠（なぜ必要か）と証拠（実際にそうなっているか）を分けて書く。証拠はすべて資料確認（inspection）で、実行した結果ではない。状態が pending の項目は、改修も検証も済んでいない。

### 2.1 構造

**S-01 なぜ既存の scheduler に同居させないのか**（逸脱）
- 現状: `app/scheduler.py:10` で10分ごとに登録している。`billing-scheduler` は `replicas: 2`（`deploy/scheduler.yaml:7`）で、session purge と同じプロセスで動く。
- 根拠: 月額更新は CronJob・`concurrencyPolicy: Forbid` の単独起動で動いている（`deploy/monthly-worker.yaml:1-8`）。この既存方式に揃える。
- 足りないもの: 同居させる根拠が資料に無い。同居させると双方のレプリカで実行され（S-02）、例外でプロセスが落ちると purge も止まる（D-03）。
- 対応: remove_or_align。年額用の CronJob（Forbid）を置き、scheduler の登録を外す。
- 検証計画: 差分で確認する。次の強さでは、ステージングで1回の実行時刻に Job が1つだけ動くことを見る。状態は pending。

**S-02 二重課金はどこで防ぐのか**（影響: 並行実行・冪等性）
- 根拠: BILL-212 要求2「同じ購読の同じ請求期間に二重課金しない」（`BILL-212.md:10`。BILL-212 は利用規約 §4.2 に明記済みとしているが、規約本文は見ていない）。PayCo は `Idempotency-Key` を受け付け、同じキーの再送には最初の要求の結果を返す（`payco-api-v2-excerpt.md:8`）。
- 足りないもの: 現状は「同時に1プロセスだけが実行する」ことを暗黙に前提しているが、2レプリカではこの前提が成り立たない。一方が処理中の行をもう一方も取得すれば、同じ購読に2回課金する。毎月1日の約40万件（`BILL-212.md:18`）のように処理が長い日ほど重なりやすい。CronJob に寄せても、Kubernetes 文書（CronJob limitations）のとおり1回の実行時刻に Job が2つ作られることがあるので、単一起動だけでは要求2を保証できない。
- 対応: change。単一起動（S-01）に加えて、請求期間ごとに固定した冪等キー（B-01・B-05）と、旧値一致を条件にした更新（D-02）で保証する。分散ロックやリーダー選出は足さない。状態は pending。

### 2.2 境界

**B-01 決済クライアントの自動再送**（影響: 外部API・成否不定）
- 根拠: PayCo の転記に「5xx 応答の場合、課金が成立しているかどうかは不定のことがある」（`payco-api-v2-excerpt.md:10`）とある。
- 証拠: 再送のときに `Idempotency-Key` を付けていない（`app/payments_client.py:27-39`）。requests の ConnectionError は、要求を送ったあとの切断でも発生する（requests の公開 issue で確認。一次文書の該当箇所は未確認）。
- 対応: change。`charge()` が呼び出し側から冪等キーを受け取ってヘッダで送る。キーを渡さない呼び出しは再送しない。状態は pending。

**B-02 共有クライアントを変えたことで、月額ジョブの挙動も変わる**（影響: 後方互換）
- 根拠: 月額プランは BILL-212 の対象外（`BILL-212.md:22`）。月額ジョブは既定引数の `PaymentsClient()` を使う（`app/monthly_worker.py:9`）。
- 対応: change。B-01 の「キー無しなら再送しない」によって、月額は変更前と同じ1回の送信に戻る。月額ジョブのコードは変えない。状態は pending。

**B-05 冪等キーを何から作るか**（反例駆動）
「期間ごとのキーで送れば二重課金しない」という説明には従っているのに、実際には困る実装が三つある。
1. キーを購読IDだけで作る → 翌年の更新に前年の結果が返り、課金されないまま `renews_at` だけが進む。
2. 3日後の再試行にも同じキーを使う → 拒否済みの結果が返るので、要求3の再試行が実際には行われない。
3. キーに `renews_at` を使う → 再試行のたびに `renews_at` が動く（P-02）ので、成否不定のあとの再送が重複排除されない。
- 対応: change。キーは「購読ID＋再試行で動かない期間の起点＋確定した失敗のあとの試行番号」で作る。成否不定のときは試行番号を進めない。状態は pending。

**B-03 金額の単位と計算**（逸脱）
- 根拠: PayCo の `amount` は通貨の最小単位の整数（`payco-api-v2-excerpt.md:7`）。要求4は税込で、最小単位に丸める（`BILL-212.md:12`）。既存の計算は `money.with_tax_minor_units`（`app/money.py:7-11`、月額 `app/monthly_worker.py:21`）。
- 証拠: `app/renewal_worker.py:26` は主単位の小数を渡している。仮の例では JPY 999 が 1098.9、USD 120.00 が 132.0 になる。非整数を送ったときに PayCo がどう扱うかは転記に無い。拒否されれば顧客の失敗として数えられ、受理されれば USD はセント扱いで1/100の請求になる。
- 対応: remove_or_align。`money.with_tax_minor_units` に寄せる。状態は pending。

**D-03 金額計算の型**（影響: 金銭・数値型。B-03 に従属）
- 根拠と証拠: `price` 列は `numeric(12,2)`（`0031_subscriptions.sql:6`）で、psycopg は numeric を Decimal で返す（psycopg 文書 Data adaptation configuration）。Decimal と float の算術は TypeError になる（Python decimal 文書）。`config.TAX_RATE` は float（`app/config.py:3`）。
- 帰結: 対象が1件でもあれば、本番の行では最初の1件で例外が起き、1件も課金されない。schedule は実行中の例外を捕まえない（schedule 文書 Exception Handling）ので、scheduler プロセスごと止まる。再起動しても10分後にまた落ちるため、1時間間隔の session purge は実行される機会が無い。ここはライブラリの既定動作からの推論で、実行して確かめてはいない。テストの `price` は float（`tests/test_renewal_worker.py:41`）なので、テストではこの経路を通らない。
- 対応: B-03 で寄せると、この算術自体が無くなる。状態は pending。

**D-04 税率はどこから取るか**（模擬尋問）
- 要求は「config の `TAX_RATE`」と書いている（`BILL-212.md:12`）。一方、既存の計算は `money.TAX_RATE`（`app/money.py:3`）を使う。いまはどちらも 0.10。
- 対応: investigate。どちらを正とするか要求オーナーに確認する。確認できるまでは「現在は同値」と範囲を限って説明する。

**B-04 マイグレーション 0042**（影響: 移行。確認済み・done）
- `ADD COLUMN failure_count integer NOT NULL DEFAULT 0`。PostgreSQL 16 文書（ALTER TABLE Notes）によれば、非 volatile な DEFAULT 付きの列追加は表の書き換えを要しない。
- 手順は pre-deploy で適用し、ロールバックではイメージだけを戻す（`deploy/README.md:3-5`）。旧版のコードはこの列を参照しないので、どちらの順でも両立する。
- 回答: 「PG16 では表を書き換えず、旧版アプリともロールバック手順とも両立します。」（版 `6b8bd2f8a059` で確認）

### 2.3 手続き

**P-01 何を「失敗」とみなすか**（反例駆動。要求3「失敗したら3日後に再試行」への反例）
- 証拠: 再送を使い切った 5xx も、4xx の拒否と同じ `PaymentError` になる（`app/payments_client.py:40-43`）。課金と `renews_at` の更新は別々の文で実行される（`app/db.py:6` autocommit）。
- 反例: 実際には成立していた課金を失敗として記録し、3日後にもう一度課金する。課金が成功したあと、更新する前にプロセスが止まると、次の実行で再課金する。
- 対応: change。クライアントで「確定した拒否」と「成否不定」を別の例外に分ける。成否不定は B-05 の同じキーで再送する。状態は pending。

**P-02 再試行が請求期間の起点を書き換えている**（反例駆動）
- 証拠: 失敗時に `renews_at` を「今＋3日」で上書きし（`app/renewal_worker.py:56-57`）、成功時にはその値に1年を足す（`:38`）。
- 足りないもの: `renews_at` が再試行時刻と期間の起点を兼ねているので、キーの基準にできない。
- 対応: change。`renews_at` は再試行では動かさない。候補は (a) 再試行時刻の列を1つ足す、(b) 起点＋失敗回数×3日で求める、の二つ。改修後に、抽出条件が既存の索引（`0031_subscriptions.sql:11`）を使える形かも確認する。

**D-11 次回更新日の起算日**（模擬尋問）
- `BILL-212.md:13` の「前回更新日」が、元の予定日を指すのか課金が成功した日を指すのかは資料から決まらない。いまの実装は「成功した試行の予定時刻」を起算日にしている。
- 対応: investigate。要求オーナーに確認する。D-02 はこの確認待ちの候補にとどめる。

**P-03 顧客を1件ずつ取得している**（逸脱）
- 対応: remove_or_align。月額と同じ JOIN（`app/monthly_worker.py:14-19`）に寄せ、必要な列だけを取る。

**P-04 1日の約40万件**（影響: 規模）
- 所要時間は計測していない。BILL-212 に完了期限の要求は無い。全件を一度に取得して逐次処理するので、処理している間に解約された購読にも課金しうる。解約の経路は抜粋に無い。抽出条件の列は既存の索引（`0031_subscriptions.sql:11`）と一致している（実行計画は取っていない）。
- 対応: investigate。計測と、解約経路の確認をする。

**P-05 1件の想定外の例外でバッチ全体が止まる**（影響: 部分失敗。月額と同じ形だが、影響領域なので一致していることを根拠にしない）
- 対応: change。課金前の例外は1件単位で記録して次に進む。課金後の例外による再実行は、キーで安全にする。
