# PR #611 チーム機能の改善（TEAM-45）: レビュアー向け弁明

第一周の記録です。コードはまだ変えておらず、テストも実行していません。
以下の「改修」は台帳（`ledger.yaml`）に書いた予定で、未実施・未検証です。「確認済み」は資料とコードを読んで確かめたという意味で、実行して確かめたものはありません。

## 1. その場の回答

今の版には直すまで出さない穴が4つあり、一覧キャッシュが組織と権限を区別しないこと、ロゴ取得が内部の宛先まで届くこと、同時の招待で席数の判定が破れること、列の改名がデプロイ中とロールバックで旧版を壊すことです。
キャッシュを置くかどうかと、ロゴをどう渡すかは、遅さの計測とメール送信部の確認が済むまで決めません。
招待の権限判定と席数の境界比較は要求と既存のやり方どおりなのを資料で確認済みで、409 は要求で決まっていない任意の選択です。

## 3. 認める限界と見直す条件

### 3.1 今回は直さない限界（確認済みの項目に付く限界を含む）

- **D-007**: 同じ相手への重複招待や放置された招待も、席を使います。また、承諾処理（抜粋外）が `accepted_at` を設定するかは確認していません。
  - 見直す条件: 要求者が数え方を決めたとき、承諾処理を確認したとき、「空きがあるのに招待できない」という問い合わせが来たとき。
- **D-012（メール送信部分）**: 送信後にコミットが失敗すると、無効なトークンのメールが届きます。送信の成否が分からない失敗の後で再送すると、二重に届くことがあります。この項目はロゴ取得部分に改修を予定しているため、限界を書いても終了条件には数えません。
  - 見直す条件: 送信位置がPR前からのものか確認したとき、無効リンクの問い合わせが来たとき。
- **D-008**: 抜粋の外にAPIエラーの規約文書があれば、まだ照合していません。
  - 見直す条件: その規約文書が見つかったとき。
- **D-010**: セッション（`sessions.lookup`、抜粋外）の `org_id` と `role` が正しいことを前提にしています。
  - 見直す条件: セッションの実装を変えるとき。
- **D-016**: 「上限−1なら成功」側の境界テストがなく、読んで確認しただけです。並行時の保証は D-011 の改修が前提です。
  - 見直す条件: 境界テストを足すとき。

### 3.2 未確認のまま残る事項

改修を予定しているか、確認を待っている項目です。終了条件には数えません。

- D-001: 要求1が達成できたかは計測していません。キャッシュが問い合わせの遅さに効くとは主張しません。→ 計測結果が出たとき。
- D-002: ロゴの受け渡し方式が決まっていません。→ mailer の契約を確認したとき。
- D-003: リポジトリ外で `users.name` を参照しているもの（別サービス、集計など）は確認していません。→ `name` を削除するリリースの前。
- D-004・D-006: 今の版はテナントの越境と、内部応答を持ち出す経路を持ちます。改修の前はマージしません。→ D-001・D-002 が決まったとき。
- D-005: 一覧APIの応答キーの互換性は確認していません。→ PRの差分を確認したとき。
- D-009: 一括招待が途中で拒否されたとき、利用者にどう見えるかは確認していません。→ 画面コードを確認したとき。
- D-011: 並行時に上限が守られるかは検証していません。→ 並行テストの結果が出たとき。
- D-013: 60秒には根拠がなく、唯一の正解とは主張しません。→ 許容範囲が決まったとき、または「追加したメンバーが出ない」という問い合わせが来たとき。
- D-014: Redis上の個人情報の扱いは確認していません。→ 担当者から回答が来たとき。
- D-015: プランのない組織や上限のない組織で、招待が500になる可能性を否定できていません。→ スキーマを確認したとき。
