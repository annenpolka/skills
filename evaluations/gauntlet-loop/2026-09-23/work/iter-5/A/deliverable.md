# 『はじめに』章のガントレット設計

実行は別セッションで行うとのことなので、composeモードで設計します。最上段は Stripe Docs と名指しいただいているため、ページはこちらで一つ選びました。開始前なら差し替えられます。設計内容はどのページを選んでも変わらないので、確認のための質問は挟まずに最後まで書いています。

## 1. 判定

| 問い | 答え |
|---|---|
| 1. 成果物をエージェントが実物として検査できるか | はい。Markdown/MDX を読めるうえ、`npm run build` で生成した HTML を読んだり、手順を実際に走らせたりもできる |
| 2. 取得できるバー候補があるか | はい。Stripe Docs をはじめ、公開されている入門チュートリアルはどれも取得できる |
| 3. 「良い」が機械検証だけでは決まらないか | はい。ビルドとリンタでは「壊れていない」までしか分からず、「分かりやすい」かどうかは判定できない。機械で決まる部分は床に回す |
| 4. 予算の上限を決められるか | はい。一晩8時間と伺っています。トークンは実行前チェックで見張る |

→ **回す**

## 2. バー

**最上段: Stripe Docs「Development quickstart」（https://docs.stripe.com/development/quickstart）**
選んだ理由は、依頼の「Stripe Docs の入門チュートリアル」に最も近い一本だからです。前提、最初のコマンド、成功したときの見え方、次の一歩を一本道で示すページとして評価されています。（未確認。開始前なら差し替えられます。代わりの候補は同じサイトの「Accept a payment」クイックスタートです。）

梯子（下 → 上）。段はすべて開始時に `refs/` へスナップショットします。

| 段 | 実物 | 取得方法 |
|---|---|---|
| 0 | 現行の『はじめに』章（開始時のコミット） | `git show <開始コミット>:docs/getting-started/` を `refs/rung0/` へ書き出す |
| 1 | Docusaurus 公式「Tutorial Intro」（https://tutorial.docusaurus.io/docs/intro）（未確認） | ページを取得し、本文を Markdown に整形して `refs/rung1/` へ保存 |
| 2 | Vite「Getting Started」（https://vite.dev/guide/）（未確認） | 同上 → `refs/rung2/` |
| 3 | Django「Writing your first Django app, part 1」（https://docs.djangoproject.com/en/stable/intro/tutorial01/）（未確認） | 同上 → `refs/rung3/`。版番号はスナップショットに記録する |
| 4（最上段） | Stripe「Development quickstart」（未確認） | 同上 → `refs/rung4/`。言語タブは一つ（例: Node）に固定する |

- 較正: 1周目の前に、隣り合う段同士（0-1、1-2、2-3、3-4）を新しい批評役にブラインドで比べさせ、想定どおりの順になるかを確かめます。順が崩れた段は入れ替えるか外します。既知の参照すら並べられないなら、この領域では判定できないので止めます
- 参照は評価専用です。文章も構成も成果物に写しません

## 3. 比べ方

主な判定は**読者タスク**です。題材が違ううえ、「Stripe らしさ」の見た目で出自がばれるので、好みの一対比較は補助にとどめます。

- 新しいエージェントに、一回につき一文書だけ読ませます（成果物、または梯子のどれか一段）。そのうえで、内容に依存しない次の型の設問に答えさせます
  1. 始める前に何が必要か（前提・環境）
  2. 最初に打つコマンド・操作は何か
  3. 成功したら何が見えるか
  4. 途中で失敗したら何を確かめ、どうするか
  5. 終わった後、次に何を読む・やるか
  6. この章を終えると何ができるようになるか
- 各文書の正答は開始時に作り、`refs/answers/rungN.yaml` と `refs/answers/target.yaml` に固定します。成果物の正答は章の改訂に合わせて更新しますが、設問の型は変えません
- 採点は正答との一致数です（採点役は回答した読者とは別の新しいエージェント）。読者は各文書につき3体とし、中央値を取ります
- 補助として伏せた一対比較も行います。両文書を同じ Markdown 書式に整え、製品名・社名・URL・コード中の固有名を中立の記号（`<PRODUCT>`、`<CMD>` など）に置き換え、分量は章の長さに揃えて切り出してから比べます
- 進捗の周で比べるのは三対だけです: 現在の段、一つ上の段、前の版

## 4. 床

いずれも終了コードで判定します。

- `npm run build`（壊れたリンクもここで落ちる前提。`docusaurus.config.js` の `onBrokenLinks: 'throw'` を実行前に確認する）
- `npm run lint`
- 【新規】変更範囲の確認。`! git diff --name-only <開始コミット> -- . ':!docs/getting-started/' ':!gauntlet/' ':!refs/' | grep .` で、章の外のファイルが変わっていたら失敗させる
- 【新規】手順の実走。章に書かれたコマンドをコードブロックから抜き出し、使い捨てのディレクトリで順に実行し、すべて終了コード0なら通す（`node gauntlet/tools/run-tutorial.mjs`）。1周目の前に作り、現行版に二度走らせて結果が一致することを確かめてから床に入れる

## 5. 停止条件

- 予算: 8時間（壁時計で計る）。トークンは上限を置かず、実行前チェックで見張る
- 停滞: 梯子の位置が3周動かない
- 勝利判定: 新しい批評役3体が全員、順番を入れ替えても最上段に勝つと判定し、かつ床が緑

## 6. 実行プロンプト

次のブロックをクリーンなセッションの Claude Code に貼り付けてください。

```text
社内技術ドキュメントサイト（Docusaurus）の『はじめに』チュートリアル章（docs/getting-started/）を、初めて読む社員が迷わず最初の成功までたどり着ける水準まで改善する。

バーは Stripe Docs の「Development quickstart」（https://docs.stripe.com/development/quickstart）。途中の段として、現行版の章（開始コミット）、Docusaurus「Tutorial Intro」（https://tutorial.docusaurus.io/docs/intro）、Vite「Getting Started」（https://vite.dev/guide/）、Django「Writing your first Django app, part 1」（https://docs.djangoproject.com/en/stable/intro/tutorial01/）を使う。開始時にすべてを refs/ に保存し、以後はそれを基準にする。
比べ方: 読者タスクを主にする。新しいエージェントに一文書だけ読ませ、固定した六問（前提、最初の一手、成功の見え方、失敗時の対処、次の一歩、終えると何ができるか）に答えさせ、開始時に refs/answers/ に固定した正答との一致数を比べる。読者は各文書3体で中央値を取る。補助として、書式と分量を揃え固有名を中立の記号に置き換えたうえで、伏せた一対比較を行う。参照は評価専用で、文章も構成も写さない。
床は npm run build、npm run lint、章の外を変えていないことの確認、章のコマンドを使い捨てディレクトリで実走して全部成功すること。床を通らない変更は評価に回さない。

進め方はあなたが決めてよい。守ることだけを書く。
- 作業を、独立に改善・判定できる単位に分ける。前提を共有する部分は一つの単位にし、一人の担当が順に磨く。並列にするのは結合の無い単位だけ。
- 各単位に作る役と、毎回新しい批評役を立てる。批評役には目標・バー・実物だけを渡し、作る役の説明は渡さない。
- 批評役は、どちらが自作か伏せたまま実物と梯子の段を比べ、勝敗と、差を分けた最大の症状を場所つきで一つ返す。直し方は言わない。
- 作る役は症状を計測で確かめてから、それだけを直す。計測が批評と食い違ったら計測に従う。同じ症状が二周続いたら、直すのをやめて原因を調べる。
- 1周目の前に検査系を作り、同じ版を二度検査して一致することを確かめる。実物と参照は同じ条件で並べる。
- 波の終わりに、全体を新しい批評役に見せて部品間の食い違いを直し、全体と参照の全体を比べる。
- 勝ったと言えるのは、新しい批評役 3 体が全員、順番を入れ替えても最上段に勝つと判定したときだけ。
- 止めるのは、勝ったとき、予算 8時間 を使い切ったとき、梯子の位置が 3 周動かないとき、原因を調べても同じ症状が残るとき、参照が取得できないとき。止まったら理由と現状を報告する。
- 状態は gauntlet/ledger.yaml に置き、進み具合を gauntlet/index.html に示し続ける。
- サブエージェントを使う。/loop や高いeffort設定が使えるなら使う。
```

雛形の［任意］行のうち、並列の行は落としました。章は一本道の読書体験で、節同士が前提（用語、環境、前の手順の結果）を共有しているため、一つの単位として逐次に磨きます。検査系の行は、読者タスクと手順の実走が揺れうるので残しています。

## 7. 実行前チェック

- リポジトリをgitにコミットし、専用ブランチか `git worktree` で回す。開始コミットのハッシュを控え、床の変更範囲の確認に使う
- 章の所在が `docs/getting-started/` で合っているか確かめる。違えば、プロンプトと床のパスを実際の場所に書き換える
- `docusaurus.config.js` の `onBrokenLinks` が `throw` になっているか確かめる。なっていなければ、リンク切れの検査を床に別途足す
- 無関係なskill・MCPを切った、クリーンなセッションで回す
- 予算を見張る。8時間・多数のサブエージェント・高effortの組み合わせは、プランの上限を大きく食う。数時間おきに使用量を確認し、危なければ手動で止める
- 「未確認」と書いた参照4つ（Docusaurus、Vite、Django、Stripe）を実際に開き、取得できることを確かめる。開けない段は差し替えるか外す
- 参照のスナップショット（`refs/`）は評価専用。成果物に取り込まない。`refs/` をサイトのビルド対象に含めない
- 手順の実走は、社内の認証情報や本番環境に触れない使い捨てディレクトリで行う。章に社内システムへのログインなどが含まれていて実走できない手順は、実走の対象から外したことを台帳に記録する
