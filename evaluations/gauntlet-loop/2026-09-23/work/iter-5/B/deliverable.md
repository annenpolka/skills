# ガントレット・ループ設計（決済まわり）: ゲート前

「回して」だけではこのセッションでの実行の指定とは受け取れないので、まず設計（compose）として出します。ループはまだ一周も回していません。下の「確認したいこと」に答えてもらえれば、梯子の全段・床のコマンド・実行プロンプト・実行前チェックまで仕上げます。

## 1. 判定（対象ごと）

| 問い | 手数料計算 `src/fees.ts` | 決済完了メール `templates/receipt.mjml` |
|---|---|---|
| 1. 実物を検査できるか | はい（実行できる） | はい（MJMLをHTML化して描画し、読める） |
| 2. 取得できるバーの候補があるか | 不要 | はい（下の候補） |
| 3. 良さが機械検証だけでは決まらないか | **いいえ**。求められるのは正しさで、正しさはテストが決める | はい。分かりやすさや安心感はテストでは決まらない |
| 4. 予算の上限を決められるか | — | はい（値は下で聞きます） |
| 結論 | **回さない。** Jest（`npm test`）に境界値（端数処理・最低手数料・0円・上限・通貨）を足して閉じる | **回す** |

手数料計算はループで磨く対象にはしません。ただし機械検査としてメール文面ループの**床**に組み込みます（§4）。メールに載る金額は手数料計算の結果なので、文面を磨く途中で金額表示が壊れたら、その変更は通しません。

## 2. バー（メール文面）: 最上段の候補

| 案 | 候補 | 選ぶ理由（一文） | 取得方法 |

| A | Stripe の顧客向け決済レシートメール（テストモードで発行） | 金額・内訳・支払手段・問い合わせ先を一画面にまとめた定番の形で、同じ注文データを入れて同じ条件で何通でも出せる | Stripe テストモードで決済を作り、レシートメールを送信して保存（未確認） |

案を選んでもらった後に、下の段（現行の `receipt.mjml` → 同規模ECの平均的なメール → …）を含む 3〜5 段の梯子を固定し、1周目の前に隣り合う段の順を新しい批評役で較正します。

## 3. 比べ方（方針）

好みの比較は割れやすく、題材（店名・ブランド）で出自も見抜かれるので、**読者タスクを主な判定**にします。

- 新しいエージェントに、正規化したメール1通だけを読ませ、固定した設問に答えさせる。正答数（と答えるまでに迷った箇所）で比べる
- 設問は内容に依存しない型で固定する:
  - 最終的にいくら払ったか（小計・手数料・送料・合計のそれぞれ）
  - 何をいつ買ったか（注文番号・日時・品目）
  - 支払いは完了しているか、どの手段で払ったか
  - 次に何が起こるか（発送・ダウンロード等）、いつ頃か
  - 問題があったら何をするか（問い合わせ先・キャンセル／返品の入口）
- 正規化: 同じ注文データ（金額・品目）を流し込み、同じ幅（デスクトップ 600px／モバイル 375px）で描画、テキスト抽出も同じ手順。店名・社名・URL・ロゴは中立の記号に置き換える
- 伏せた一対比較は補助にとどめる

各段の正答と正規化の細部は、バーが決まった後に作って `refs/` に固定します。

## 4. 床（見込み）

| コマンド／検査 | 状態 |
|---|---|
| `npm test`（Jest。手数料計算のテストを含む） | 既存 |
| MJML のビルドが警告なしで通る（strict バリデーション） | 既存かは未確認（ゲート後に確かめる） |
| **金額の突合**: 注文フィクスチャ数件で `fees.ts` の計算結果を出し、同じフィクスチャで描画したメール中の金額（小計・手数料・合計）が一致しなければ非ゼロで終了する | **新規**。1周目の前に作り、現行版に二度走らせて同じ結果になることを確かめてから床にする |
| 描画サイズの予算（HTMLサイズ・画像数）など、守りたい軸があれば | 必要なら追加 |

床が赤い変更は、比較でどれだけ勝っていても批評に回さず、採用しません。

## 5. 停止条件（案）

- 予算: **3時間**、または周回 20 周のどちらか先（案。トークン上限は実行前チェックで見張る）
- 停滞: 梯子の位置が **3周** 動かず、欠陥も減らなければ人間へ
- 勝利判定: 新しい批評役 **3体** が全員一致、かつ順番を入れ替えても最上段に勝ち、床が緑
- 他に止まる場合: 原因調査後も同じ症状が残る、参照が取得できない、検査系が再現しない、批評の要求が床（金額の正しさ）と矛盾する
