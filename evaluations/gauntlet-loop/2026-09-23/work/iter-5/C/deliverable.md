## 2. バー: 最上段の候補（ここから一つ選んでください）

同じカテゴリで、実在して公開されているランディングページから選びました。どれもこの設計のために開いて確かめてはいないので、「未確認」です。実行前チェックで実際に開けるかを確かめます。

| 案 | 最上段 | 選んだ理由（一文） |
|---|---|---|
| A | **Things**（culturedcode.com/things/）のトップ | 少人数で作った個人向けタスク管理アプリのLPで、規模と読み手が近く、しかも仕上げの水準の高さで定評があるので、「個人開発でも届く最上段」になる |
| B | **Todoist**（todoist.com）のトップ | 個人向けタスク管理の代表格。何のアプリか、なぜ使うか、どう始めるかを一画面目で伝える型が完成していて、比べる軸がはっきりしている |
| C | **Superlist**（superlist.com）のトップ | 新しめのタスク管理アプリで見た目の作り込みが強く、ビジュアルの印象で勝ちたいならこちらが目標になる |

絞り込みの経緯（六条件で落とした候補）:

- Notion、ClickUp: 「オールインワン」のワークスペースで、タスク管理のLPとして**同種同尺**ではない。訴求の幅が違いすぎて、比べても感想にしかならない
- Asana、Monday.com: 企業向けの営業導線（デモ予約、導入事例の壁）が中心。個人開発アプリとは読み手も分量も違い、**識別可能**な近さがない
- Linear: デザインの評価は高いが開発チーム向けのissue管理。見た目が強い独特の型なので、目標にすると写したくなる（**素材ではない**に反するおそれ）
- 「おしゃれなSaaSのLP」「Awwwards受賞サイト」のような括り: **名指し**になっていない

どれを選んでも、開始時にページを `refs/` へスナップショットして固定します。参照は水準の目安で、文面、画像、レイアウトは成果物に取り込みません。

梯子の全段（最上段の下の段）と取得方法は、最上段が決まってから確定します。形は「現在のLP → 同カテゴリの平均的なLP → 選んだ最上段」の3〜4段で、1周目の前に隣り合う段の順を新しい批評役にブラインドで比べさせて較正します。

## 3. 比べ方（方針）

Web/UIの型を使います。

- デスクトップとモバイルの固定ビューポートで、同じ内容量（ファーストビュー＋スクロール数画面分）を撮影します
- LPの好みは割れやすく、ブランドも出自を明かしてしまうので、**判定の主は読者タスク**にします。新しいエージェントに片方のページだけを見せ、内容に依存しない同じ設問に答えさせ、正答率で比べます。設問の型:
  - これは何のアプリか
  - 誰のためのものか
  - 似たアプリと何が違うか
  - 最初に何をすればよいか（どこを押すか）
  - 無料で試せるか、費用はどうか
- 伏せた一対比較（どちらがバーに近いか、差を分けた最大の症状は何か）は補助にします。製品名、ロゴ、URLは中立の記号に置き換えます
- 各ページの正答は開始時に作って `refs/` に固定します。設問集は検査系の一部として、1周目の前に検証します

## 4. 床（見込み）

所在はリポジトリを見てから確かめます。現時点では見込みです。

- `next build`（または `npm run build`）
- リンタ（`npm run lint`）
- 既存のテストがあればそれも（`npm test` 等）
- **新規**: a11yの自動検査（Playwright＋axeでLPのURLを検査し、重大な違反0件で終了コード0）
- **新規**: 表示性能の予算（Lighthouse CIでモバイルのLCP・CLS・転送量に上限を置く）
- **新規**: 撮影の再現性チェック（同じ版を二度撮影して画素差分が許容差内）

新規のものは1周目の前に作り、現行のLPに二度走らせて同じ結果になることを確かめてから床に入れます。
