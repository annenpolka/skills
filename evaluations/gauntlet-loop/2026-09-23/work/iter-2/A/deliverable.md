# ガントレット設計: 社内Docusaurus『はじめに』章 → Stripe Docs 入門水準

composeモードで設計しました。実行は別のクリーンなセッションで行う前提です。

## 1. 判定: 回す

| 問い | 答え |
|---|---|
| 1. 成果物をエージェントが実物として検査できるか | はい。Markdown/MDXを読めるうえ、`npm run build` した実ページも見られる。手順は新しいエージェントに実際にたどらせて検査できる |
| 2. 取得できるバー候補があるか | はい。Stripe Docs も下の段の候補も公開ページなので、取得してスナップショットを取れる |
| 3. 「良い」が機械検証だけでは決まらないか | はい、決まらない。ビルドとlintが通っても分かりやすさは保証されない。ビルド・lint・リンク・手順の実行可能性は床に、分かりやすさは梯子に振り分ける |
| 4. 予算の上限を決められるか | はい。壁時計で8時間 |

→ 回します。

## 2. バー

**最上段: Stripe Docs「Set up your development environment」**（`https://docs.stripe.com/get-started/development-environment`）。
「Stripe Docs の入門チュートリアル」はサイト単位のご指定で、特定のページまでは決まっていませんでした。そこで、社内向け『はじめに』章と役割が最も近いページを選んでいます。このページは、環境構築から最初の成功確認、次の一歩までを一本の流れで案内します。**開始前なら差し替えられます**（例: `https://docs.stripe.com/payments/quickstart`）。

梯子（下→上）。開始時にすべてを取得し、`refs/` に固定します。

| 段 | 実物 | 取得方法 |
|---|---|---|
| 0 | 現行の『はじめに』章（開始時のコミット） | `git worktree` で開始時のコミットを取り出し、`refs/rung0/` にコピーする |
| 1 | Docusaurus 公式チュートリアル「Tutorial Intro」〜「Create a Page」（`https://tutorial.docusaurus.io/docs/intro`） | ページ本文をMarkdownに落として `refs/rung1/` に置く |
| 2 | Vite「Getting Started」（`https://vite.dev/guide/`） | 同上で `refs/rung2/` に置く |
| 3 | Django「Writing your first Django app, part 1」（`https://docs.djangoproject.com/en/stable/intro/tutorial01/`） | 同上で `refs/rung3/` に置く。版の変動を避けるため、取得日とURLを記録する |
| 4（最上段） | Stripe「Set up your development environment」 | 同上で `refs/rung4/` に置く。取得日時とHTMLの原本も保存する |

- 段1〜3も同じ扱いです。開始前なら差し替えられます。開始後は変えません
- 参照は水準の目安として使い、文章も構成も成果物に写しません。スナップショットは評価専用です
- **較正**: 1周目の前に、新しい批評役に隣り合う段（0-1, 1-2, 2-3, 3-4）をブラインドで比べさせます。順が崩れた段は入れ替えるか外します。3段未満になった場合や、較正が成り立たない場合は止めて人間に戻します

## 3. 比べ方

好みの比較（「どちらが分かりやすいか」）は割れやすいので、**読者タスク**を主にします。

- **正規化**: 各章を本文だけのMarkdownに揃えます（ナビ・装飾・ブランド要素は除く）。製品名・社名・固有URLは `<PRODUCT>` `<URL>` などの伏せ字に置き換え、見た目や出自の癖で「どちらが本物か」が当たらないようにします。コードブロックは残します
- **読者タスク（全段共通）**: 新しいエージェントに片方だけを読ませ、共通設問8問に本文だけを根拠に答えさせます。設問は次のとおりです。
  1. この章を終えると何ができているか
  2. 始める前に必要なもの
  3. 最初に打つコマンドや操作
  4. 各ステップが成功したとどう確かめるか
  5. 典型的な失敗の症状と対処
  6. 出てきた用語の意味
  7. 所要時間の目安
  8. 次に読むべきもの

  比べるのは「根拠箇所つきで答えられた設問数」と「根拠箇所に着くまでに読んだ段落数」です。
- **ブラインド一対比較**: 読者タスクの結果と正規化した本文を、ラベルを伏せて一対ずつ比べ、勝敗と、差を分けた最大の症状を場所つきで一つ返させます（直し方は書かせない）
- **実走タスク（自章のみ、欠陥数として記録）**: 新しいエージェントをクリーンな環境に置きます。自章だけを見て手順を最後まで実行させ、詰まった箇所の数を記録します。欠陥数の推移と停滞判定に使います

## 4. 床

終了コードで判定します。床が赤い変更は批評に回しません。

- `npm run build`（`docusaurus.config` の `onBrokenLinks` が `throw` でないなら、壊れたリンクを検出するリンク検査コマンドを床に加える）
- `npm run lint`
- 所有範囲の検査: `git diff --name-only <開始コミット> -- . ':(exclude)docs/getting-started/**' ':(exclude)gauntlet/**' ':(exclude)refs/**' | (! grep .)`（『はじめに』章のディレクトリ名は実リポジトリに合わせる）
- `node gauntlet/tools/check-steps.mjs`: 章内のシェルコマンドを抜き出してクリーンなコンテナで順に実行し、すべて0で終わるかを見る。1周目の前に作り、同じ版で二度回して一致することを確かめてから床に入れる。実行できない社内依存のコマンドは明示的に除外リストに書く

## 5. 停止条件

- **予算**: 壁時計8時間（トークン上限も決めるなら台帳の先頭に書く）
- **停滞**: 梯子の位置が3周動かず、実走の欠陥数も減らないとき → 人間へ
- **勝利**: 新しい批評役3体が全員一致で、順番を入れ替えても章全体がStripe（段4）に勝つと判定し、かつ床が緑のとき
- **その他**: 原因を調べても同じ症状が再発する、参照が取得できない、検査系が再現しない、批評の要求が床・所有範囲と衝突する、社内の事実（手順・権限）の判断が要る → 止めて報告

## 6. 実行プロンプト

『はじめに』章は冒頭から最後まで同じ前提（読者像、環境、用語）を共有する一本の流れです。そのため一つの単位にし、一人の担当が逐次に磨きます。並列の［任意］行は落としました。検査系の再現性（読者タスクの揺れ）は起こりうるので、検査系の行は残しています。

```text
社内技術ドキュメントサイト（Docusaurus）の『はじめに』チュートリアル章を、新しく来たエンジニアが迷わず最後までたどり着ける水準に書き直す。編集してよいのは『はじめに』章のディレクトリ（docs/getting-started/ 相当）と gauntlet/ だけ。

バーは Stripe Docs「Set up your development environment」（https://docs.stripe.com/get-started/development-environment）。途中の段として 段0: 開始時点の現行『はじめに』章、段1: Docusaurus 公式チュートリアル Tutorial Intro〜Create a Page（https://tutorial.docusaurus.io/docs/intro）、段2: Vite Getting Started（https://vite.dev/guide/）、段3: Django Writing your first Django app, part 1（https://docs.djangoproject.com/en/stable/intro/tutorial01/）を使う。開始時にすべてを refs/ に保存し、以後はそれを基準にする。参照は評価専用で、文章も構成も写さない。
比べ方: 各章を本文だけのMarkdownに正規化し、製品名・社名・URLを伏せ字にする。新しいエージェントに片方だけを読ませて共通設問8問（到達点、前提、最初の操作、成功の確かめ方、典型的な失敗と対処、用語、所要時間、次に読むもの）に本文だけを根拠に答えさせ、根拠つきで答えられた数と、そこに着くまでに読んだ段落数で比べる。そのうえでラベルを伏せた一対比較を行う。あわせて、自章は新しいエージェントにクリーンな環境で手順を最後まで実行させ、詰まった箇所の数を欠陥数として記録する。
床は npm run build、npm run lint、所有範囲外の差分が無いことの検査、章内のコマンドをクリーンなコンテナで実行する gauntlet/tools/check-steps.mjs。床を通らない変更は評価に回さない。

進め方はあなたが決めてよい。守ることだけを書く。
- 作業を、独立に改善・判定できる単位に分ける。前提を共有する部分は一つの単位にし、一人の担当が順に磨く。並列にするのは結合の無い単位だけ。
- 各単位に作る役と、毎回新しい批評役を立てる。批評役には目標・バー・実物だけを渡し、作る役の説明は渡さない。
- 批評役は、どちらが自作か伏せたまま実物と梯子の段を比べ、勝敗と、差を分けた最大の症状を場所つきで一つ返す。直し方は言わない。
- 作る役は症状を計測で確かめてから、それだけを直す。計測が批評と食い違ったら計測に従う。同じ症状が二周続いたら、直すのをやめて原因を調べる。
- 1周目の前に検査系を作り、同じ版を二度検査して一致することを確かめる。実物と参照は同じ条件で並べる。1周目の前に隣り合う段をブラインドで比べて梯子の順を較正し、崩れたら止めて報告する。
- 波の終わりに、全体を新しい批評役に見せて部品間の食い違いを直し、全体と参照の全体を比べる。
- 勝ったと言えるのは、新しい批評役 3 体が全員、順番を入れ替えても最上段に勝つと判定したときだけ。
- 止めるのは、勝ったとき、予算 壁時計8時間 を使い切ったとき、梯子の位置が 3 周動かないとき、原因を調べても同じ症状が残るとき、参照が取得できないとき。社内の事実や権限の判断が要るときも止める。止まったら理由と現状を報告する。
- 状態は gauntlet/ledger.yaml に置き、進み具合を gauntlet/index.html に示し続ける。
- サブエージェントを使う。/loop や高いeffort設定が使えるなら使う。
```

## 7. 実行前チェック

- 作業ブランチを切って現状をgitにコミットする。可能なら `git worktree` かコンテナで回す（check-steps はコンテナ必須）
- 無関係なskill・MCPを切った、クリーンなClaude Codeセッションで回す
- 予算を見張る。8時間・多数のサブエージェント・高effortの組み合わせは、プラン上限を大きく食います。途中で上限に当たっても台帳から再開できます
- 参照のスナップショットは評価専用にし、成果物に取り込まない
- 社内文書を外部に送らない。勝利判定に別系統のモデルを混ぜる場合は、社内文書をそのサービスへ送ってよいかを先に確認する。許可が無ければ同系統のみで判定し、その旨を台帳に書く
- 最上段と段1〜3の選定に異論があれば、開始前に差し替えてください
