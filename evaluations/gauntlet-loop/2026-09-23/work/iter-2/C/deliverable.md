ガントレットで回せる題材です。まだバー（比べる相手の実在サイト）が決まっていないので、最初にそれを選んでもらいます。実行プロンプトは、バーが決まってから書きます。

## 1. 判定（回すかどうか）

| 問い | 答え | 理由 |
|---|---|---|
| 成果物を実物として検査できるか | はい | Next.js のページをビルドして起動し、固定したビューポートで撮影・計測できる |
| 取得できるバー候補があるか | はい | 同じカテゴリの公開ランディングページが多数あり、批評役がブラウザで開いて撮影できる |
| 「良い」が機械検証だけでは決まらないか | はい | 伝わりやすさ、第一印象、登録したくなるかどうかはテストでは決まらない。ビルド・a11y・表示性能のように機械で決まる部分は床に回す |
| 予算の上限を決められるか | はい（値は下で決めてもらう） | 時間またはトークンで上限を切れる |

→ **回します。**

## 2. バー候補（最上段）: どれか一つを選んでください

候補を探し、六つの条件（名指し・取得可能・同種同尺・識別可能・固定・素材ではない）で絞りました。

| 案 | 対象ページ | 選んだ理由 |
|---|---|---|
| **A. Things 3** | https://culturedcode.com/things/ | 少人数で作られた個人向けタスク管理アプリで、ページの規模と対象読者があなたのアプリに最も近く、「一つの製品を静かに、分かりやすく見せる」水準として定評がある |
| **B. Todoist** | https://www.todoist.com/ | 個人向けタスク管理の代表格で、見出し・価値の伝え方・登録導線の定石が揃っているため、差が症状として言葉にしやすい |
| **C. Linear** | https://linear.app/ | 開発者向けツールのランディングページとして視覚の完成度の最上位に置かれることが多い。ただし対象がチーム向けの課題管理なので、同種同尺はA・Bより弱い（見た目の水準を狙うなら候補になる） |

外した候補と理由:
- Notion、Asana: 製品の範囲と会社の規模が大きすぎて、同じ量の中身で並べられない（同種同尺で落ちる）
- 終了・大改装が続いているサービス: 実行中にページが変わる恐れがある（固定で落ちる）
- 「おしゃれなSaaSのLP全般」のようなカテゴリ: 名指しになっていない

どの案でも、開始時にページを `refs/` へ保存し、以後はその保存版と比べます。参照は水準の目安として使うだけで、文言・画像・レイアウトを成果物に写すことはしません。

## 3. ゲートの前に決めてある既定値（選んだ後で変更できます）

- **床の見込み**: `next build` が通る、リンタ（`next lint` など、既にあるもの）、a11y の自動検査（axe / Lighthouse accessibility が一定以上）、表示性能の予算（Lighthouse performance や LCP の上限）。実際のコマンドは、リポジトリの `package.json` を見て確定します
- **停止条件の既定値**: 梯子の位置が3周動かなければ人間に戻す（停滞3周）。「最上段に勝った」と言えるのは、新しい批評役3体が全員、順番を入れ替えても勝ちと判定したときだけ

## 4. 一度にまとめて答えてほしいこと

1. **バー**: A / B / C のどれにしますか（ほかに意識しているサイトがあれば、それを挙げてもらっても構いません。六条件で確認してから使います）
2. **予算の上限**: 時間（例: 4時間）かトークン量のどちらか、または両方
3. **実行の場所**:
   - compose（おすすめ）: ここでは実行プロンプトまで作り、あなたが無関係なskillやMCPを切ったクリーンなClaude Code / Codexのセッションに貼って回す
   - run: このセッションで私がリードとして回す（この場合、ほかのskillが有効なままのセッションで回すことになります）
4. **ランディングページのリポジトリの場所**（このセッションで見られるパス、または公開URL）

回答をもらったら、梯子の途中の段、比べ方、床のコマンド、停止条件、実行プロンプト、実行前チェックを書きます。
