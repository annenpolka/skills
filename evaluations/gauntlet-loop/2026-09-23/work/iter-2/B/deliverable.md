# 決済まわりのガントレット設計（compose）

「回して」とのことですが、ここではまず実行プロンプトを設計するところまでを出します（compose）。このセッションでは他のskillが多数有効になっていて、ループが乗っ取られやすいためです。私自身はまだ一周も回していません。以下は設計と、決めていただきたい事項です。

## 1. 判定（Phase 0）

依頼は性質の違う二つに分かれるので、別々に判定しました。

### 手数料計算（src/fees.ts）: 回しません。床（機械検証）に回します

| 問い | 答え |
|---|---|
| 1. 実物として検査できるか | はい（実行できる） |
| 2. 取得できるバーがあるか | 意味のあるバーが無い |
| 3. 「良い」が機械検証だけでは決まらないか | **いいえ**。手数料計算に求められるのは正しさで、正しさはテストで決まります |
| 4. 予算を決められるか | はい |

問い3が「いいえ」なので、ブラインド比較のループは費用に見合いません。代わりに次の手当てをします。

- Jest テスト（`npm test`）を拡充して閉じる: 境界値（0円、最小・最大金額）、端数処理（丸めの方向と桁）、税込・税抜の順序、通貨ごとの小数桁、返金・部分返金、料率の切り替え日
- 可能なら性質ベースのテスト（例: 手数料が非負で、金額を上回らない。金額が増えても手数料は減らない）
- そのうえで `npm test` を、下のメール側ループの**床**として使います。メール文面を磨いている最中に計算側が壊れても、そこで止まります

### 決済完了メール（templates/receipt.mjml）: 回します

| 問い | 答え |
|---|---|
| 1. 実物として検査できるか | はい（MJMLをHTMLにレンダリングし、読んで、撮影できる） |
| 2. 取得できるバーがあるか | はい、候補は実在します（下記） |
| 3. 「良い」が機械検証だけでは決まらないか | はい。分かりやすさ、安心感、次の行動の見つけやすさはテストでは決まりません |
| 4. 予算を決められるか | はい（下のゲートで決めてください） |

機械で決まる部分（金額が正しく差し込まれること、MJMLが妥当であること）は床に回し、決まらない部分（読み手にとっての文面の質）をバーに回します。

## 2. バーの候補（ここで一度決めていただきます）

メール文面のバーが指定されていないので、候補を三つ挙げます。どれも「取得できる」「同じ粒度で並べられる」「中身は写さない」を満たすものです。参照のHTMLとスクリーンショットは開始時に `refs/` に保存して固定します。**使うのは水準の目安としてだけで、文面や構成を成果物に取り込むことはしません**（模倣で勝つのを防ぐため。ライセンス上も取り込めません）。

| 案 | 最上段の候補 | 取得方法 | 選ぶ理由（一文） |
|---|---|---|---|
| A（推奨） | Stripe のテストモード決済で送られる領収書メール | テストモードで決済し、自分宛てに送らせてHTMLを保存 | 決済領収書として同じ種類・同じ粒度で、何度でも同じ条件で取り直せます |
| B | Shopify の既定の「注文確認」通知テンプレート | Shopify 管理画面の通知テンプレートから、テスト注文で生成したメールを保存 | EC の注文完了メールとして広く目にされる基準線で、商品明細つきの構成を比べられます |
| C | 大手ECで実際に受け取った注文確認メール（例: 自分のアカウントでの Amazon.co.jp の注文確認） | 手元のメールボックスからHTMLを書き出す | 読み手が普段見慣れている水準そのものですが、個人情報の伏せ字処理が必要になります |

梯子の途中の段（例: 現行の receipt.mjml → 案B → 案A）、比べ方の細部、実行プロンプトは、バーが決まってから書きます。

### ほかに、同じ場で決めていただきたいこと

1. **バー**: A / B / C のどれにするか（ほかに意識しているメールがあれば、それでも構いません）
2. **予算の上限**: 時間・トークン・周回数のどれで区切るか（案: 3時間）
3. **実行の場所**: compose（この設計をもとに、他のskillやMCPを切ったクリーンなセッションで回す。推奨）か、run（このセッションで私がリードとして回す）か。run にする場合、このセッションで他のskillが多数有効になっていることは承知のうえで選んでください
4. **正の金額の見本**: 床のメール金額チェックに使う注文フィクスチャ（明細・税・手数料の組み合わせ）を既存のテストデータから流用してよいか

## 3. バーに依存せず、この時点で決めておけること

### 床（見込み）

終了コードで判定するコマンドです。どれか一つでも赤い変更は批評に回しません。

- `npm test` — 手数料計算の Jest テスト（上で拡充するもの）
- MJML の厳格検証 — 例: `npx mjml --validate strict templates/receipt.mjml` で妥当性を確認
- **メール内の金額の照合** — 固定の注文フィクスチャ群について、`src/fees.ts` で計算した小計・手数料・税・合計と、`receipt.mjml` をレンダリングしたHTMLに表示される金額（通貨記号・桁区切りを含む）が一致することを検査するスクリプト（例: `node tools/check-receipt-amounts.mjs`、新規に作る）。文面を磨く過程で金額表示が消えたり、ずれたりするのを機械で止めます
- （必要なら）HTMLサイズの上限（Gmail は約102KBを超えると本文を切り詰めます）とリンク切れの検査

コマンド名は現時点での提案です。リポジトリの実際のスクリプト名に合わせて確定させます。

### 比べ方の方向（領域の型: 文章）

「どちらのメールが良いか」は好みで割れやすいので、課題に変えて比べる予定です。例えば、新しいエージェントにどちらか片方のメールだけを読ませ、次の設問にどれだけ速く正確に答えられるかを比べます。

- 請求された合計額と、そのうちの手数料はいくらか
- 何を買ったか、いつ届くか
- 返品・問い合わせをするには次に何をすればよいか
- このメールが本物の決済通知だと判断できるか（送信元・注文番号の見つけやすさ）

あわせて、ラベルを伏せた一対比較も行います。どちらもレンダリング済みのHTMLとスクリーンショットを同じ幅（デスクトップ600px・モバイル375px）・同じ注文内容・同じ個人情報の伏せ方にそろえ、出自の癖で見分けられないようにします。細部はバーが決まってから確定します。

### 停止条件（既定値）

- **予算**: 上のゲートで決める上限（案: 3時間）
- **停滞**: 梯子の位置が3周動かず、欠陥も減らなければ人間に戻す
- **勝利判定**: 新しい批評役3体が全員一致で、提示順を入れ替えても最上段に勝つと判定し、かつ床が緑のときだけ。可能なら別系統のモデルを1体混ぜる
- そのほか: 原因を調べても同じ症状が残ったら人間へ。参照が取得できない、または検査系が再現しない場合は停止

## 次の一歩

上の「決めていただきたいこと」1〜4に答えていただければ、梯子の段、比べ方の細部、クリーンなセッションに貼る実行プロンプト、実行前チェックを書きます。手数料計算のテスト拡充は、ループとは別の通常の作業として先に進めて構いません。
