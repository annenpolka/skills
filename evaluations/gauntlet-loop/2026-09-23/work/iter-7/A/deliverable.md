# 『はじめに』チュートリアル章 ガントレット設計

バーは「Stripe Docs の入門チュートリアル」と指定されているので、ページを一つ選んだうえで設計を最後まで出します。選んだページは開始前なら差し替えられます。実行は別セッションで行う前提なので、このセッションはcomposeモードで設計だけを書きます。

## 1. 判定（Phase 0）

| 問い | 答え | 理由 |
|---|---|---|
| 1. 成果物を実物として検査できるか | はい | `npm run build` で出力したHTMLを読める。書かれた手順を実際にたどることもできる |
| 2. 取得できるバー候補があるか | はい | Stripe Docs は公開ページ。下記の梯子の各段は、設計時にこの環境から開けることを確かめた |
| 3. 良さが機械検証だけでは決まらないか | はい | 「分かりやすさ」はビルドやlintでは決まらない。ビルド、lint、リンク切れ、手順が実際に動くかどうかは床として別に扱う |
| 4. 予算の上限を決められるか | はい | 一晩8時間という指定がある。トークンの上限は実行前チェックで見張る |

→ **回す。**

## 2. バー

**最上段: Stripe「Stripe がオンラインで提供する Checkout ページを作成」クイックスタート**（https://docs.stripe.com/checkout/quickstart ）
選んだ理由: Stripe Docs の入門チュートリアルの中で、前提、手順、動作確認（テストカード）、「完了しました」、次のステップという流れを1ページで最後までたどれる代表的な例だから。Stripe のページとしては、ほかに「支払いを受け付ける」（accept-a-payment）も候補になります。こちらに差し替えたい場合は開始前に言ってください。

梯子（下→上、4段）:

| 段 | 実物 | 取得方法 | 確認 |
|---|---|---|---|
| 0 | 現行の『はじめに』章（開始時点のコミット） | 開始時のコミットで `npm run build` を実行し、該当ページのHTMLを `refs/rung0/` に保存する | 章のパスは未確認（下記参照） |
| 1 | Docusaurus「Tutorial Intro」 https://tutorial.docusaurus.io/docs/intro | ページのHTMLと本文を `refs/rung1/` に保存し、取得日時を記録する | 設計時に開けた |
| 2 | Vite「はじめに（Getting Started）」 https://vite.dev/guide/ | 同上で `refs/rung2/` | 設計時に開けた |
| 3 | Stripe Checkout クイックスタート（上記URL） | 同上で `refs/rung3/`。言語タブは Node に固定し、Node の版だけを保存する | 設計時に開けた |

- 途中の段（1と2）はこちらで選んだものです。順番の妥当性は、1周目の前の較正で確かめます。新しい批評役に隣り合う段をブラインドで比べさせ、順が崩れた段は入れ替えるか外します。
- 梯子の中身は開始後に変えません。変えたくなったらランを止め、利用者に戻します。
- 参照は水準の目安として使うだけで、本文を写しません。`refs/` の中身は評価専用とし、成果物には取り込みません。

## 3. 比べ方

題材が違う（決済の入門と社内ドキュメントの入門）うえ、Stripe は見た目や固有名で出自が分かってしまいます。そのため**読者タスクを主な判定**にし、伏せた一対比較は補助にとどめます。

- **読者タスク**: 新しいエージェントに文書を一つだけ読ませ、内容に依存しない次の設問に答えさせる。正答数で比べる。
  1. 始める前に何が必要か（前提）
  2. 最初に打つコマンド、または最初にする操作は何か
  3. うまくいったら何が見えるか
  4. うまくいかなかったら何をすればよいか
  5. 読み終えたら次に何をするか
  6. 途中で「なぜこの手順が要るのか」を説明できるか
  各文書の正答は開始時に作り、`refs/answers/` に固定する。読者は毎回新しく立て、文書は一つしか渡さない。
- **伏せた一対比較（補助）**: 本文をプレーンテキストの同じ書式に正規化して比べる。コードブロックは残し、見出しの深さを揃え、ナビゲーションやサイドバーは除く。製品名、社名、URLは中立の記号（例: `〈製品A〉`、`〈URL〉`）に置き換える。長さは目安として揃える。
- 進捗の周で比べるのは三対だけ: 現在の段、一つ上の段、前の版。

## 4. 床（終了コードで判定）

| コマンド | 内容 | 状態 |
|---|---|---|
| `npm run build` | Docusaurus のビルド。リンク切れで失敗するかどうかは `onBrokenLinks` の設定次第なので、設定を確かめる | 既存（package.json 上の所在は未確認） |
| `npm run lint` | 既存のlint | 既存（同上） |
| `node gauntlet/tools/walkthrough.mjs` | 章に書かれたコマンドを、新しい一時ディレクトリで上から順に実走し、どれかが失敗したら非ゼロで終了する | **新規**。1周目の前に作る。現行版に二度走らせて同じ結果になることを確かめてから床にする |
| `node gauntlet/tools/scope-check.mjs` | 開始時のコミットからの `git diff --name-only` が『はじめに』章のディレクトリ（と、その画像）に収まっていることを確かめる | **新規**。上と同じく二度走らせて確かめる |

床が赤い変更は批評に回しません。比較でどれだけ勝っていても採用しません。

## 5. 停止条件

- 予算: **8時間**（壁時計）。トークンは実行前チェックで見張る
- 停滞: 梯子の位置が **3周** 動かず、読者タスクの誤答も減らない → 人間へ
- 勝利判定: 新しい批評役 **3体** が全員、提示順を入れ替えても最上段に勝つと判定し、かつ床が緑 → 終了
- ほかに、次のどれかで止めて報告する: 原因調査の後も同じ症状が出る、参照が取得できない、検査系が再現しない、批評の要求が目標や床と矛盾する

## 6. 実行プロンプト（別セッションの Claude Code にそのまま貼る）

```text
社内技術ドキュメントサイト（Docusaurus）の『はじめに』チュートリアル章を、初めて読む社員が迷わず最後まで進め、成功を確かめ、次に何をするか分かる水準にする。対象は『はじめに』章のファイルだけ。

バーは Stripe の Checkout クイックスタート（https://docs.stripe.com/checkout/quickstart 、言語タブは Node に固定）。途中の段として、開始時点の現行章、Docusaurus の Tutorial Intro（https://tutorial.docusaurus.io/docs/intro）、Vite の Getting Started（https://vite.dev/guide/）を使う。開始時にすべてを refs/ に保存し、以後はそれを基準にする。1周目の前に、隣り合う段を新しい批評役にブラインドで比べさせ、順が崩れる段は入れ替えるか外す。
比べ方: 主な判定は読者タスク。新しいエージェントに文書を一つだけ読ませ、「前提は何か／最初の一手は何か／成功したら何が見えるか／失敗したらどうするか／次に何をするか／なぜその手順が要るか」に答えさせ、開始時に refs/answers/ に固定した正答との一致数で比べる。補助として、同じ書式のプレーンテキストに正規化し、製品名・社名・URLを中立の記号に置き換えた本文を、伏せて一対で比べる。
床は npm run build、npm run lint、node gauntlet/tools/walkthrough.mjs（章のコマンドを一時ディレクトリで実走する。新規に作る）、node gauntlet/tools/scope-check.mjs（変更が章のディレクトリに収まることを確かめる。新規に作る）。床を通らない変更は評価に回さない。

進め方はあなたが決めてよい。守ることだけを書く。
- 作業を、独立に改善・判定できる単位に分ける。前提を共有する部分は一つの単位にし、一人の担当が順に磨く。並列にするのは結合の無い単位だけ。
- 各単位に作る役と、毎回新しい批評役を立てる。批評役には目標・バー・実物だけを渡し、作る役の説明は渡さない。
- 批評役は、どちらが自作か伏せたまま実物と梯子の段を比べ、勝敗と、差を分けた最大の症状を場所つきで一つ返す。直し方は言わない。
- 作る役は症状を計測で確かめてから、それだけを直す。計測が批評と食い違ったら計測に従う。同じ症状が二周続いたら、直すのをやめて原因を調べる。
- 1周目の前に検査系を作り、同じ版を二度検査して一致することを確かめる。実物と参照は同じ条件で並べる。
- 波の終わりに、全体を新しい批評役に見せて部品間の食い違いを直し、全体と参照の全体を比べる。
- 勝ったと言えるのは、新しい批評役 3 体が全員、順番を入れ替えても最上段に勝つと判定したときだけ。
- 止めるのは、勝ったとき、予算 8時間 を使い切ったとき、梯子の位置が 3 周動かないとき、原因を調べても同じ症状が残るとき、参照が取得できないとき。止まったら理由と現状を報告する。
- 状態は gauntlet/ledger.yaml に置き、進み具合を gauntlet/index.html に示し続ける。
- 批評役は毎回、文脈を共有しない別のサブエージェントか別プロセス（codex exec、claude -p 等）で立てる。
- /loop や高いeffort設定が使えるなら使う。
```

雛形との違い:
- 並列の［任意］行は落としました。章は一つの読み物の流れで、節同士が前提を共有しているからです。一つの単位として逐次に磨きます。
- 検査系の行は札を外して残しました。読者タスクも実走も試行ごとに揺れうるからです。
- Claude Code の行も札を外して残しました。

- [ ] 無関係なskillとMCPを切った、クリーンなセッションで起動する

- [ ] **未確認の項目を確かめる**: 『はじめに』章の実際のパス（`docs/` 以下のどこか）、`package.json` に `build` と `lint` があること、`docusaurus.config` の `onBrokenLinks` の値。パスが違っていたら、実行プロンプトと scope-check の対象を直す
- [ ] 実行直前に、梯子の3つの外部ページがまだ開けることを確かめる（設計時には開けた）。開けない段は開始前に差し替えるか外す
- [ ] `refs/` は評価専用で、成果物に取り込まないことを確認する
- [ ] 章の手順が社内の認証や社内ネットワークを要する場合は、walkthrough を実行する環境からそれに届くかどうかを確かめる
