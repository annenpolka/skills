# ガントレット設計: 社内ドキュメント「はじめに」チュートリアル章

モード: compose（実行は別のクリーンなセッションで行う前提）

## 1. 判定

| 問い | 答え |
|---|---|
| 1. 成果物をエージェントが実物として検査できるか | はい。Docusaurus をビルドして描画・読解でき、チュートリアルの手順を実際に打って確かめられる |
| 2. 取得できるバーの候補があるか | はい。Stripe Docs は公開されていて、取得も保存もできる |
| 3. 「良い」が機械検証だけで決まらないか | はい。分かりやすさはテストでは決まらない。ビルド・lint・リンク・手順が動くことは機械で決まるので、そちらは床に回す |
| 4. 予算の上限を決められるか | はい。壁時計で8時間 |

→ **回す。**

## 2. バー

**最上段: Stripe Docs「Get started」から入る入門チュートリアル（例: https://docs.stripe.com/get-started と、そこから辿る最初の成功体験までのページ群）。** 選んだ理由（一文）: 前提、最初の一手、期待される結果、次にやることが一続きで示され、初めての読者が迷わず最初の成功に届く入門ドキュメントとして定評があるから。

梯子（下→上、0始まり。開始時に固定し、以後は差し替えない）:

| 段 | 実物 | 取得方法 |
|---|---|---|
| 0 | 現行の「はじめに」章 | 開始時点のコミットを `git tag gauntlet-baseline` し、ビルドした当該ページ群を `refs/rung0/` に保存 |
| 1 | Docusaurus 公式チュートリアル（https://tutorial.docusaurus.io/docs/intro から Tutorial - Basics の最初の数ページ） | ページを取得し、本文とコードブロックを `refs/rung1/` に保存 |
| 2 | Supabase Docs の Next.js クイックスタート（https://supabase.com/docs/guides/getting-started/quickstarts/nextjs） | 同上、`refs/rung2/` |
| 3 | Stripe Docs の入門チュートリアル（上記） | 同上、`refs/rung3/`。取得日時と URL を `refs/MANIFEST.md` に記録 |

- 参照はすべて評価専用。文章・構成・コード例を成果物に写さない（批評役にも `imitation_suspected` を返させる）
- 段1・段2は、利用者が別の実物を好むならこの時点で差し替えてよい。開始後は変えない
- **較正**（1周目の前）: 隣り合う段（0対1、1対2、2対3）を新しい批評役に伏せて比べさせ、下の段が負ける順になるか確かめる。崩れた段は外すか入れ替える。段0が段1に勝ってしまうなら、段1を外して3段で回す

## 3. 比べ方

好みの比較は割れやすいので、**読者タスク**に変える。

- **正規化**: 各段と成果物を、同じ書式のプレーンな Markdown（見出し・本文・コードブロックのみ）に変換する。製品名・社名・ロゴ・配色・URL などの出自の手がかりは伏せ字にする（`{PRODUCT}` 等）。分量が大きく違う場合は「最初の成功体験まで」の範囲に切りそろえる。あわせて固定ビューポート（デスクトップ 1280px、モバイル 390px）のスクリーンショットも同条件で撮る
- **読者タスク**: 新しいエージェントに片方だけを読ませ、共通の設問テンプレートに答えさせる。設問は内容に依存しない型で固定する:
  1. 始める前に必要なものは何か
  2. 最初に打つコマンド（または操作）は何か
  3. それが成功したとき何が見えるか
  4. 失敗したとき、どこを見て何をすればよいか
  5. 最初の成功の後、次に何をすればよいか
  6. 読み終えるまでに、意味の分からなかった語はどれか（数える）
  正答は各ドキュメントの本文から開始時に作り、`refs/answers/` に固定する
- **成果物側の実行タスク**: 社内章については、新しいエージェントがクリーンな環境（コンテナ等）で章の手順だけを頼りに最初の成功まで進め、詰まった箇所と試行回数を記録する
- **伏せた一対比較**: 上の結果を材料に、批評役が伏せた二つを比べ、勝敗と差を分けた最大の症状を一つ（場所つき）返す

## 4. 床

終了コードで判定する。一つでも赤なら批評に回さない。

- `npm run build`（Docusaurus 設定で `onBrokenLinks: 'throw'` になっていることを開始前に確認する。なっていなければリンク切れ検査を別コマンドで足す）
- `npm run lint`
- `node gauntlet/check-scope.mjs` — `git diff --name-only gauntlet-baseline` が「はじめに」章のディレクトリと `static/img/getting-started/` 以外を含んだら失敗（章の外を触らない）
- `node gauntlet/check-steps.mjs` — 章のコードブロックのうち実行可能と印をつけたコマンドを、クリーンな環境で上から順に実行し、全て終了コード0なら成功（書かれた手順が本当に動くこと）
- `node gauntlet/check-length.mjs` — 章の総文字数が段0の1.5倍以下（分かりやすくするために長くなりすぎるのを防ぐ）

`gauntlet/` 以下の検査スクリプトは1周目の前に作り、段0に対して二度走らせて同じ結果になることを確かめてから使う。

## 5. 停止条件

| 条件 | 値 |
|---|---|
| 予算 | 壁時計 8時間（到達したら終了して報告） |
| 停滞 | 梯子の位置が 3 周動かず、読者タスクの誤答・詰まりも減らない → 人間へ |
| 勝利 | 新しい批評役 3 体が全員、順番を入れ替えても最上段（段3）に勝つと判定し、床が緑 |
| その他 | 原因を調べても同じ症状が残る、参照が取得できない・検査系が再現しない、批評の要求が床や目標と衝突する → 停止して報告 |

## 6. 実行プロンプト

「はじめに」章は一つの流れで前提を共有するので、分割せず一つの単位として一人の担当が逐次に磨く。並列の［任意］行は落とした。検査系（正規化とスクリーンショット）は比較の土台なので残した。

```text
社内技術ドキュメントサイト（Docusaurus）の「はじめに」チュートリアル章を、初めて読む社員が迷わず最初の成功まで届く水準、つまり Stripe Docs の入門チュートリアル並みに分かりやすくする。

バーは Stripe Docs の入門チュートリアル（https://docs.stripe.com/get-started から最初の成功体験までのページ群）。途中の段として 段0: 現行の「はじめに」章（git tag gauntlet-baseline）、段1: Docusaurus 公式チュートリアル（https://tutorial.docusaurus.io/docs/intro からの Tutorial - Basics）、段2: Supabase Docs の Next.js クイックスタート（https://supabase.com/docs/guides/getting-started/quickstarts/nextjs）を使う。開始時にすべてを refs/ に保存し、以後はそれを基準にする。参照は評価専用で、文章・構成・コード例を成果物に写さない。1周目の前に、隣り合う段を新しい批評役に伏せて比べさせ、順が想定どおりか確かめる。
比べ方: 読者タスク。各段と成果物を同じ書式のプレーンな Markdown に正規化し、製品名・社名・URL など出自の手がかりを伏せる。新しいエージェントに片方だけを読ませ、固定した設問（必要なもの／最初の一手／成功したら何が見えるか／失敗したらどうするか／次に何をするか／意味の分からなかった語の数）に答えさせ、refs/answers/ の正答と照合する。社内章については、新しいエージェントがクリーンな環境で章の手順だけを頼りに最初の成功まで進み、詰まった箇所と試行回数を記録する。これらを材料に伏せた一対比較をする。
床は npm run build、npm run lint、node gauntlet/check-scope.mjs（章の外を触っていない）、node gauntlet/check-steps.mjs（章のコマンドがクリーンな環境で全て通る）、node gauntlet/check-length.mjs（総文字数が段0の1.5倍以下）。床を通らない変更は評価に回さない。

進め方はあなたが決めてよい。守ることだけを書く。
- 作業を、独立に改善・判定できる単位に分ける。前提を共有する部分は一つの単位にし、一人の担当が順に磨く。並列にするのは結合の無い単位だけ。
- 各単位に作る役と、毎回新しい批評役を立てる。批評役には目標・バー・実物だけを渡し、作る役の説明は渡さない。
- 批評役は、どちらが自作か伏せたまま実物と梯子の段を比べ、勝敗と、差を分けた最大の症状を場所つきで一つ返す。直し方は言わない。
- 作る役は症状を計測で確かめてから、それだけを直す。計測が批評と食い違ったら計測に従う。同じ症状が二周続いたら、直すのをやめて原因を調べる。
- 1周目の前に検査系（Markdown への正規化、伏せ字化、デスクトップ1280px・モバイル390pxのスクリーンショット、gauntlet/ の検査スクリプト）を作り、同じ版を二度検査して一致することを確かめる。実物と参照は同じ条件で並べる。
- 波の終わりに、全体を新しい批評役に見せて部品間の食い違いを直し、全体と参照の全体を比べる。
- 勝ったと言えるのは、新しい批評役 3 体が全員、順番を入れ替えても最上段に勝つと判定したときだけ。
- 止めるのは、勝ったとき、予算 壁時計8時間 を使い切ったとき、梯子の位置が 3 周動かないとき、原因を調べても同じ症状が残るとき、参照が取得できないとき。止まったら理由と現状を報告する。
- 状態は gauntlet/ledger.yaml に置き、進み具合を gauntlet/index.html に示し続ける。
- サブエージェントを使う。/loop や高いeffort設定が使えるなら使う。
```

## 7. 実行前チェック

- 作業ディレクトリを git にコミットし、専用ブランチか worktree で回す（`git worktree add ../docs-gauntlet -b gauntlet/getting-started`）。可能ならコンテナで。`check-steps.mjs` のためのクリーンな実行環境もここで用意する
- 無関係な skill・MCP を切った、クリーンな Claude Code セッションで回す
- 予算を見張る。8時間・多数のサブエージェント・高 effort の組み合わせは個人のプラン上限を大きく食う。上限に近づいたら止まるよう、利用量を朝ではなく途中でも確認できるようにしておく
- `refs/` のスナップショットは評価専用。成果物に取り込まない。社内リポジトリに第三者のページを保存してよいかも確認し、だめなら `refs/` を `.gitignore` に入れる
- 社内ドキュメントの本文を外部のサービスや別系統のモデルに送ってよいか、社内規則を確認する（勝利判定で別系統の批評役を混ぜる場合に関係する）
- 章のディレクトリ（`docs/getting-started/` 等）の実際のパスを `check-scope.mjs` と実行プロンプトに合わせる
