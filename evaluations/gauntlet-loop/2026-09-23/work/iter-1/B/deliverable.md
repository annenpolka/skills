# 決済まわりのガントレット設計（composeモード）

「回して」とだけ伺っていて、このセッションで回すかどうかの指定はなかったので、既定の compose で進めます。ここでは設計と、クリーンなセッションに貼る実行プロンプトを用意します。このセッションでループは回していません。
なお、このセッションでは他の skill や MCP が多数有効です。ガントレットをここで回すと、それらにループが乗っ取られるおそれがあります（Matt Shumer 本人の経験則で、独立した検証はありません）。このセッションで回したい場合は、そのリスクを承知のうえでお知らせください。

## 1. 判定（Phase 0）

依頼は性質の違う二つに分かれるので、別々に判定します。

### 手数料計算（src/fees.ts）: ループは回さず、床に回す

| 問い | 答え |
|---|---|
| 1. 実物を検査できるか | はい（実行してテストできる） |
| 2. バー候補があるか | 考える必要なし |
| 3. 「良い」が機械検証だけで決まらないか | **いいえ**。求めているのは正しさで、正しさはテストで判定できる |
| 4. 予算を決められるか | はい |

問3が「いいえ」なので、ガントレットは回しません。手数料計算で必要なのは参照との見比べではなく、正しさを閉じるテストです。代わりにやること:

- 既存の Jest（`npm test`）に、境界値（0円、最小・最大金額、端数処理の境目）、丸め方向、通貨・税の組み合わせのケースを足す。テストと型で閉じる
- このテストを、下のメール文面ループの**床**として使う

### 決済完了メール（templates/receipt.mjml）: 回す

| 問い | 答え |
|---|---|
| 1. 実物を検査できるか | はい。MJML を HTML に描画し、固定ビューポートで撮影して読める |
| 2. バー候補があるか | はい（下の候補を参照） |
| 3. 「良い」が機械検証だけで決まらないか | はい。読みやすさや、次に何をすればよいかの伝わり方はテストで決まらない |
| 4. 予算を決められるか | はい。金額はあとで伺います |

四問とも「はい」なので回します。機械で決まる部分（金額の正しさ、描画できること）は床に、決まらない部分（伝わり方）はバーに回します。

### 床に入れる予定の機械ゲート（手数料側からの持ち込み）

- `npm test`（手数料計算の Jest）
- メール中の金額の突合: 固定した注文フィクスチャを数件用意し、それぞれ `src/fees.ts` で計算した結果と、`receipt.mjml` を描画した出力に載る小計・手数料・合計を照合する。1件でも一致しなければ非ゼロで終わるスクリプトにする（例: `node tools/check-receipt-amounts.mjs`）
- MJML がエラーなしで HTML にコンパイルできること（`mjml --validate strict`）

このゲートが赤い版は、比較でどれだけ勝っていても採用しません。

## 2. バー候補（最初の人間ゲート）

メール文面のバーはまだ決まっていません。skill の手順では、バーが決まるまで比べ方、床の確定、停止条件、実行プロンプトは書きません。先に次の候補から一つ選んでください。

どの候補も水準の目安として使うだけで、文面やデザインは写しません（ライセンスの面でも、成果物には取り込みません）。開始時に `refs/` へ保存し、以後は保存した版を基準にします。

| 案 | 実物と取得方法 | 一文の理由 | 懸念 |
|---|---|---|---|
| A | **Stripe の領収書メール**。テストモードで決済を作り、receipt email を実際に送って受信した .eml / HTML を保存する | 誰でも同じ手順で取得でき、決済完了メールとして同じ種類・同じ大きさで並べられる | 英語が既定なので、日本語の文面と比べると言語の違いで見分けがつく。正規化するか、日本語ロケールで取れるかの確認が必要 |
| B | **Shopify の既定の「注文確認」通知テンプレート**。ストア管理画面の通知プレビューから、同じ注文内容で描画して保存する | EC の注文確認として広く使われる標準の水準で、梯子の中段に向く | Shopify のストアアカウントが要る。お持ちでなければ取得できないので外す |
| C | **Amazon.co.jp の注文確定メール**（実際に受信したもの）。受信箱から .eml で書き出して保存する | 日本語で、同じ読者層に向けた実物。言語による見分けが起きない | 個人情報を伏せる加工が要る。1件だけでは取得方法を再現できないので、書き出した版を固定する |

こちらの推奨は、最上段を C（日本語、同種）、中段を A か B とする梯子「現行の receipt.mjml → B → A → C」です。梯子は1周目の前に較正し、新しい批評役が隣り合う段を想定どおりの順に並べられるか確かめます。

## ご確認いただきたいこと

1. バーの最上段と梯子: 推奨の「現行版 → B → A → C」でよいですか。取れない候補（例: Shopify のアカウントが無い）はありますか
2. 予算の上限: トークン・時間・周回のうち、どれでいくらまでにしますか
3. 実行の場所: 既定どおり、クリーンなセッションに貼る実行プロンプトをお渡しする形でよいですか。それともこのセッションで回しますか（他の skill が有効な点は上に書いたとおりです）

選んでいただければ、比べ方（読者タスク: 新しいエージェントに片方のメールだけを読ませ、「請求額はいくらか」「手数料はいくらか」「次に何をすればよいか（領収書の入手、問い合わせ先、返金の手順）」に答えさせ、正答数で比べる。あわせて伏せた一対比較）、床の確定、停止条件（予算、停滞の周回数の既定は3、勝利判定に立てる批評役の数の既定は3）、実行プロンプト、実行前チェックを続けて書きます。
