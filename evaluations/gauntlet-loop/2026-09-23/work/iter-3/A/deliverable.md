# ガントレット設計: 社内ドキュメント「はじめに」章

Stripe Docs は「サイト単位」の指定だったので、比べる相手はこちらで一ページに絞りました（下の「バー」）。開始前なら差し替えられます。

## 1. 判定: 回す

| 問い | 答え |
|---|---|
| 成果物を実物として検査できるか | はい。Markdown/MDX を読めるし、`npm run build` の出力 HTML も確かめられる。手順を実際に辿らせることもできる |
| 取得できるバーがあるか | はい。Stripe Docs は公開ページなので、取得して `refs/` に固定できる |
| 良さが機械検証だけでは決まらないか | はい。ビルドと lint が通っても「分かりやすさ」は決まらない。ビルドと lint は床にして、分かりやすさをバーで測る |
| 予算の上限を決められるか | はい。8時間 |

## 2. バー

**最上段**: Stripe Docs「Set up your development environment」（https://docs.stripe.com/get-started/development-environment ）。
Stripe の入門の入口で、前提 → インストール → 最初の成功 → 次の一手を一本道で見せます。題材に依存しない「入門の型」を比べるのに最も向いたページなので、これを選びました。

**梯子**（下 → 上。開始時に全段を取得して `refs/` に固定し、以後はそこだけを使う）

| 段 | 実物 | 取得方法 |
|---|---|---|
| 0 | 現行版の社内「はじめに」章（開始時のコミット） | `git show <開始コミット>:<章のパス>` を `refs/rung0/` に保存 |
| 1 | Docusaurus「Installation」 https://docusaurus.io/docs/installation | ページを取得し、本文を Markdown に整形して `refs/rung1/` に保存 |
| 2 | Next.js「Installation」 https://nextjs.org/docs/app/getting-started/installation | 同上 → `refs/rung2/` |
| 3（最上段） | Stripe「Set up your development environment」 | 同上 → `refs/rung3/` |

- 取得日と URL を `refs/SOURCES.md` に書く。参照は評価専用で、文言も構成も成果物に写さない
- **較正**（1周目の前）: 隣り合う段（0対1、1対2、2対3）を新しい批評役にブラインドで比べさせ、0 < 1 < 2 < 3 の順になるか確かめる。順が崩れた段は外すか入れ替える（段は3つ以上残す）。段 0〜3 の順が付けられないなら、この比べ方では判定できないとみなして止める

## 3. 比べ方: 読者タスク（主）＋伏せた一対比較（従）

題材が違う（社内サイトと決済 API）ので、「どちらが良いか」を直接聞くと好みで割れます。そこで比較を課題に置き換えます。

- **設問集**: 題材に依存しない型で固定する。
  1. 始める前に何が要るか
  2. 最初に打つコマンドか、最初の操作は何か
  3. 成功したら何が見えるか
  4. 途中で失敗したらどうするか
  5. 読み終えたら次に何をするか
  6. 全体で何分・何ステップかかるか
- **正答**: 各段と現行版について、開始時に正答を作り `refs/answers/` に固定する。現行版の正答は、元の章から読み取れる範囲で作る。章に書かれていない項目は「記載なし」を正答にする
- **読者**: 毎回新しいエージェントに、正規化した文書を片方だけ読ませて設問に答えさせる。採点は正答との一致数（0〜6）。もう片方も、別の新しいエージェントに読ませて同じ設問で採点する
- **正規化**: 両方をナビゲーション、ブランド名、ロゴ、スクリーンショットの装飾を落とした Markdown にそろえる。製品名は中立な記号（`<製品>` 等）に置き換え、見出しの深さと長さの枠をそろえる
- **一対比較**: 読者タスクのスコアと並べて、伏せた一対比較もする。批評役に「初めての人が迷わずに最初の成功まで辿り着けるのはどちらか」を問い、勝敗と差を分けた最大の症状を一つ、場所つきで返させる
- **検査系の検証**（1周目の前）: 同じ版の現行版に対して読者タスクを二度回し、正答数の差が各設問群で ±1 以内に収まることを確かめる。収まらなければ設問か正規化を直してから始める

## 4. 床（終了コードで判定）

| コマンド | 守るもの | 状態 |
|---|---|---|
| `npm run build` | サイトがビルドできる | 既存 |
| `npm run lint` | 既存の lint 規則 | 既存 |
| `node gauntlet/tools/check-scope.mjs` | 変更が「はじめに」章のファイルと `gauntlet/` だけに収まる（`git diff --name-only <開始コミット>` で判定） | **新規**。1周目の前に作り、現行版で二度走らせて同じ結果になることを確かめてから床にする |
| `node gauntlet/tools/check-links.mjs` | 章内のリンクと相対パスが切れていない（ビルド結果で判定。`onBrokenLinks: 'throw'` が既に設定済みなら不要） | **新規**。条件は上と同じ |

床が赤い変更は批評に回しません。一対比較でどれだけ勝っていても採用しません。

## 5. 停止条件

- 予算: 8時間（壁時計）。トークンの上限は、利用者のプラン残量から開始前に決める（未記入なら時間だけで止める）
- 停滞: 梯子の位置が3周動かず、読者タスクの正答数も増えないとき
- 勝利判定: 新しい批評役3体が全員、順番を入れ替えても最上段（段3）に勝つと判定し、かつ床が緑のとき
- ほかに止める条件: 同じ症状が原因調査の後も残るとき、参照が取得できないか検査系が再現しないとき、批評の要求が床や範囲と矛盾するとき

## 6. 実行プロンプト（別セッションの Claude Code に貼り付け）

```text
社内技術ドキュメントサイト（Docusaurus）の「はじめに」チュートリアル章を、初めての社員が迷わず最初の成功まで辿り着け、次に何をすればよいか分かる水準にする。編集してよいのはこの章のファイルと gauntlet/ だけ。

バーは Stripe Docs「Set up your development environment」（https://docs.stripe.com/get-started/development-environment）。途中の段として、段0: 開始時点の現行の「はじめに」章、段1: Docusaurus「Installation」（https://docusaurus.io/docs/installation）、段2: Next.js「Installation」（https://nextjs.org/docs/app/getting-started/installation）を使う。開始時にすべてを refs/ に保存し、以後はそれを基準にする。参照は評価専用で、文言や構成を写さない。1周目の前に、隣り合う段を新しい批評役にブラインドで比べさせ、段0<段1<段2<段3の順になるか確かめる。
比べ方: 読者タスクを主にする。題材に依存しない設問（前提、最初の一手、成功したら何が見えるか、失敗したらどうするか、次に何をするか、所要時間とステップ数）と各文書の正答を開始時に refs/answers/ に固定する。毎回新しいエージェントに、正規化した文書（ナビ・ブランド名・装飾を除き、製品名を中立な記号に置き換えた Markdown）を片方だけ読ませ、正答数で比べる。あわせて、伏せた一対比較で「初めての人が迷わず最初の成功まで辿り着けるのはどちらか」を問う。1周目の前に、現行版で読者タスクを二度回し、正答数が ±1 以内で一致することを確かめる。
床は npm run build、npm run lint、node gauntlet/tools/check-scope.mjs（変更範囲の確認）、node gauntlet/tools/check-links.mjs（リンク切れの確認）。後の二つは新規なので、1周目の前に作り、現行版で二度走らせて同じ結果になることを確かめてから床にする。床を通らない変更は評価に回さない。

進め方はあなたが決めてよい。守ることだけを書く。
- 作業を、独立に改善・判定できる単位に分ける。前提を共有する部分は一つの単位にし、一人の担当が順に磨く。並列にするのは結合の無い単位だけ。
- 各単位に作る役と、毎回新しい批評役を立てる。批評役には目標・バー・実物だけを渡し、作る役の説明は渡さない。
- 批評役は、どちらが自作か伏せたまま実物と梯子の段を比べ、勝敗と、差を分けた最大の症状を場所つきで一つ返す。直し方は言わない。
- 作る役は症状を計測で確かめてから、それだけを直す。計測が批評と食い違ったら計測に従う。同じ症状が二周続いたら、直すのをやめて原因を調べる。
- 波の終わりに、全体を新しい批評役に見せて部品間の食い違いを直し、全体と参照の全体を比べる。
- 勝ったと言えるのは、新しい批評役 3 体が全員、順番を入れ替えても最上段に勝つと判定したときだけ。
- 止めるのは、勝ったとき、予算 8時間 を使い切ったとき、梯子の位置が 3 周動かないとき、原因を調べても同じ症状が残るとき、参照が取得できないとき。止まったら理由と現状を報告する。
- 状態は gauntlet/ledger.yaml に置き、進み具合を gauntlet/index.html に示し続ける。
- サブエージェントを使う。/loop や高いeffort設定が使えるなら使う。
```

実行プロンプトから落とした任意行と、その理由:
- 「視覚・性能」の行は落としました。成果物は文章なので、撮影の再現性の代わりに、読者タスクを二度回す検証を「比べ方」に入れています。
- 「並列」の行も落としました。入門章は流れ全体が一つの前提を共有するので、一人の担当が順に磨きます。

## 7. 実行前チェック

- 作業ブランチを切ってコミットしてから始める（例: `git switch -c gauntlet/getting-started`）。可能なら `git worktree` かコンテナで回す。push や main への merge は、ラン後に人が確認してから行う
- 無関係な skill と MCP を切った、クリーンなセッションで回す
- 予算を見張る。8時間・多数のサブエージェント・高effort の組み合わせは、個人のプラン上限を大きく食う。開始前にトークンの上限を決めて台帳の先頭に書く
- `refs/` のスナップショット（Stripe・Next.js・Docusaurus）は評価専用。成果物にもリポジトリの公開ブランチにも取り込まない（`refs/` を `.gitignore` に入れるか、作業ブランチだけに置く）
- 章の手順が社内システム（VPN、社内認証など）に依存する場合、夜間のエージェントは実走できない。そこは読者タスク（読解）で判定し、実走での確認は朝に人がやる
