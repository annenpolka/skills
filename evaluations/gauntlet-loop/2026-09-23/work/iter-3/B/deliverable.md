# 決済まわりのガントレット設計（compose）

「回して」とのことですが、run と compose のどちらかは指定がありませんでした。そこで既定の compose で進めます。**実行プロンプトと設計を書くところまでで、ループはまだ一周も回していません。**
compose にしたもう一つの理由は、このセッションで他の skill が多数有効になっていることです。そういうセッションではループが乗っ取られて結果が落ちる、という報告があります（Shumer の経験則で、独立した検証はありません）。このセッションで run したい場合は、下のゲートでそう指示してください。その場合は、他の skill が有効なまま始めることを承知のうえで進めます。

---

## 1. 判定（Phase 0）

二つの対象で判定が分かれます。

### 手数料計算（src/fees.ts）→ **回しません。床に回します**

| 問い | 答え |
|---|---|
| 1. 実物として検査できるか | はい（実行できる） |
| 2. バー候補があるか | 必要なし |
| 3. 「良い」が機械検証だけでは決まらないか | **いいえ**。手数料計算に求めるのは正しさで、正しさはテストが決めます |
| 4. 予算を決められるか | はい |

3が「いいえ」なので、ガントレットの対象外です。ブラインド比較で「どちらの手数料計算が良いか」を批評役に選ばせても、得られるのは感想だけで、正しさは保証されません。
代わりにやること:
- テストで閉じる: 端数処理（切り上げ／切り捨て／銀行丸め）、最低手数料・上限、0円・最大額、通貨ごとの小数桁、税込／税抜の順序、返金時の逆算。この境界ケースを Jest に足してください。性質ベースのテスト（例: 手数料 ≤ 金額、金額に対して単調）も有効です
- 足したテスト `npm test` は、下のメール文面ループの**床**として使います。ループ中にメール側の変更が fees.ts を壊したら、その変更は採用しません

### 決済完了メール（templates/receipt.mjml）→ **回します**

| 問い | 答え |
|---|---|
| 1. 実物として検査できるか | はい（MJML を HTML に描画して読める・撮れる） |
| 2. バー候補があるか | はい（実在する他社の決済完了メール。下記） |
| 3. 「良い」が機械検証だけでは決まらないか | はい。分かりやすさや、次の行動へのつながりはテストでは決まりません。一方、金額の正しさと描画エラーの有無は機械で決まるので、床に回します |
| 4. 予算を決められるか | はい（下のゲートで決めてください） |

## 2. バー（最上段の候補）→ ここで選んでください

バーの指定はまだありません。バーの六条件（名指し・取得可能・同種同尺・識別可能・固定・素材ではない）で候補を絞り、残ったのが次の3案です。

| 案 | 最上段の候補 | 取得方法 | 一文の理由 |
|---|---|---|---|
| A | **Stripe の決済完了レシートメール**（Stripe が自動送信する標準のもの） | テストモードで決済し、自分のテスト用アドレスにレシートを送って .eml と HTML で保存する | 同じ「決済完了」という用途で、金額の内訳・支払方法・問い合わせ先の示し方に定評があります。こちらで同じ条件を何度でも再現できます |
| B | **Shopify の標準「注文確認」通知メール** | 開発用ストアを作ってテスト注文を入れ、通知のプレビューまたは実際の受信を保存する | EC の注文確認として広く使われる基準です。商品行・送料・税の並べ方が同じ粒度で比べられます |
| C | **あなたが「これは良い」と思う実在の決済完了メール1通**（受信箱にあるもの） | 受信箱から .eml を書き出して `refs/` に置いてもらう | 自社の客層に近い好例を使えます。ただし再取得はできないので、渡してもらった1通を固定の基準にします |

どの案でも次の扱いは共通です。
- 開始時に `refs/` へスナップショットを取り、以後は変えません
- 参照は**水準の目安としてだけ使い、文言やレイアウトを写しません**。成果物には取り込みません（ライセンス上も同じです）。批評役には、写しに見えるかどうか（`imitation_suspected`）も毎回返させます
- 梯子の最下段は**現行の receipt.mjml** です。途中の段（2〜3段）は、選ばれたバーに合わせてこの後で固定し、1周目の前に較正します。隣り合う段を新しい批評役にブラインドで比べさせ、想定どおりの順になるかを確かめます

## 3. 比べ方（方針）

好みで比べると判定が割れやすい領域なので、**読者タスク**に変えます。
- 新しいエージェントに、描画したメールを**片方だけ**読ませ、同じ設問に答えさせます。正答数と、答えに迷った箇所で比べます
- 参照と成果物で注文の中身が違うので、設問は内容に依存しない型で固定します
  1. 最終的にいくら請求されたか（合計額）
  2. その内訳（商品代・手数料・送料・税）はそれぞれいくらか
  3. どの注文か（注文番号・日時）、何を買ったか
  4. どの支払方法で払ったか
  5. 次に何が起きるか（発送・ダウンロード等）、いつか
  6. 間違いや不審な請求に気づいたら、どこへ・どうするか
  7. 領収書や明細を後で取り出すにはどうするか
- 各メールの正答は開始時に作り、`refs/` に固定します。設問集は検査系の一部として、1周目の前に検証します
- あわせて、伏せた一対比較（どちらのメールでこの課題が解けるか）を行い、差を分けた最大の症状を一つ、場所つきで返させます。直し方は言わせません
- 正規化: 成果物と参照を同じ幅・同じクライアント相当の描画（例: 幅600pxの HTML スクリーンショットと、プレーンテキスト版）で出します。ロゴ・社名・配色の出自が分かる要素は中立の伏せ字に置き換えます。出自で見分けがつくと、批評役は品質ではなく「どちらが本物か」を当てにいくからです

細部（描画するクライアント、スクリーンショットの条件）は、バーが決まってから詰めます。

## 4. 床（機械ゲート）

| コマンド | 守るもの | 状態 |
|---|---|---|
| `npm test` | 手数料計算の正しさ（上で足す境界ケースを含む） | 既存 |
| MJML のコンパイルを strict 検証で実行（例: `npx mjml templates/receipt.mjml --config.validationLevel=strict -s`） | 描画エラー・不正なタグが無いこと | 既存の道具。コマンドはプロジェクトの構成に合わせて確定させる |
| **金額突合スクリプト（新規）**: 固定の注文フィクスチャ（通常、手数料の端数が出るもの、0円手数料、高額、複数通貨）で fees.ts の結果を計算する。receipt.mjml をそのデータで描画し、メール中に出る合計・手数料・内訳の金額が計算結果と文字列レベルで一致することを検査して、不一致なら非ゼロで終了する | 文面の改善で金額表示が壊れない／ずれないこと | **新規**。1周目の前に作り、現行版に二度走らせて同じ結果になることを確かめてから床にする |
| 描画後 HTML のサイズ上限（例: 100KB 未満。Gmail の切り詰め対策）と、必須リンク（問い合わせ先・注文詳細）が存在することの検査 | 天井を押したときに削れやすい軸 | 新規（任意）。同じく二度走らせて確認してから床にする |

床が赤い変更は、批評に回しません。比較でどれだけ勝っていても採用しません。

## 5. 停止条件（既定値の案。台帳の先頭に書く）

| 条件 | 値（案） |
|---|---|
| 予算 | **ゲートで決めてください**（案: 3時間 / 20M トークン / 15周 のうち先に来たもの） |
| 停滞 | 梯子の位置が **3周** 動かず、読者タスクの誤答も減らなければ人間へ |
| 勝利判定 | 新しい批評役 **3体** が全員一致し、順番を入れ替えても最上段に勝ち、かつ床が緑。可能なら別系統のモデルを1体混ぜる |
| 再発 | 同じ症状が二周続いたら原因調査の周に切り替える。調査の後も残れば人間へ |
| 根拠の欠落 | 参照が取得できない、検査系が再現しない → 停止 |
| 衝突・価値判断 | 批評の要求が床（金額の正しさ）やブランド規定と矛盾する、法的表記の判断が要る → 人間へ |

## ここで止めます: 人間ゲート（まとめて答えてください）

1. **バー**: A（Stripe）／B（Shopify）／C（手持ちの1通。その場合は .eml を渡してください）のどれにしますか
2. **予算の上限**: 時間・トークン・周回のどれで、いくつにしますか
3. **実行の場所**: 既定は compose です（実行プロンプトを受け取り、他の skill・MCP を切ったクリーンなセッションで Claude Code に貼って回す）。このセッションで run する場合は、他の skill が有効なままであることを承知のうえで指示してください
4. **描画用のデータ**: receipt.mjml の変数（注文番号・金額など）を埋めるフィクスチャや、描画の仕組み（テンプレートエンジン、送信処理）はリポジトリのどこにありますか。無ければ新規に作ります
5. **fees.ts のテスト追加**: 上に挙げた境界ケースのテスト追加を、ループとは別の作業として先にやってよいですか

選んでもらったら、次を書いて渡します。
- 梯子の途中の段とその取得手順
- 比べ方の細部（描画条件・伏せ字の規則・設問の正答）
- 貼り付け用の実行プロンプト（単位はメール文面全体を一つ、逐次で磨く。並列の［任意］行は落とす。描画の再現性の行は残す）
- 実行前チェック（git へのコミットか worktree、クリーンなセッション、予算の見張り、`refs/` は評価専用で成果物に取り込まない）
