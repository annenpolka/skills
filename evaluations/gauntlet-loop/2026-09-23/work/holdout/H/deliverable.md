# commit-msg skill のガントレット設計（compose）

実行は別セッションで行う前提なので、composeモードで設計を出します。バーは「skill・プロンプト」の型（素のモデル → 現行版）で決まるため、最初の人間ゲートは置かずに進めます。最上段の参照リポジトリは私の判断で選びました。開始前なら差し替えられます。

## 1. 判定（Phase 0）

| 問い | 答え |
|---|---|
| 1. 成果物を実物として検査できるか | はい。同じdiffをCodexに渡し、生成されたメッセージを読んで比べられる |
| 2. 取得できるバーがあるか | はい。素のCodexの出力はその場で作れる。人間が書いた実際のコミットメッセージは公開リポジトリから取れる |
| 3. 良さが機械検証だけでは決まらないか | はい。形式（Conventional Commitsへの準拠）はcommitlintで決まるので床に回す。diffを正しく要約しているか、typeやscopeの選び方が適切か、本文が役に立つかは機械では決まらないのでバーに回す |
| 4. 予算の上限を決められるか | はい。2時間 |

→ **回す。** 結論は三つのどれかになります: 「skillを残す」「直したうえで残す」「廃止を提案する」。

## 2. バーと梯子

**最上段**: `conventional-changelog/commitlint` リポジトリで人間が書いた元のコミットメッセージ。Conventional Commitsをcommitlintで強制しているプロジェクトなので、「同じdiffに人間の保守者がつけた、形式どおりのメッセージ」の実例になります（未確認。取得できなければ、Conventional Commitsを強制している別のOSSか、あなた自身のリポジトリに差し替えてください）。

| 段 | 中身 | 取得（生成）方法 | 固定先 |
|---|---|---|---|
| 0 | 素のモデル（無指示） | skillなしの `codex exec` に「このdiffのコミットメッセージを書いて」とdiffだけを渡す | `refs/rung0/<task-id>.txt` |
| 1 | 素のモデル（一行指示） | skillなしの `codex exec` に「このdiffのコミットメッセージを Conventional Commits 形式で書いて」と渡す。skillが最低限勝たなければならない、いちばん安い代替 | `refs/rung1/<task-id>.txt` |
| 2（最上段） | 人間の元メッセージ | 各タスクの元コミットの `git log -1 --format=%B <sha>` | `refs/rung2/<task-id>.txt` |

- 評価対象は `skills/commit-msg/SKILL.md`（未確認のパス）。開始時点の版を v0 として `refs/skill-v0/SKILL.md` にコピーし、v0 の出力も `refs/v0/<task-id>.txt` に固定する
- 段0と段1は、評価する版と同じモデル、同じreasoning effort、同じ指示文（skillの有無だけが違う）で生成する。モデル名とeffortは `gauntlet/ledger.yaml` の先頭に書く
- 段の出力は開始時に一度だけ生成して固定し、以後は作り直さない

### タスク集（開始前に固定し、改善用と判定用に分ける）

1. commitlintリポジトリから、次の条件でコミットを40件選ぶ: マージコミットでない／bot（renovate・dependabot）の作者でない／diffが400行以下／typeが偏らない（feat・fix・docs・refactor・chore・test・ci を含む。`!` や `BREAKING CHANGE` を含むものを最低2件入れる）
2. SHA一覧を `refs/tasks.json` に保存し、各タスクのdiffは `git show --format= <sha>` で `refs/diffs/<task-id>.diff` に保存する
3. 固定した乱数の種（`seed: 20260923`）で分ける:
   - **dev（16件）**: 作る役と、毎周の批評役が使う。症状はここから取る
   - **holdout（24件）**: `refs/holdout/` に置き、作る役には渡さない。梯子の位置、廃止の判定、勝利の判定にだけ使う
4. **改善に使ったタスクで勝敗を判定しない。** 勝敗、梯子の位置、廃止の判定はすべてholdoutの結果で決める。devでの勝ち負けは症状を探すためにだけ使う

### 較正（1周目の前、devで行う）

新しい批評役（別プロセスの `codex exec`）に、段0対段1と段1対段2を、伏せたまま順番を入れ替えて二度ずつ比べさせる。段0 < 段1 < 段2 の順にならなければ、その段を外すか設問を見直す。人間の元メッセージ（段2）が素のモデルに勝てないと出たら、この批評役ではこの領域を判定できないので Phase 0 に戻り、あなたに返す。

## 3. 比べ方

好みが割れやすい領域なので、主な判定は課題にし、伏せた一対比較は補助にします。

- **主: 識別タスク（holdout）**: 新しいエージェントに、メッセージ1本と候補のdiff4本（正解1本と、同じリポジトリから開始時に固定したダミー3本。`refs/distractors.json`）を渡し、どのdiffのメッセージか当てさせる。あわせて「破壊的変更を含むか」をはい／いいえで答えさせ、diffから開始時に作った正答（`refs/answers.json`）と照合する。スコアは正答数
- **補助: 伏せた一対比較（holdout）**: diffと2本のメッセージ（X/Yはランダム）を見せ、「このdiffのメッセージとして `git log` に残したいのはどちらか」を判定させる。各対を順番を入れ替えて二度判定し、両方で勝ったときだけ勝ちとする。片方だけなら引き分け
- **正規化**: 全出力（人間の元メッセージを含む）から、`(#1234)` のようなPR・issue参照、`Signed-off-by:` などのトレーラ、作者名を落とす。コードフェンスや前置き（「以下がコミットメッセージです」など）を剥がし、本文を72桁で折り返す。整形は `scripts/normalize.py`（新規）で行い、同じ入力を二度通すと同じバイト列になることを確かめる
- **「段に勝った」の定義（holdout）**: 識別タスクの正答数が段以上、かつ一対比較で「勝ち数 > 負け数」、かつ決着した対の勝率が60%以上

### 判定規則（残す／直す／捨てる）

- **最初（1周目の前）**: v0 を段1とholdoutで比べる。ここで既に負けていても即座に捨てず、予算の範囲で直してみる
- **終了時**: 最良版が **段1（素のモデル＋一行指示）に勝てなければ、skillの廃止を提案する。** 段1にだけ勝ち、段0に負ける版は論外として扱う。段1に勝てば残す。段2にも勝てばそのまま完成とする
- 廃止の提案には、holdoutでの正答数、一対比較の勝敗、残った最大の症状を添える

## 4. 床（終了コードで判定）

`gauntlet/` 直下で次を実行し、すべて終了コード0なら床は緑。

```sh
npm ci                                                   # @commitlint/cli と @commitlint/config-conventional を固定バージョンで入れる
python3 scripts/check_skill.py skills/commit-msg/SKILL.md  # 新規: frontmatterのname/descriptionの有無、nameとディレクトリ名の一致、YAMLとして読めるか
bash scripts/floor_commitlint.sh out/<version>/            # 新規: 正規化した全出力を1件ずつ npx commitlint --extends @commitlint/config-conventional に通し、1件でも落ちれば非0
bash scripts/check_holdout_sealed.sh                       # 新規: SKILL.md と作る役の作業ツリーに、holdoutのSHA・元メッセージの件名・diffの特徴行が一つも含まれないことをgrepで確かめ、含まれれば非0
```

- 新規の三つは1周目の前に作り、v0 に二度走らせて同じ結果になることを確かめてから床にする
- 段0と段1の出力もcommitlintに通して通過率を台帳に記録する（床ではなく参考情報。素のモデルが形式で落ちること自体がskillの存在理由になりうる）

## 5. 停止条件

| 条件 | 値 |
|---|---|
| 予算 | 2時間（実時間）。配分の目安: 準備・較正・v0の測定に40分、改善の周に60分、終了時の判定に20分。トークンの上限は置かず、実行前チェックで見張る |
| 停滞 | 梯子の位置（holdout）が **2周** 動かず、識別タスクの正答数も増えない → 人間へ（既定は3周だが、2時間では周回数が4〜5周にとどまるため縮めた） |
| 勝利判定の人数 | **3体**の新しい批評役が全員、順番を入れ替えても段2に勝つと判定したら終了 |
| 再発 | 原因調査の後も同じ症状が出る → 人間へ |
| 根拠の欠落 | commitlintリポジトリを取得できない、または再現性の検査に落ちる → 停止 |
| 予算切れで終わった場合 | その時点の最良版を上の判定規則にかけ、残すか廃止かを報告する |

## 6. 実行プロンプト（別セッションのCodexに貼る）

```text
skills/commit-msg/SKILL.md（Conventional Commits形式でコミットメッセージを書かせるskill）が、skill無しの素のモデルより良いかを確かめ、良くなければ直す。予算内で素のモデルに勝てなければ、廃止を提案して終える。

バーは conventional-changelog/commitlint リポジトリで人間が書いた元のコミットメッセージ。途中の段として、段0「skill無しのcodex exec＋『このdiffのコミットメッセージを書いて』」、段1「skill無しのcodex exec＋『このdiffのコミットメッセージをConventional Commits形式で書いて』」を使う。段0と段1は評価する版と同じモデル・同じeffortで生成する。開始時に、commitlintリポジトリから選んだ40件のコミット（マージ・bot除外、diff 400行以下、typeが偏らない、破壊的変更を2件以上含む）のSHAとdiff、各段の出力、現行のSKILL.md（v0）とその出力をすべて refs/ に保存し、以後はそれを基準にする。種20260923でdev 16件とholdout 24件に分ける。holdoutは作る役に渡さず、勝敗・梯子の位置・廃止の判定にだけ使う。改善に使ったdevのタスクで勝敗を決めない。
比べ方: 主はholdoutでの識別タスク。新しいエージェントにメッセージ1本と開始時に固定した候補diff4本を渡してどのdiffのものか当てさせ、破壊的変更の有無を答えさせ、正答数で比べる。補助はholdoutでの伏せた一対比較（diffと2本のメッセージを見せ、git logに残したいほうを選ばせる）。全出力からPR番号・トレーラ・作者名・前置きを落とし、72桁で折り返してから渡す。段に勝ったと言えるのは、識別タスクの正答数が段以上で、一対比較の勝ちが負けより多く、決着した対の勝率が60%以上のとき。終了時に最良版が段1に勝てなければ廃止を提案する。
床は `npm ci`、`python3 scripts/check_skill.py skills/commit-msg/SKILL.md`、`bash scripts/floor_commitlint.sh out/<version>/`、`bash scripts/check_holdout_sealed.sh` がすべて終了コード0。床を通らない変更は評価に回さない。

進め方はあなたが決めてよい。守ることだけを書く。
- SKILL.md は前提を共有する一つの単位として扱い、一人の担当が順に磨く。
- 各周に作る役と、毎回新しい批評役を立てる。批評役には目標・バー・実物だけを渡し、作る役の説明は渡さない。
- 批評役は、どちらが自作か伏せたまま実物と梯子の段を比べ、勝敗と、差を分けた最大の症状を場所（devのタスクID）つきで一つ返す。直し方は言わない。
- 作る役は症状を計測で確かめてから、それだけを直す。計測が批評と食い違ったら計測に従う。同じ症状が二周続いたら、直すのをやめて原因を調べる。
- 1周目の前に検査系を作り、同じ版を二度検査して一致することを確かめる（整形は完全一致、批評の判定は80%以上一致、v0の段1への勝率の差は15ポイント以内）。実物と参照は同じ条件で並べる。あわせて、devで段0<段1<段2の順になることを伏せた比較で確かめる。
- 波の終わりに、最良版とすべての段をholdoutで比べる。
- 勝ったと言えるのは、新しい批評役3体が全員、順番を入れ替えても段2に勝つと判定したときだけ。
- 止めるのは、勝ったとき、予算2時間を使い切ったとき、梯子の位置が2周動かないとき、原因を調べても同じ症状が残るとき、参照が取得できないとき。止まったら理由、梯子の位置の推移、残る最大の症状、残すか廃止かの判定を報告する。
- 状態は gauntlet/ledger.yaml に置き、進み具合を gauntlet/index.html に示し続ける。
- 作る役・批評役・生成は、それぞれ別プロセスの codex exec で立てる。
```

使わなかった［任意］行: 「並列」の行は落としました（SKILL.md 一枚で、全体が結合しているため）。Claude Code 用の行も落としました（Codexで回すため）。検査が揺れうる行は、生成と判定が毎回ぶれるので、札を外して残しています。

## 7. 実行前チェック

- 作業ディレクトリ（skillのリポジトリと `gauntlet/`）をgitにコミットしてから始める。可能なら worktree かサンドボックスで回す
- 無関係なskill・MCPを切った、クリーンなCodexセッションで回す。特に段0と段1の生成では、`skills/commit-msg` がCodexから読まれない状態になっていることを確かめる（skillが自動で読み込まれると素のモデルにならない）
- `skills/commit-msg/SKILL.md` のパスは未確認。実在を確かめる
- `conventional-changelog/commitlint` の取得（clone）と、条件を満たすコミットが40件あることは未確認。開始前に確かめ、足りなければ別のConventional Commits強制リポジトリに差し替える（差し替えは開始前だけ）
- skillを使う版と使わない版で、モデル・effort・指示文をどう固定するか（`codex exec` の設定、skillの読み込ませ方）は未確認。1本試して、違いがskillの有無だけになっていることを確かめる
- 系統の偏り: 批評役も生成もCodexなので、同じ系統の盲点を共有する。`claude -p` など別系統のCLIが使えるなら、最終の勝利判定と廃止判定の批評役に1体混ぜる。使えなければ、その限界を報告に書く
- 予算を見張る。40件×複数の段×二度判定は呼び出し回数が多い。準備に40分を超えたら、holdoutを減らさずに改善の周の数を削る
- 参照（人間の元メッセージ）は評価専用。文面をskillの例として写さない（`check_holdout_sealed.sh` はholdoutしか見ないため、devの元メッセージの丸写しも作る役に禁じる）
