ガントレットで回す前に、目標にするサイト（バー）を一つ選んでもらう必要があります。どのサイトを選ぶかで、比べ方の細部、段の構成、実行プロンプトの中身がすべて変わります。なので今回出すのは、選ぶ前に決められる部分までです。

## 1. 回すかどうか

| 問い | 答え |
|---|---|
| 成果物を実物として検査できるか | はい。Next.js をビルドして起動し、固定したビューポートで撮影して読めます |
| 取得できるバーの候補があるか | はい。タスク管理アプリの公開ランディングページは誰でも開けます（候補は下に挙げます） |
| 「良い」が機械検証だけでは決まらないか | はい。伝わりやすさや説得力はテストでは決まりません。ビルド、リンタ、アクセシビリティ、表示速度のように機械で決まる部分は「床」として別に守ります |
| 予算の上限を決められるか | はい。値は下の質問でうかがいます |

→ **回します。**

## 2. バー（最上段）の候補（ここで選んでください）

名指しでき、批評役が実際に開けるタスク管理アプリのランディングページから選びました。

| 案 | 最上段にするページ | 選んだ理由（一文） |
|---|---|---|
| **A** | Todoist のトップページ（https://todoist.com/） | 個人向けタスク管理という同じカテゴリで、「何ができて、なぜ自分に要るのか」を一画面目で伝えることに長く磨きをかけてきたページだからです。 |
| **B** | Things 3 の製品ページ（https://culturedcode.com/things/） | 小さなチームが作る個人向けタスク管理アプリで、機能を並べるのではなく、使い心地そのものを見せて売っているページです。個人開発の規模感に最も近いと考えます。 |
| **C** | Sunsama のトップページ（https://www.sunsama.com/） | 「一日の計画」という一つの考え方を軸に、個人向けの有料ツールを売っているページです。独自の使い方を持つアプリなら、見せ方の手本になります。 |

アプリの立ち位置でおおよそ決まります。機能の幅で勝負するなら A、使い心地やデザインで勝負するなら B、独自の方法論で勝負するなら C が向いています。なお、ここで選ぶのは段の一番上だけです。途中の段は選ばれたバーに合わせて、あとから3〜5段で組みます。

**候補から外したもの**

- Linear（linear.app）: 評価は高いものの、チーム向けの開発管理ツールです。読み手も訴えどころも違うので、同じ尺度で並べられません。
- Notion、Asana: 扱う範囲が広すぎるか、法人向けの色が濃すぎます。ページの分量も構成も個人開発のランディングページとかけ離れていて、どこに差があるのかを言葉にしにくくなります。
- 「おしゃれなSaaSのランディングページ」のようなカテゴリ全体: どれか一つに特定できないので、批評が一般論になります。

**どの案を選んでも守ること**

- 開始時に参照ページを `refs/` へスナップショットし、実行中はそれだけを基準にします（ページが途中で更新されても比べる相手が変わらないようにするため）。
- 参照は、どの水準を目指すかの目安として使うだけです。文言、画像、構成をそのまま写すことはしません（模倣で勝っても意味がなく、ライセンス上も成果物に取り込めません）。

## 3. 比べ方（方針）

Web/UI の型を使います。

- デスクトップとモバイルの固定したビューポートで、あなたのページと参照ページを同じ条件（解像度、切り抜き、スクロール位置、情報量）で撮影します。
- 見た目の好みを比べると判定が割れやすいので、**課題で比べることを主な判定にします**。新しいエージェントにどちらか一方のページだけを見せ、どのページでも使える同じ設問に答えさせて、正答の数で比べます。
  - これは何の製品か／誰のためのものか／他と何が違うか／最初に何をすればよいか（どのボタンを押すか）／料金や始めるときの負担は分かるか
- 製品名やロゴなど、どちらのページか分かってしまう固有名は、中立の記号に置き換えます。それでも題材でどちらか分かるときのために、伏せた一対の比較は補助として使うにとどめます。
- 各ページの正答と撮影の細かな条件は、バーが決まってから作ります。

## 4. 床（見込み）

コマンドの終了コードで合否が決まるものだけを床にします。実際にリポジトリにあるかは、バーが決まってから確かめます。

- `next build`（ビルドが通ること）
- リンタ（`next lint` または ESLint）、型検査（`tsc --noEmit`）
- 既存のテストがあればそれも含めます
- **新規**: アクセシビリティの自動検査（Playwright と axe で、ランディングページの違反が0件）
- **新規**: 表示性能の予算（Lighthouse CI で、モバイルの LCP、CLS、JS の転送量に上限を設ける）

新規の検査は1周目の前に作り、今のページに二度かけて同じ結果になることを確かめてから床に加えます。

## 5. 停止条件（既定値と予算の案）

- 停滞: 梯子の位置が **3周** 動かなければ、あなたに判断を戻します
- 勝利判定: 新しい批評役 **3体** が全員、順番を入れ替えても最上段に勝つと判定したときだけ勝ちとします
- 予算の案: **4時間／20周まで**。個人のプランの上限を考えると、まずは小さく始めるのが無難です

## 選んでいただきたいこと（ここで止めます）

実行プロンプトと実行前チェックは、ここへの答えが揃ってから書きます。

1. **バー**: A（Todoist）／B（Things 3）／C（Sunsama）のどれにしますか？ どのページを使うかは上で決めてありますが、同じサイトの別のページがよければ指定してください。
2. **予算の上限**: 「4時間／20周」でよいですか？ 時間、周回数、トークンのどれで区切るかでも構いません。
3. **どこで回すか**:
   - **compose（おすすめ）**: 私が貼り付け用の実行プロンプトを書き、あなたが他のskillやMCPを切ったクリーンな Claude Code のセッションで回します。
   - **run**: このセッションで私がリードとして回します。ただし、このセッションでは他のskillやMCP（Gmail、Notion、Linear などのコネクタを含む）が有効なままです。ループがそちらに引っ張られて結果が落ちるおそれがあります。
4. **対象の所在**: リポジトリの場所、ランディングページのルート（例: `app/page.tsx`）、ローカルで起動するコマンド（例: `npm run dev`）を教えてください。
