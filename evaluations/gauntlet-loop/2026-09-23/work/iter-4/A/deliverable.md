# ガントレット設計: 社内ドキュメント『はじめに』章

実行は別のセッションで行うとのことなので、ここでは設計と貼り付け用の実行プロンプトを出します（composeモード）。

## 1. 判定

| 問い | 答え |
|---|---|
| 1. エージェントが成果物を実物として検査できるか | はい。リポジトリがあり、`npm run build` で生成したページを読めます。手順を実際にたどることもできます |
| 2. 取得できるバーがあるか | はい。Stripe Docs は公開ページで、批評役が実際に開けます |
| 3. 良さが機械検証だけで決まらないか | はい。「分かりやすさ」はビルドやリンタでは決まりません。ビルドとリンタは床に回します |
| 4. 予算の上限を決められるか | はい。上限は8時間です |

→ **回します。**

## 2. バー

**最上段: Stripe Docs「Set up your development environment」**（https://docs.stripe.com/get-started/development-environment）

選んだ理由: Stripe Docs の入門チュートリアルの中で、「環境を用意して最初の一手を成功させる」という『はじめに』章と同じ役割を持つページだからです。
「Stripe Docs の入門チュートリアル」は特定のページを指していないので、最も近いものを選びました。別のページ（例: Checkout のクイックスタート）にしたい場合は、開始前なら差し替えられます。

**梯子（下→上。1周目の前に較正する）**

| 段 | 実物 | 取得方法 |
|---|---|---|
| 0 | 現行の『はじめに』章（ループ開始時のコミット） | `git rev-parse HEAD` を控え、その版を `npm run build` で出力し、章のページを `refs/rung0/` に保存する |
| 1 | Docusaurus Tutorial「Tutorial Intro」から「Tutorial - Basics」までの章（https://tutorial.docusaurus.io/docs/intro） | 章のページをHTMLで取得し、本文を抜き出して `refs/rung1/` に保存する |
| 2 | Vite「Getting Started」（https://vite.dev/guide/） | 同上 → `refs/rung2/` |
| 3 | Next.js「Installation」（https://nextjs.org/docs/app/getting-started/installation） | 同上 → `refs/rung3/` |
| 4（最上段） | Stripe「Set up your development environment」 | 同上 → `refs/rung4/` |

- 取得日時とURLを `refs/MANIFEST.md` に記録し、以後は保存した版だけを基準にします。ループ中に参照先をもう一度取得することはしません
- 参照は水準の目安です。文や構成を成果物に写してはいけません
- 較正では、隣り合う段の組（0-1, 1-2, 2-3, 3-4）を新しい批評役にブラインドで比べさせます。順が崩れた段は入れ替えるか外します（外した後も3段以上残す）。開始後は梯子の中身を変えません

## 3. 比べ方

題材が違う（決済APIの入門と自社ドキュメントの入門）ので、好みで比べると判定が割れます。出自も題材から見分けられてしまいます。
そこで**読者タスクを主な判定**にし、伏せた一対比較は補助にとどめます。

- **読者タスク（主）**: 新しいエージェントに片方の文書だけを読ませ、内容に依存しない次の設問に答えさせます
  1. 始める前に必要なもの（前提・権限・ツール）は何か
  2. 最初に実行する一手は何か
  3. 成功したら何が見えるか
  4. 失敗したとき、どう確かめてどうするか
  5. この章を終えたら次に何をするか
  6. この章を終えるまでの所要時間の見込み
- 各文書（全段と成果物）の正答は開始時に作り、`refs/answers/` に固定します。成果物の正答はリポジトリの実際（コマンド、パス、出力）から作ります
- 採点: 正答数と、答えるまでに本文へ戻った回数。段の比較は、この結果で勝敗を決めます
- **正規化**: すべての文書を同じ変換器でプレーンなMarkdownに落とします。ナビゲーション、サイドバー、フッターは除き、画像は代替テキストに置き換えます。製品名・社名・URLは中立の記号（`PRODUCT_A` 等）に置き換えます
- **伏せた一対比較（補助）**: 正規化した二文書を、X/Y のランダムなラベルで比べさせます。返すのは勝敗と、差を分けた最大の症状（場所つき）を一つだけです
- 読者タスクは結果が揺れます。1周目の前に、同じ版を二度検査して正答数が一致するか（許容差 ±1問）を確かめます

## 4. 床

| コマンド | 状態 |
|---|---|
| `npm run build` | 既存 |
| `npm run lint` | 既存 |
| `node gauntlet/checks/scope.mjs` — 変更が『はじめに』章のディレクトリ（と、その章が使う画像）の中に収まっているかを `git diff --name-only <開始コミット>` で確かめる | **新規** |
| `node gauntlet/checks/commands.mjs` — 章に書かれたコマンド・ファイルパス・npmスクリプト名が、リポジトリに実在するかを突合する | **新規** |

- 新規の2本は1周目の前に作ります。現行版に二度走らせて同じ結果になることを確かめてから床に入れます
- 壊れたリンクは、`docusaurus.config` の `onBrokenLinks` が `throw` になっていれば `npm run build` で落ちます。設定を確かめて、`throw` でなければリンク検査を新規の床に足します（設定そのものは変えません）

## 5. 停止条件

| 条件 | 値 |
|---|---|
| 予算 | 8時間（実時間）。トークンの上限はプランに合わせて利用者が決める |
| 停滞 | 梯子の位置が3周動かない |
| 勝利判定 | 新しい批評役3体が全員、順番を入れ替えても最上段に勝つと判定したとき。可能なら1体は別系統のモデル（例: `codex exec`）にする |
| そのほか | 原因を調べても同じ症状が残る、参照が取得できない、検査が再現しない、批評の要求が床や社内の決まりと衝突する → 止めて報告する |

## 6. 実行プロンプト

新しいセッションに、そのまま貼ってください。

```text
社内技術ドキュメントサイト（Docusaurus）の『はじめに』チュートリアル章を、初めての読者が迷わず最初の一手を成功させ、次に進める水準にする。

バーは Stripe「Set up your development environment」（https://docs.stripe.com/get-started/development-environment）。途中の段として、現行の『はじめに』章（開始コミット）、Docusaurus Tutorial の Intro〜Basics（https://tutorial.docusaurus.io/docs/intro）、Vite「Getting Started」（https://vite.dev/guide/）、Next.js「Installation」（https://nextjs.org/docs/app/getting-started/installation）を使う。開始時にすべてを refs/ に保存し、以後はそれを基準にする。1周目の前に、隣り合う段を新しい批評役にブラインドで比べさせて順を確かめ、崩れた段は入れ替えるか外す。参照の文や構成は成果物に写さない。
比べ方: 読者タスクで比べる。新しいエージェントに正規化した文書を一つだけ読ませ、「前提は何か／最初の一手は何か／成功したら何が見えるか／失敗したらどうするか／次に何をするか／所要時間の見込み」に答えさせる。正答数と、本文に戻った回数で比べる。各文書の正答は開始時に作って refs/answers/ に固定する。正規化では、全文書を同じ変換でプレーンなMarkdownにし、ナビゲーションを除き、製品名・社名・URLを中立の記号に置き換える。伏せた一対比較は補助として使う。
床は npm run build、npm run lint、新規の node gauntlet/checks/scope.mjs（変更が『はじめに』章の中に収まるか）、新規の node gauntlet/checks/commands.mjs（章に書かれたコマンド・パス・スクリプト名がリポジトリに実在するか）。新規の検査は1周目の前に作り、現行版に二度走らせて一致を確かめてから床にする。床を通らない変更は評価に回さない。

進め方はあなたが決めてよい。守ることだけを書く。
- 作業を、独立に改善・判定できる単位に分ける。前提を共有する部分は一つの単位にし、一人の担当が順に磨く。並列にするのは結合の無い単位だけ。
- 各単位に作る役と、毎回新しい批評役を立てる。批評役には目標・バー・実物だけを渡し、作る役の説明は渡さない。
- 批評役は、どちらが自作か伏せたまま実物と梯子の段を比べ、勝敗と、差を分けた最大の症状を場所つきで一つ返す。直し方は言わない。
- 作る役は症状を計測で確かめてから、それだけを直す。計測が批評と食い違ったら計測に従う。同じ症状が二周続いたら、直すのをやめて原因を調べる。
- 1周目の前に検査系を作り、同じ版を二度検査して一致することを確かめる（読者タスクの正答数は ±1問まで）。実物と参照は同じ条件で並べる。
- 波の終わりに、全体を新しい批評役に見せて部品間の食い違いを直し、全体と参照の全体を比べる。
- 勝ったと言えるのは、新しい批評役 3 体が全員、順番を入れ替えても最上段に勝つと判定したときだけ。可能なら1体は別系統のモデルにする。
- 止めるのは、勝ったとき、予算 8時間 を使い切ったとき、梯子の位置が 3 周動かないとき、原因を調べても同じ症状が残るとき、参照が取得できないとき。止まったら理由と現状を報告する。
- 状態は gauntlet/ledger.yaml に置き、進み具合を gauntlet/index.html に示し続ける。
- サブエージェントを使う。/loop や高いeffort設定が使えるなら使う。
```

- 『はじめに』章は流れと前提がつながった一つの文章なので、一つの単位として一人の担当が順に磨く想定です。このため並列の［任意］行は落としました
- 読者タスクは結果が揺れるので、検査系の行は残しました

## 7. 実行前チェック

- [ ] 作業ツリーをgitにコミットし、ループ用のブランチか `git worktree` を切る。main で直接回さない
- [ ] 無関係なskillやMCPを切った、クリーンなセッションで回す
- [ ] 予算を見張る。8時間の放置で、多数のサブエージェントと高effortを組み合わせると、個人のプラン上限を大きく食います。最初の1〜2周で1周あたりの消費を見て、8時間分が収まるかを確かめてください
- [ ] 批評役が Stripe、Docusaurus、Vite、Next.js の各ページを実際に取得できることを先に確かめる（ネットワーク制限のある社内環境では特に）。取得できない段は外すか、手元で保存したものを `refs/` に置く
- [ ] 参照のスナップショットは評価にだけ使い、サイトのリポジトリにコミットしない（`refs/` を `.gitignore` に入れる）。社内サイトで公開されないようにする
- [ ] 章に社内の固有情報（内部URL、権限申請の手順）がある場合、ループが勝手に書き換えたり削ったりしないよう、残すべき事項を開始前に `refs/answers/` の成果物の正答に入れておく
