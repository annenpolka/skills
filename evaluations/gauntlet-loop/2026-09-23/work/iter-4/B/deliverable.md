# ガントレット・ループの設計（決済まわり）

「回して」とありましたが、このセッションで回すのか、別のセッションで回すための設計を渡すのかの指定はありませんでした。そこで既定の compose モードで設計を出します。このセッションでは他の skill や MCP がたくさん有効になっていて、その状態で長いループを回すと乗っ取られて品質が落ちるという報告があります。まだ何も実行していません。下の最後にある質問への答えをもらってから、実行プロンプトと実行前チェックを書きます。

---

## 1. 判定（対象ごと）

### 手数料計算（src/fees.ts）：ループでは回さず、テストで閉じる

| 問い | 答え |
|---|---|
| 1. 実物として検査できるか | はい（実行して計算結果を見られる） |
| 2. 取得できるバーがあるか | 実質なし（他社の手数料ロジックは中身が見えず、同じ条件で比べられない） |
| 3. 良さが機械検証だけでは決まらないか | **いいえ。** 手数料計算に求めるのは正しさで、正しさはテストで決まる |
| 4. 予算を決められるか | はい |

問い3が「いいえ」なので回しません。手数料計算で比べるべきなのは「参照より良く見えるか」ではなく、「期待値と一致するか」です。代わりにやることを挙げます。

- 既存の Jest テスト（`npm test`）を**床**として、メール文面のループに組み込む
- テストで見落としがある場合（端数処理、最低手数料、ゼロ円や上限額、通貨ごとの桁数、税込みか税抜きか）は、ループとは別にテストを書き足して閉じる。何が正しいかは仕様やビジネス上の判断で決まるので、期待値は人間が決める

### 決済完了メール（templates/receipt.mjml）：回す

| 問い | 答え |
|---|---|
| 1. 実物として検査できるか | はい（MJML を HTML に描画し、固定したビューポートで撮影でき、本文も抽出できる） |
| 2. 取得できるバーがあるか | はい（実在する決済完了メールや領収メールを、自分で購入や決済を行って受信し、保存できる） |
| 3. 良さが機械検証だけでは決まらないか | はい（金額がひと目で分かるか、次に何をすればよいか分かるか、問い合わせ先がすぐ見つかるかは、テストでは決まらない） |
| 4. 予算を決められるか | はい（案は下の5を参照） |

機械で決まる部分（金額の正しさ、MJML として正しいか）は床に回し、機械では決まらない部分（読み手に伝わるか）をバーの対象にします。

## 2. バー：最上段の候補（どれにするか選んでください）

どの候補も、批評役が実物として開けるように、**実際に受信したメールを保存したもの**を使います。スクリーンショットの寄せ集めや記事での紹介文は使いません。

| 案 | 最上段 | 理由（一文） | 取得方法 |
|---|---|---|---|
| A | Stripe のテストモードで送られる決済領収メール（Stripe が自動で送る receipt） | 決済額、内訳、支払い方法、問い合わせ先を一画面にまとめる形として広く使われていて、自分の環境で何度でも取り直せる | Stripe のテストモードで決済を作り、自分のアドレスに receipt を送る。`.eml` と描画結果を保存する |
| B | Apple の購入領収メール（App Store や Apple のオンラインストアでの購入） | 小計、税、合計、支払い方法、注文番号、返金手続きの入口まで情報が揃っていて、分かりやすい領収メールとして定評がある | 実際に少額の購入をして受信したメールを保存する（費用がかかり、取り直しにくい） |
| C | Shopify の標準「注文確認」通知メール（テンプレートを変えていないもの） | EC の決済完了メールとして題材が最も近く、同種同尺で比べやすい | 開発用ストアでテスト注文を行い、受信したメールを保存する |

私のおすすめは **A** です。取得と再現が容易で、題材（決済が完了したことと、その内訳を伝える）も同じです。下の段には C を使えます。

**参照は素材ではない**：参照は、どの水準を目指すかの目安と比較のためだけに使います。文面、レイアウト、ロゴは成果物に取り込みません（真似で勝つことになり、ライセンス上の問題もある）。スナップショットは評価専用として `refs/` に置きます。

梯子の全段（下から、現行の receipt.mjml → …… → 最上段）と、それぞれの取得方法は、最上段を選んでもらってから確定します。最上段が決まったら、1周目の前に、隣り合う段どうしを新しい批評役に伏せたまま比べさせ、想定した順に並ぶかを確かめます（較正）。

## 3. 比べ方（方針）

「文章」の型を使い、比べ方を**読者タスク**に変えます。どちらのメールが好きかは判定が割れやすく、読み手が質問に答えられるかなら判定がぶれにくいからです。

- 新しいエージェントに、描画したメールを**片方だけ**見せる（デスクトップ幅とモバイル幅の画像と、抽出した本文）
- 内容に依存しない、固定の設問に答えさせる。
  1. 支払った合計金額はいくらか
  2. その内訳（商品代、手数料、送料、税）はそれぞれいくらか
  3. どの支払い方法で、いつ決済されたか
  4. 注文を特定する番号は何か
  5. 次に何が起きるか、次に自分が何をすればよいか（発送、ダウンロードなど）
  6. 内容が間違っていたとき、どこに連絡すればよいか、どう取り消せばよいか
- 設問ごとの正誤と、答えにたどり着くまでの手間（スクロールした量や見返した回数など）で比べる。補助として、伏せたままの一対比較も行う
- 正規化：成果物も参照も同じ架空の注文データで描画し、同じビューポートとファイル形式で出す。社名、ロゴ、URL などの固有名は中立の記号に置き換える。それでも出自が分かってしまう場合は、読者タスクだけで判定し、一対比較は補助にとどめる
- 各文書の正答は開始時に作って `refs/` に固定する。設問集は検査系の一部として、1周目の前に同じ版に二度かけて、結果が一致することを確かめる

## 4. 床（見込み）

| コマンド | 状態 |
|---|---|
| `npm test`（手数料計算の Jest テスト） | 既存 |
| MJML の厳密な検証とコンパイル（例：`npx mjml --config.validationLevel=strict templates/receipt.mjml`） | 所在の確認が必要。無ければ**新規** |
| **金額の突合**：用意した注文データごとにメールを描画して金額を抜き出し、`src/fees.ts` の計算結果（手数料と合計）と一致しなければ失敗させるスクリプト | **新規**。1周目の前に作り、現行版に二度かけて同じ結果になることを確かめてから床に入れる |
| メールサイズの予算（例：描画後の HTML が 102KB 未満。これを超えると Gmail で本文が切り詰められる） | **新規** |

床が赤い版は批評役に回さず、比較でどれだけ勝っていても採用しません。コマンドの最終的な一覧は、リポジトリで所在を確かめてからゲートの後に確定します。

## 5. 停止条件（既定値と予算の案）

- 予算：**案** 4時間、トークン 30M、20周まで（どれか一つに達したら止めて報告）
- 停滞：梯子の位置が **3周** 動かず、読者タスクの誤答も減らなければ、人間に戻す
- 勝利判定：新しい批評役 **3体** が全員、順番を入れ替えても最上段に勝つと判定し、かつ床が緑であること
- 原因を調べても同じ症状が残るとき、参照を取得できないとき、検査系が再現しないときも止める
