# ガントレット設計: 社内ドキュメント「はじめに」チュートリアル章

実行は別セッションで行うとのことなので、compose モードで設計しました。末尾の実行プロンプトを、クリーンな Claude Code セッションにそのまま貼り付けてください。

バーの候補は Stripe Docs の中から一つ選んで進めています（理由は 2 に書きました）。別のページにしたい場合は、開始前なら差し替えられます。

---

## 1. 判定（Phase 0）

| 問い | 答え | 根拠 |
|---|---|---|
| 1. エージェントが実物を検査できるか | はい | Markdown/MDX を読めるし、`npm run build` の出力も確かめられる。新しいエージェントに章だけを読ませて設問に答えさせる形で検査できる |
| 2. 取得できるバー候補があるか | はい | Stripe Docs の入門チュートリアルは公開ページで、設計時に取得できた（下記） |
| 3. 良さが機械検証だけでは決まらないか | はい | 「分かりやすさ」はテストでは決まらない。ビルドが通ること、lint、リンク切れのように機械で決まる部分は床に回す |
| 4. 予算の上限を決められるか | はい | 時間の軸として「一晩 8 時間」をいただいている。トークンの上限は実行前チェックで見張る |

→ **回す。**

## 2. バー

**最上段**: Stripe Docs「開発環境を設定する」の Node.js 版（https://docs.stripe.com/get-started/development-environment.md?lang=node）。「学習内容 → 手順ごとのコマンド → 成功したら表示される出力 → 次のステップ」を一本の流れで示しており、Stripe の入門チュートリアルの典型的な形なので選びました。

梯子（下から上へ。途中の段は私が選んだものなので、較正で並び順を確かめます）:

| 段 | 実物 | 取得方法 | 状態 |
|---|---|---|---|
| 0 | 自社の現行「はじめに」章（開始時点のコミット） | `git show <開始コミット>:<章のパス>` で取り出す。章のパスは `docs/getting-started/` と推定している | **未確認**（パスは推定） |
| 1 | Vite「Getting Started」 https://vite.dev/guide/ | ページを取得して Markdown にする | 設計時に取得を確認した |
| 2 | Docusaurus「Installation」 https://docusaurus.io/docs/installation | 同上 | 設計時に取得を確認した |
| 3（最上段） | Stripe「開発環境を設定する」Node.js 版（URL は上記） | `.md?lang=node` の URL を取得する | 設計時に取得を確認した |

開始時に、全段を取得日時つきで `refs/rung-0..3/` にスナップショットします。それ以降の比較はスナップショットだけを使います。参照は水準の目安として使うだけなので、文章や構成を章に写しません。

## 3. 比べ方

参照と成果物で題材が違う（決済 API の入門と自社ドキュメントの入門）ので、「どちらが良いか」の好みで比べるのはやめ、**読者タスク**を主な判定にします。

- **読者タスク（主判定）**: 新しいエージェントに文書を一つだけ読ませ、内容に依存しない次の型の設問に答えさせる
  1. 始める前に必要なもの（前提）は何か
  2. 最初に実行する一手は何か
  3. 成功したら何が見えるか
  4. 失敗したら何を確かめ、どうするか
  5. 終わったら次に何をするか
  6. 途中で出てくる用語・値のうち、読者が自分の値に置き換えるものはどれか

  各文書の正答は開始時に作り、`refs/answers/` に固定します。評価は、正答数と「文書に書かれておらず推測で答えた」設問の数で行います。
- **伏せた一対比較（補助）**: 正規化した文書を二つずつ並べ、ラベルを伏せて「入門者が詰まらずに最後まで進めるのはどちらか」を問う。題材から出自が分かってしまうので、これは補助にとどめ、勝敗は読者タスクで決めます。
- **正規化**: HTML/MDX は同じ書式のプレーンな Markdown に揃えます。Stripe・Vite・Docusaurus・社名・製品名・URL は中立の記号（「サービスA」「ツールB」等）に置き換えます。コードブロックは残し、画像は代替テキストに置き換えます。
- **同種同尺**: どの段も「単一の入門ページ」の粒度で揃えます。自社の章が複数ページにわたる場合は、章全体を一本に連結した版と比べます。

## 4. 床

| コマンド | 守るもの | 状態 |
|---|---|---|
| `npm run build` | サイトがビルドできる | 利用者から存在を聞いている。終了コードで失敗を返すことは**未確認** |
| `npm run lint` | lint 規約 | 同上 |
| `node gauntlet/check-links.mjs` | 章の中のリンク・アンカーが切れていない（`docusaurus.config` の `onBrokenLinks` が `throw` ならビルドで代替できる） | **新規** |
| `node gauntlet/check-scope.mjs` | 変更が「はじめに」章のディレクトリとその画像だけに収まっている（`git diff --name-only <開始コミット>` で判定） | **新規** |

新規の検査は 1 周目の前に作ります。現行版に二度走らせて、同じ結果（緑）になることを確かめてから床に入れます。

## 5. 停止条件

- 予算: **8 時間**（壁時計）。トークンの上限は定めず、実行前チェックで見張る
- 停滞: 梯子の位置が **3 周**動かず、推測で答えた設問の数も減らなければ、止めて人間に戻す
- 勝利判定: 新しい批評役 **3 体**が全員、順番を入れ替えても最上段に勝つと判定し、かつ床が緑
- 再発: 原因を調べた後も同じ症状が出たら、人間に戻す
- 根拠の欠落: 参照のスナップショットが読めない、または読者タスクが再現しない場合は止める
- 衝突・価値判断: 章の範囲外の変更や、社内の手順・権限そのものを変える必要が出たら、人間に戻す

## 6. 実行プロンプト

```text
社内向け Docusaurus サイトの「はじめに」チュートリアル章（docs/getting-started/ と推定。まず実在を確かめ、違えば正しいパスを台帳に書く）を、初めての読者が詰まらずに最後まで進められる水準まで改善する。

バーは Stripe Docs「開発環境を設定する」Node.js 版（https://docs.stripe.com/get-started/development-environment.md?lang=node）。途中の段として、段0: 開始時点の現行「はじめに」章、段1: Vite Getting Started（https://vite.dev/guide/）、段2: Docusaurus Installation（https://docusaurus.io/docs/installation）を使う。開始時にすべてを refs/ に保存し、以後はそれを基準にする。1周目の前に、隣り合う段同士を新しい批評役にブラインドで比べさせ、順が崩れる段は入れ替えるか外す。
比べ方: 読者タスクを主な判定にする。新しいエージェントに文書を一つだけ読ませ、「前提は何か／最初の一手は何か／成功したら何が見えるか／失敗したらどうするか／次に何をするか／自分の値に置き換えるものはどれか」に答えさせる。開始時に refs/answers/ へ固定した正答と照らし、正答数と、推測で答えた設問の数で比べる。伏せた一対比較（入門者が詰まらずに進めるのはどちらか）は補助にする。比べる文書は同じ書式のプレーンな Markdown に揃え、製品名・社名・URL は中立の記号に置き換える。
床は npm run build、npm run lint、node gauntlet/check-links.mjs（新規）、node gauntlet/check-scope.mjs（新規。変更が章のディレクトリに収まっているか）。新規の検査は1周目の前に作り、現行版に二度走らせて一致を確かめる。床を通らない変更は評価に回さない。

進め方はあなたが決めてよい。守ることだけを書く。
- 作業を、独立に改善・判定できる単位に分ける。前提を共有する部分は一つの単位にし、一人の担当が順に磨く。並列にするのは結合の無い単位だけ。
- 各単位に作る役と、毎回新しい批評役を立てる。批評役には目標・バー・実物だけを渡し、作る役の説明は渡さない。
- 批評役は、どちらが自作か伏せたまま実物と梯子の段を比べ、勝敗と、差を分けた最大の症状を場所つきで一つ返す。直し方は言わない。
- 作る役は症状を計測で確かめてから、それだけを直す。計測が批評と食い違ったら計測に従う。同じ症状が二周続いたら、直すのをやめて原因を調べる。
- 1周目の前に検査系を作り、同じ版を二度検査して一致することを確かめる。実物と参照は同じ条件で並べる。
- 波の終わりに、全体を新しい批評役に見せて部品間の食い違いを直し、全体と参照の全体を比べる。
- 勝ったと言えるのは、新しい批評役 3 体が全員、順番を入れ替えても最上段に勝つと判定したときだけ。
- 止めるのは、勝ったとき、予算 8 時間を使い切ったとき、梯子の位置が 3 周動かないとき、原因を調べても同じ症状が残るとき、参照が取得できないとき。止まったら理由と現状を報告する。
- 状態は gauntlet/ledger.yaml に置き、進み具合を gauntlet/index.html に示し続ける。
- サブエージェントを使う。/loop や高いeffort設定が使えるなら使う。
```

雛形の［任意］行のうち、検査系の行は残しました。読者タスクは答えが揺れうるからです。並列の行は落としました。「はじめに」章は一本の流れで、前提・用語・手順が互いに依存するため、一つの単位として逐次に磨きます。

## 7. 実行前チェック

- [ ] 作業ツリーを git にコミットし、専用ブランチか worktree で回す。可能ならコンテナかサンドボックスを使う。開始コミットのハッシュを控えておく
- [ ] 無関係な skill と MCP を切ったクリーンなセッションで回す
- [ ] 予算を見張る。8 時間・多数のサブエージェント・高 effort の組み合わせは、個人プランの上限を大きく食う。トークンの上限を決めていないので、最初の 1〜2 周の消費量を見て、8 時間分がプラン内に収まるか確かめる
- [ ] 「未確認」と印をつけたものを実際に開いて確かめる。具体的には、章の実際のパス、`npm run build` と `npm run lint` が失敗時に 0 以外の終了コードを返すこと、`onBrokenLinks` の設定
- [ ] 実行時の環境からも 3 つの参照 URL を取得できるか確かめる（社内ネットワークやプロキシで遮られることがある）。開けない段は差し替えるか外す
- [ ] 参照のスナップショットは評価専用にし、章には取り込まない
- [ ] 章の手順に社内限定の認証や環境が要る場合、読者タスクのエージェントは実際には手順を走らせない。これは読解での判定だと承知しておく
