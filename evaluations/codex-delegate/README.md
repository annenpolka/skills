# codex-delegate evaluation

ラウンドごとに新しい実行主体（Claude Code の general-purpose サブエージェント。シナリオごとに1体）が
`codex-delegate` を読み、**実際の `codex exec` 委譲**（gpt-6-luna、ChatGPTログイン、Codex CLI 0.155.1）を実行した。
親は毎回、次の3点で独立に検証した。

- 親が保持するベースラインとのファイルハッシュ比較
- コピー上でのテスト再実行
- 各スレッドの rollout `turn_context` の確認

実行主体が自己申告した不明点は、親が「スキル欠陥」と「実行主体自身の誤り」に裁定した。
評価対象は委譲プロトコル（sandbox と承認ポリシーの固定、resume、成否判定、証拠、呼び出し側の受け入れ）であり、
モデル品質やコストではない。

評価環境のユーザー Codex 設定は `workspace-write`・`on-request`・自動承認レビュー役・ネットワーク有効・追加の書込みルートを持つ。
これは実行主体には知らせていない。評価前の検証（`codex-delegate/references/validation.json`）で、
`-s read-only` だけでは書込みを防げなかったのはこの条件である。

シナリオは4つ。チェックリストは各ラウンドの開始前に固定した（[scenarios.json](scenarios.json)）。

- A: 実装
- B: 読み取り専用の調査
- C: git管理外のワークスペースで、同一スレッドを2フェーズ
- H: SIGTERMで中断してから同一スレッドで再開

シナリオごとの tool_uses と duration は [results.json](results.json) にある。

**停止判断**: 収束ではなく「リソース打ち切り」で止めた。全ラウンドで全要件を満たしたが、新規の不明点はゼロにならなかった。
iter3〜iter5 で 10・8・8 と3ラウンド減らなかったため divergence 基準に従い、
v6 で誤りやすい機械的な部分を `scripts/codex-delegate.sh` に移した。移したのはフラグ、`cd`、ターンごとの出力、
watchdog、成否判定、rollout 読み取り、スナップショットと比較である。以後、指摘は細部に移り、修正済みの問題は再発しなかった。

**主要な発見（v10までに修正済み）**:
- **承認ポリシーの固定（重大）**: ユーザー設定が `approval_policy=on-request` と自動レビュー役を持つ環境では、
  `-s read-only` の run が権限昇格を申請し、レビュー役がファイル書込みを承認した。ヘルパーは毎ターン
  `approval_policy="never"` を渡す。
- **resume が復元するのは会話だけ**: sandbox、承認ポリシー、モデル、作業ディレクトリ、`--ignore-user-config` は
  すべて設定または実行時の既定値に戻る。ヘルパーは設定を1回保存し、resume のたびに渡し直す。
- **exit 0 は成功ではない**: SIGTERM では exit 0 のまま終端イベントが出ず、実行中の `sleep` が孤児として残った。
  そこで成功の条件を、`turn.completed` が最後のイベントであることと、実効設定が要求どおりであることにした。
  `stop` は子孫プロセスを記録し、`reap` はコマンドラインがまだ一致するPIDだけにシグナルを送る。
- **使用量**: `turn.completed.usage` は中断されたターンの分を含まないことを holdout で発見した。
  現在は rollout の `token_usage_record` からターンごとに取る。
- **ターンの取り違え**: 以前のターンを後から再計算すると、最新の `turn_context` を拾っていた。
  現在は各ターンが自分の rollout turn ID を保持する。
- 台帳: [failure-patterns.json](failure-patterns.json) に12パターンを記録した。

**iter10 以降の修正**: 出荷物は v10 に、iter10 の指摘への修正を加えたものである。

- `accepted-*` の名前が2つの節で食い違っていた
- 時間上限の値をどこにも記録していなかった
- ツール呼び出しの全文が rollout にしかなかった（`tool_calls.jsonl` を出力するようにした）
- 開始状態を記録した後に比較を足した
- 中断で打ち切られたコマンドの扱い
- 制御を返せるか判断がつかないときの予備手段
- 書き込みを否定できないコマンドをスナップショットのコピー上で実行すること

これらはヘルパーのテスト（64/64）、本物のCodexでの読み取り専用の実行、SKILL.md と実装・契約書の Jev 照合で確認した。
評価者による再評価は行っていない。

**未解決（軽微）**:
- 特定のイベントが起きた時点で止めるトリガー（中断のタイマーは呼び出し側の実装に任せている）
- テストコマンドが書き込むかどうかを、コピー上での実行以外で確かめる方法
- 呼び出し側が自分でもブリーフを持つ場合、どちらが正本か

**制約**:
- フィクスチャは小規模で、検証したのは macOS・単一の設定・単一モデル・ChatGPT ログインのみ。
  API キー、Linux、WSL は未検証。
- チェックリストは実行主体に提示している。
- holdout H は1回目のみ真の holdout で、2回目は回帰確認として使った。
- 生ログ、rollout、実行主体のセッションは配布しない。
