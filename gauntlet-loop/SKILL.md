# Gauntlet Loop（ガントレット・ループ）

## 定義

> 実在する参照に負けている限り、毎回新しい批評役が実物と参照を伏せて比べ、
> 差を分けた最大の症状を一つ返す。作る役はそれを計測で確かめてから、それだけを直す。
> 勝つか、先に書いた停止条件に当たるまで繰り返す。

このskillの本体は手順ではなく不変条件。分け方、作り方、道具の選び方はリードエージェントが決める。
強いモデルに道順を書き込むと、モデルの判断を人間の判断で上書きすることになる。

七つの不変条件:

1. **バーは実在し、取得でき、並べて比べられる。** 「すごく」「本番品質」はバーではない
2. **作った者は採点しない。** 批評役は毎回新しい文脈で起動し、作る役の経緯も説明も受け取らない
3. **実物を見る。** 要約、作る役の報告、説明文は判定材料にならない
4. **批評は症状を言い、処方しない。** 原因と直し方は、計測した作る役が決める
5. **一周に一つ。** 直すのは最大の差だけ。複数を同時に直すと、何が効いて何が壊したかが分からなくなる
6. **床は機械で守る。** 非回帰はコマンドの終了コードで判定する。宣言では通さない
7. **回数ではなく条件で止める。** 条件は開始前に書く

このskillが長いのは設計時の知識だから。実行時に渡すプロンプトは短く保つ。

## 出自と補強

手法は Matt Shumer が2026年7月に名付けたもの（Claude of Duty を生んだプロンプト）。原典の骨格は
「ゴールと実在の参照を渡す → リードが分割する → 部品ごとに作る役と独立した批評役 →
ブラインド比較で負けたら最大の差を差し戻す → 固定回数なしで回す」。

このskillは骨格を保ち、Claude of Duty 自身の README に残った記録で補強している。

| 公開記録 | 補強 |
|---|---|
| ブラインドA/Bでは、全ラウンドで全批評役が本物のCall of Dutyを選んだ。進捗は10点満点スコア（3.59→4.14→4.05→5.05）と致命的欠陥の数で追われていた | 二値の勝敗は終了判定にだけ使う。進捗は参照の梯子で測る |
| ディレクトリ単位の6体並列×3ラウンドはスコア+0.46、致命的欠陥は60→47→66と悪化した。トーンマップ・空・間接光が一つの結合系で、互いの前提を壊し合ったため。結合した関心ごとに単独の担当を置いた逐次パスは+1.00、欠陥66→26 | 分割は結合で切る。結合系は単独担当が逐次に磨く |
| 批評役は3ラウンド続けて武器を「テクスチャが無い」と報告したが、実際は鏡面反射が支配的で拡散成分が足りなかった。先行ラウンドは明るすぎるという苦情に応えてアルベドを下げ、悪化させていた。最も価値ある修正は、指示と逆の方向だった | 批評は症状だけを言う。作る役は計測してから直し、批評に反してよい。同じ症状の再発は原因調査に切り替える |
| 静止カメラのベンチは94fpsだったが、実プレイは12〜17fpsで1秒前後の停止があった。撮影は前のショットの状態が漏れ、同じ条件の2回で11枚中10枚が一致しなかった | 1周目の前に検査系を作り、再現性と代表性を検証する |
| 最適化パスの「見た目の変化ゼロ」は画素差分ゲートで強制した。アート強化で三角形数は5.9Mから11.3Mに増え、フレームレートが落ちた | 守る軸を床に書き、ゲートで強制する |

派生実装からも取り込んでいる。取得できない参照だと批評役は比較をでっち上げて全部通す。
前の版を見た批評役に次の版を採点させない。リードは実装しない。部品が全部勝っても、最後は全体と参照の全体を比べる。

## モードの選択

| モード | 使う場面 | 出すもの |
|---|---|---|
| compose（既定） | いつでも。サブエージェントの無い環境（claude.ai 等）では必ずこちら | 判定、バーと梯子、比べ方、床、停止条件、貼り付け用の実行プロンプト、実行前チェック |
| run | 利用者がこのセッションでの実行を明示し、独立した批評役を立てられるとき | ラン本体（台帳、進捗ページ、成果物） |

composeを既定にする理由: Shumer は、他のskillやMCPが有効なセッションではループが乗っ取られ、結果が大きく落ちると報告している（本人の経験則で、独立した検証は確認できていない）。
実行はクリーンなセッションに任せ、このskillは設計に使う。runを選ぶときは、有効な他のskillがあることを利用者に一度伝えてから始める。

独立した批評役を立てる手段:

- 独立したコンテキストを持つサブエージェント（Claude Code 等）
- 非対話CLIを別プロセスで起動する（`claude -p`、`codex exec` 等）。プロセスが別なら、文脈の独立は構造で保証される

どちらも無い環境で「批評役を演じる」のは独立ではない。runは不可、composeに落とす。

## Phase 0: 回すかどうか

四問すべてが「はい」のときだけ回す。

1. 成果物を、エージェントが実物として検査できるか（描画、実行、読解、計測）
2. 取得できるバーの候補があるか、探せば見つかる見込みがあるか
3. 「良い」が機械検証だけでは決まらないか。決まるならテストを書けば足りる
4. 予算の上限を決められるか

一つでも「いいえ」なら、理由を一文で述べて代わりを示す（テストと型で閉じる／人間のレビューを挟む／一発生成で足りる）。
例: 決済金額の計算ロジックは3が「いいえ」。欲しいのは正しさで、正しさはテストが決める。
機械で決まる部分と決まらない部分が混ざるなら、前者を床に、後者をバーに回す。

## Phase 1: バー

### 六つの条件

| 条件 | 問い | 欠けたときの壊れ方 |
|---|---|---|
| 名指し | カテゴリではなく具体的な一つか | 批評が一般論になる |
| 取得可能 | 批評役が実際に開ける・動かせる・読めるか | 比較がでっち上げられ、全部合格になる |
| 同種同尺 | 同じ粒度・同じ条件で並べられるか | 比較が感想になる |
| 識別可能 | 差を言葉にできる程度に近いか | 勝敗が気分になる |
| 固定 | 実行中に変わらないか | ラウンド間の比較が崩れる。開始時に `refs/` へスナップショットを取る |
| 素材ではない | 水準の目安として使い、中身を写さないか | 模倣で勝つ。ライセンス上も成果物に取り込まない |

### 参照の梯子

最上段は届かなくてよい（原典もそう言っている）。ただし届かない参照との二値比較は毎回負け、進捗の情報を返さない。
スコアで補うと、点は周ごとに上ずりやすい（派生実装の指摘）。

だから開始時に3〜5段の梯子を固定する。下の段は届く水準、最上段は目標の水準。
人間が選ぶのは最上段だけ。途中の段はリードが選び、下の較正で順を確かめる。途中の段のためにゲートは作らない。
開始時の現行版は、スナップショットにして最下段に置いてよい。最上段は必ず外部の実物にする。

- 位置 = 新しい批評役がブラインドで勝った最も高い段
- 段は外に固定された実物なので、評価者の甘さでずれない
- 最上段に届かない間も、位置の変化が進捗の信号になる

**較正**: 1周目の前に、隣り合う段同士を新しい批評役にブラインドで比べさせ、想定どおりの順になるか確かめる。
順が崩れる段は入れ替えるか外す。既知の参照すら並べられない批評役は、この領域で成果物を判定できない。そのときは Phase 0 に戻る。

梯子の中身は開始後に変えない。変えたくなったら止めて人間に戻す。

### 領域別の型

| 領域 | 床（機械ゲート） | 梯子（下→上）の例 | 比べ方 |
|---|---|---|---|
| Web/UI | ビルド、リンタ、a11y自動検査、表示性能の予算 | 同カテゴリの平均的な実サイト → 評価の高い実サイト → カテゴリ最上位 | 固定ビューポート（デスクトップ・モバイル）、同じ内容量で撮る |
| 文章 | 事実・引用の照合、分量 | 同じ読者層向けの平均的な記事 → 定評ある書き手の記事 | 読者タスク: 新しいエージェントに片方だけ読ませ、同じ設問への正答で比べる |
| バックエンド/CLI | テスト、型、リンタ、既存契約、性能予算 | 自分の現行版 → 定評あるOSSの同等機能 | 同じハーネスでのベンチ、同じ障害注入、同じ用途のクライアントコードを両方に対して書かせたときの書きやすさ |
| 調査・報告 | すべての主張が出典に辿れる | 平均的な報告 → 定評ある報告 | 判断タスク: 読んだ後に同じ意思決定をさせ、残った未解決の問いの数で比べる |
| skill・プロンプト | 形式の検証、取り置き集の封印 | 素のモデル（skill無し）→ 一行だけ指示した素のモデル → 定評ある実物（人間の専門家の出力、等） | タスクを開発用と取り置きに分けて開始前に固定する。症状は開発用から、勝敗と位置は取り置きからブラインドで取る。素のモデルの段に勝てないなら廃止を提案する |
| ゲーム・3D | 決定論的な撮影、画素差分、フレーム時間の分布 | 同規模の作品 → 目標の作品 | 同じ構図・同じ解像度のフレーム |

型は組み合わせてよい（UIの撮影比較に読者タスクを足す、等）。
好みの比較が割れやすい領域では、比較を課題に変える（読者タスク、判断タスク、利用タスク）。
「どちらが良いか」より「どちらでこの課題が解けるか」のほうが判定がぶれない。

参照と成果物で題材が違う（他社の入門記事と自社の入門章、等）なら、設問は内容に依存しない型で固定する。
例: 前提は何か、最初の一手は何か、成功したら何が見えるか、失敗したらどうするか、次に何をするか。
各文書の正答は開始時に作って `refs/` に固定する。設問集は検査系の一部として Phase 2 で検証する。

### バーが決まっていないとき

バー探しを最初の仕事にする。「良いとは何かを決めて」とは頼まない。
候補を探し、六条件で落とし、残った2〜3案を一文の理由つきで人間に示して選ばせる。これが最初の人間ゲート。

- ゲートの前に出してよいかは「どのバーが選ばれるかで中身が変わるか」で決める。項目ごとの振り分けは「composeモードの出力」の表に置いた
- 予算の上限、実行の場所（runかcomposeか）、成果物の所在など、後の手順に要ることで利用者にしか決められないものは、同じゲートでまとめて聞く。ゲートを何度も作らない。runを選択肢に出すときは、他のskillやMCPが有効なことを選択肢の説明に書く

利用者がサイトや作者の単位で名指しし、どのページや作品かが決まらないときは、未定とは扱わない。
最も妥当な一つを選び、理由と「開始前なら差し替えられる」ことを添えて進める。候補によって判定が変わるときだけ、ゲートで聞く。

## Phase 2: 床と検査系（1周目の前）

### 床

- 終了コードで結果が決まるコマンドの一覧。テスト、型、リンタ、既存契約の検査、性能・サイズ・費用の予算
- 床が赤い変更は批評に回さない。比較でどれだけ勝っていても採用しない
- 天井（バーに向けた改善）を押すと床が削れる。守りたい軸はすべて床に書く
- まだ無い検査（金額の突合、手順の実走、変更範囲の確認など）を床に入れるときは、新規と明記する。1周目の前に作り、現行版に二度走らせて同じ結果になることを確かめてから床にする

### 検査系

批評役が見る「実物の見え方」を作る道具（撮影、実行、計測、整形）。成果物と同じ扱いで作り、次の三つを検証してから使う。

- **再現性**: 同じ版を二度検査して一致する（許容差を認めるなら先に書く）。乱数の種、時計、状態の持ち越しを潰す
- **代表性**: 実際の使われ方で測る。中央値だけでなく分布（p50/p95/p99）と最悪値を残す
- **正規化**: 成果物と参照を、同じ解像度・切り抜き・圧縮・書式・長さの枠で出す。出自の癖で見分けがつくと、批評役は品質ではなく「どちらが本物か」を当てにいく。製品名・社名・URLなど出自を明かす固有名は中立の記号に置き換える。題材そのものが出自を明かすなら、課題（読者タスク等）を主な判定にし、伏せた一対比較は補助にとどめる

検証に落ちたら、作る役を動かす前に検査系を直す。再現しない検査の上での比較は雑音でしかない。

## Phase 3: 分割と契約

- **単位は、前提を共有するまとまり。** ファイルやディレクトリで切らない
- 判定の問い: 「Aを変えるとBの評価が変わるか」。変わるなら同じ単位にするか、逐次に並べる
- 並列にするのは結合の無い単位だけ。結合した関心ごとは、単独の担当が順に磨く
- 並列にする前に契約をファイルに書く: 所有範囲（誰が何を編集してよいか）、インターフェース、共有する語彙（イベント・型）、決定性の規則、禁止する依存
- 並列の担当は別々の作業ツリー（git worktree 等）で動かし、統合で合流させる
- 部品に切れない性質（操作感、全体の一貫性、文章の流れ）は全体でしか判定しない。無理に部品にしない

## Phase 4: ラウンド

### 一周

1. 作る役: 目標・バー・梯子・契約・今回の症状（場所つき）を受け取る
2. 作る役: 症状を再現して計測する。計測が批評の見立てと食い違えば計測に従い、食い違いを記録する
3. 作る役: その症状だけを直す。所有範囲の外は触らない。版を切る（コミット）
4. 床: ゲートを回す。赤なら直すか戻す。批評には回さない
5. 批評役（新規）: 正規化した実物と梯子の段を、ラベルを伏せて一対ずつ比べる
6. 批評役: 各対の勝敗と、差を分けた最大の症状を一つ返す。症状は、負けた対のうち最も高い段との対から取る
7. リード: 台帳に記録し、続行・戻す・原因調査・人間へ、のどれかを決める

進捗の周で比べるのは三対だけ: 現在の段、一つ上の段、前の版。上の段に勝てば位置が上がり、現在の段に負ければ下がる。

### 批評役への渡し方

渡すもの: 目標、バー（段つき）、規則、正規化した実物。対の並び順とラベルは毎回ランダムにし、対応表はリードだけが持つ。

渡さないもの: 作る役の経緯・説明・自己評価、以前の批評、どちらが自作かの手がかり。

返させる形:

```yaml
pairs:
  - pair: P1
    winner: Y            # X / Y はランダムな伏せ字
    confidence: high     # low は引き分けとして扱い、位置を動かさない
biggest_gap:
  symptom: 近距離で武器の表面がのっぺり見える   # 何が、どう見えるか
  where: ショット3、ショット7の手元
  visible_in: X
imitation_suspected: false   # 片方が他方の写しに見えるか
cannot_judge: null           # 参照が開けない、条件が揃っていない、等
```

直し方は書かせない。症状に名前をつけるまでが批評役の仕事で、原因の特定は作る役が計測でやる。
批評の見立てが外れ、処方どおりの修正が悪化させた記録があるから。

### 周をまたぐ規則

- **前の版との比較**: 新しい批評役に、前の版と今の版のどちらがバーに近いかをブラインドで問う。後退なら戻す。問いには必ずバーを添える。添えないと、批評役はバーへの距離ではなく改善の幅を採点しはじめる
- **再発**: 同じ症状が二周続いたら直すのをやめ、原因調査の周にする。計測と切り分けだけを行い、見立てを書き直す
- **補償負債**: 原因を直さず症状を打ち消す変更（明るすぎるから暗くする、等）は台帳に補償として残す。補償が溜まった単位は原因調査に回す
- **批評役の数**: 進捗の周は1体で足りる。最上段への勝ちを主張する周だけ、新しい批評役をk体（既定3）立てて全員一致を求める。安い周を多く回し、判定の周だけ厳しくする
- **並び順の偏り**: LLMの判定者には提示順の偏りがある。勝利判定では各対を順番を入れ替えて二度判定し、両方で勝ったときだけ勝ちとする
- **系統の偏り**: 文脈を新しくしても、同じモデルは同じ盲点を持つ。自分と同系統のモデルが書いた文章を好む偏りの報告もある。勝利判定には、可能なら別系統のモデルを批評役に混ぜる

## Phase 5: 波の終わり

1. 新しい批評役に全体を見せ、部品同士の食い違いだけを挙げさせる
2. 統合担当が食い違いだけを直す。作り直しはしない
3. 全体と参照の全体をブラインドで比べる。部品が勝っても全体が勝ったことにはならない

## 停止条件

開始前に台帳の先頭へ書く。固定の周回数は置かない。
原典が挙げる止めどき（満足した、改善が小さくなった、計算資源を使い切った）を、条件として先に書いておくだけ。

| 条件 | 判定 | 動作 |
|---|---|---|
| 勝利 | 全体で最上段に、新しい批評役k体が全員一致・順番を入れ替えても勝ち、かつ床が緑 | 終了 |
| 予算 | トークン・時間・周回の上限に達した | 終了して報告 |
| 停滞 | 梯子の位置がN周（既定3。予算で回せる周回が少なければ下げる）動かず、欠陥も減らない | 人間へ |
| 再発 | 原因調査の後も同じ症状が出る | 人間へ |
| 根拠の欠落 | 参照が取得できない、検査系が再現しない | 停止 |
| 衝突 | 批評の要求が目標・床・契約と矛盾する | 人間へ |
| 価値判断 | 次の一手に人間の好み・権限・リスク判断が要る | 人間へ |
| 手動 | 人間が止めた | 終了して報告 |

止まったら、理由、梯子の位置の推移、残る最大の症状、補償負債、使った予算を報告する。

## 台帳と進捗ページ

状態はファイルに置く。リードの文脈が圧縮されても、別のセッションに替わっても、台帳から再開できるように。

```yaml
# gauntlet/ledger.yaml
run:
  goal: 自作CLIのエラー表示を、次に打つべきコマンドが分かる水準にする
  bar: {top: rustc, rungs: [現行版, git, cargo, rustc], snapshots: refs/}
  floor: ["npm test", "npm run lint", "node tools/exit-codes.mjs"]
  budget: {tokens: 30M, hours: 4}
  stop: {plateau_rounds: 3, exit_critics: 3}
  defect_taxonomy: [誤った案内, 原因の欠落, 読めない長さ]   # 任意。開始時に固定する
rounds:
  - id: R-007
    unit: エラー表示の書式
    version: 9f3c2e1
    gap_in: {symptom: 不正な値のとき何を渡せばよいか分からない, where: 誤用シナリオ4と9, from: R-006}
    diagnosis: {measured: 期待値を出す分岐が2経路で欠けている, contradicts_critic: false}
    change: 検証エラーに期待値と入力例を足した
    floor: pass
    critics: [{id: c-019, fresh: true, family: claude}]
    ladder: 2                   # 勝った最も高い段の番号（0始まり）
    vs_previous: better         # better | same | worse
    defects: 5
    compensation: []
    decision: continue          # continue | revert | investigate | escalate | stop
    spent: {tokens: 1.2M, minutes: 14}
```

人間が進捗ページで見つけた症状は、`from: human` として台帳に足してよい。リードは次の周でそれを優先する。

進捗ページ（`gauntlet/index.html` か `workbench.md`）には、梯子の位置の推移、最新の実物と参照の並置、残る症状、予算の消化を載せる。
人間はこれを眺め、割り込まずに見守る。

## composeモードの出力

次の順で出す。

1. **判定**: Phase 0 の四問への答え。回さないならここで終わる
2. **バー**: 最上段と、それを選んだ理由を一文。梯子の各段と、その取得方法
3. **比べ方**: 領域別の型から選ぶ。好みの比較が割れやすいなら課題に変える
4. **床**: コマンドの一覧
5. **停止条件**: 予算、停滞の周回数、勝利判定の批評役の数
6. **実行プロンプト**: 下の雛形に代入する
7. **実行前チェック**

バーが決まっていないときは、1の後に最上段の候補を2〜3案出し、人間ゲートで選んでもらう。各項目をゲートの前後どちらで出すかは次の表で決める。

| 項目 | ゲート前 | ゲート後 |
|---|---|---|
| 1 判定 | 出す | — |
| 2 バー | 最上段の候補2〜3案（これが選ばせる対象） | 梯子の全段と取得方法 |
| 3 比べ方 | 領域の型で決まる方針と設問の型 | 各段の正答、正規化の細部 |
| 4 床 | 見込み（新規の検査には「新規」の印） | 所在を確かめたうえでのコマンドの一覧 |
| 5 停止条件 | 既定値（停滞3周、勝利判定3体）と予算の案 | 確定値 |
| 6 実行プロンプト | 書かない | 書く |
| 7 実行前チェック | 書かない | 書く |

利用者の入力が欠けているときの扱い:

- Phase 0 の問い4は「決められるか」を問う。値がまだ無くても「はい」でよく、値はゲートで聞くか案を置く
- 予算の軸を一つでも示されたら（「一晩8時間」等）、それで進める。他の軸（トークン等）は実行前チェックで見張る対象にし、そのためだけにゲートを作らない
- 「回して」「やって」のような動詞だけでは run の明示とみなさない。「このセッションで」「runで」のように場所やモードの指定があって初めて明示とする
- 参照は、設計時に開ける環境なら開いて確かめてから出す。開けないなら「未確認」と書き、実行前チェックで取得を確かめる。成果物側の所在（章のパス、設定値など）を推定で書いたときも同じく「未確認」とする

依頼に対象が複数あるときは、判定を対象ごとに出し、設計は一つにまとめる。回さない対象の機械検査（テスト、突合）は、回す対象の床に組み込む。
例: 手数料計算は問い3が「いいえ」なのでテストで閉じ、メール文面のループの床に `npm test` と、メールに載る金額と計算結果の突合を入れる。

### 実行プロンプトの雛形

短く保つ。道順は書かない。［任意］の行は、その失敗が起こりうる課題のときだけ残し、残した行からは［任意…］の札を外す。

```text
{GOAL}

バーは {TOP_BAR}。途中の段として {RUNGS} を使う。開始時にすべてを refs/ に保存し、以後はそれを基準にする。
比べ方: {METHOD}
床は {FLOOR}。床を通らない変更は評価に回さない。

進め方はあなたが決めてよい。守ることだけを書く。
- 作業を、独立に改善・判定できる単位に分ける。前提を共有する部分は一つの単位にし、一人の担当が順に磨く。並列にするのは結合の無い単位だけ。
- 各単位に作る役と、毎回新しい批評役を立てる。批評役には目標・バー・実物だけを渡し、作る役の説明は渡さない。
- 批評役は、どちらが自作か伏せたまま実物と梯子の段を比べ、勝敗と、差を分けた最大の症状を場所つきで一つ返す。直し方は言わない。
- 作る役は症状を計測で確かめてから、それだけを直す。計測が批評と食い違ったら計測に従う。同じ症状が二周続いたら、直すのをやめて原因を調べる。
- ［任意: 検査が揺れうる（撮影、計測、読者タスクなど）］1周目の前に検査系を作り、同じ版を二度検査して一致することを確かめる。実物と参照は同じ条件で並べる。
- ［任意: 並列］並列にする前に、所有範囲とインターフェースをファイルに書く。
- 波の終わりに、全体を新しい批評役に見せて部品間の食い違いを直し、全体と参照の全体を比べる。
- 勝ったと言えるのは、新しい批評役 {K} 体が全員、順番を入れ替えても最上段に勝つと判定したときだけ。
- 止めるのは、勝ったとき、予算 {BUDGET} を使い切ったとき、梯子の位置が {N} 周動かないとき、原因を調べても同じ症状が残るとき、参照が取得できないとき。止まったら理由と現状を報告する。
- 状態は gauntlet/ledger.yaml に置き、進み具合を gauntlet/index.html に示し続ける。
- 批評役は毎回、文脈を共有しない別のサブエージェントか別プロセス（codex exec、claude -p 等）で立てる。
- ［任意: Claude Code］/loop や高いeffort設定が使えるなら使う。
```

### 実行前チェック

- 作業ディレクトリをgitにコミットするか、バックアップを取る。可能なら worktree・コンテナ・サンドボックスで回す
- 無関係なskill・MCPを切った、クリーンなセッションで回す
- 予算を見張る。長時間・多数のサブエージェント・高effortの組み合わせは、個人のプラン上限を大きく食う（原典側も警告している）
- 参照のスナップショットは評価専用。成果物に取り込まない
- 「未確認」と印をつけた参照と所在を実際に開いて確かめる。開けない段は差し替えるか外す

## runモード

自分がリードになる。

1. Phase 0〜2 を行い、バー・床・停止条件を利用者に確認する。ここが人間ゲートで、確認が済めば以後の割り込みは要らない
2. 契約、台帳、進捗ページを作る
3. Phase 3〜5 を回す。批評役は必ずサブエージェントか別プロセスで立てる
4. リードは実装も判定もしない。持つのは分割、割り当て、記録、判定の集計、停止の判断だけ。
   自分で直した変更を自分の集計で通した瞬間、作った者が採点していることになる

## Deny

- 批評役が取得できない参照をバーにする
- 較正で順が崩れた梯子のまま回す
- 作る役やリードが自分の成果を採点する
- 前の版を見た批評役に、次の版を採点させる
- 要約、作る役の報告、説明文をもとに判定する
- 批評役に直し方を指示させる／作る役が計測せずに批評の処方を実行する
- 一周で複数の差を直す
- 床が赤いまま批評に回す／床を宣言で通す
- スコアの上昇を勝利とみなす（勝利は最上段へのブラインドでの勝ちだけ）
- 前提を共有する部分を、別々の担当に並列で渡す
- 再現性を確かめていない検査系で、ラウンド間を比べる
- 部品の勝ちを全体の勝ちとみなす
- 参照を写して勝つ
- 予算と停止条件を書かずに始める
- 開始後に梯子の段を差し替える
- 他のskillやMCPが有効なセッションで、そのことを告げずにrunを始める

## 例: composeの出力

入力: 「自作CLIのエラーメッセージを良くしたい。Claude Codeで回す」

1. **判定**: 検査できる（実行して出力を読める）／バー候補あり／良さはテストだけでは決まらない／予算は決められる → 回す
2. **バー**: rustc のエラー表示。原因の位置、理由、次の一手を一画面で示す水準として定評がある。
   梯子は 現行版 → git → cargo → rustc。各ツールで同種の誤用（引数不足、不正な値、未知のフラグ、競合する指定）を実際に起こし、出力を `refs/` に保存する
3. **比べ方**: 利用タスク。誤用シナリオ20件について、新しいエージェントにエラー出力だけを見せて正しい呼び出しに直させ、成功までの試行回数で比べる。あわせて伏せた一対比較
4. **床**: `npm test`、終了コードの契約テスト
5. **停止条件**: 予算4時間、停滞3周、勝利判定は3体
6. **実行プロンプト**: 雛形に代入する。エラー表示の書式は全サブコマンドが共有する前提なので、一つの単位として逐次に磨く。並列の［任意］行は落とす。利用タスクは試行ごとに揺れうるので、検査の行は札を外して残す
7. **実行前チェック**: gitへのコミット、クリーンなセッション、予算の見張り
