# Defense-Driven Refit（弁明駆動改修）

## 定義

> 成果物に対する質問から、根拠の不足・不要な判断・説明と実体の矛盾を発見し、
> 説明と成果物の両方を修正して、人間が採用判断を引き受けやすくする後工程。

このskillは成果物を弁護しない。弁護士が長演説しなくて済むように、成果物のほうを整える。

全部を必然として弁護するな。

- 必要なものは根拠で支える
- 不要なものは削る
- どちらでもよいものは「どちらでもよい」と説明する
- 分からないものは範囲を明示して保留する

目的は弁明の量ではなく、弁明する負担を減らすこと。
interfaceを五枚足して「疎結合だから」と言うのは負担を増やしている。
逆に、状態遷移を型に限定して「この状態ではこの操作を受け付けない」と局所的に
説明・確認できるなら、コードが増えても意味がある。

## なぜ「後付け」が正当か

AI出力に復元可能な意図は無い。だから「なぜこうなったか」を当てる作業は成立しない。
成立するのは「なぜ妥当か」を用意する作業で、これは堂々と後付けできる。
ADRが審議録を持たないのと同じ理屈。

**時制を固定する。** 台帳に書くのは妥当性の条件。選択の経緯（誰がいつ何を検討したか）は書かない。
存在しない審議史を語った瞬間に嘘になり、問い詰められた場面で真っ先に割れる。

弁明が割れるのは曖昧だからではなく、滑らかで偽だから。
だから台帳の各行は検証手段を持たなければならない。

## 根拠と証拠 — 最重要の区別

| 種類 | 答える問い | 例 |
|---|---|---|
| 根拠 (grounding) | なぜその性質・選択が必要／妥当か | 要求、計測値（出典つき）、既存契約、名前つき規約、許容範囲の宣言 |
| 証拠 (evidence) | 成果物が実際にその性質を持つか | テスト、型、実行結果、特性化テスト |

二つを分けないと循環する。

```
実装は3回リトライする
  → 3回リトライすることを確認するテストを書く
  → 「テストがあるので3回には根拠がある」
```

これは3回を保存しただけで、3回を採用する理由は増えていない。
根拠になり得るのは「応答時間の上限」「追加リクエストの許容数」「既存設定との整合」。
テストはその条件に実装が合っていることを確認する役。

### 根拠の五種

- `requirement` — 要求・チケットへの参照
- `measurement` — 値と出典
- `existing_contract` — 既存API・既存実装との整合
- `convention` — 名前つき規約（「Rails流儀」「チーム規約§3」）
- `freedom` — 許容範囲内の任意選択。「既存設定に合わせた。2や4を否定はしない」も弁明として成立する。すべての定数に必然を背負わせなくていい

### 証拠の四種

- `test` / `type` / `execution_result`
- `characterization_test` — 必ず `preservation_only: true` を付ける。現在の挙動を変えないための証拠であり、現在の挙動が望ましいことの証拠ではない

### 規則

- 根拠と証拠を単一の強さ順に並べない。役割が違う
- 根拠は親の判断から継承できる。証拠は継承しない——親が妥当でも子の実装が正しいことにはならない
- 証拠の要素を根拠の欄に書かない。現在値を主張するテストは根拠にならない

## 台帳 (ledger)

保存はグラフ、閲覧は木。横断的な判断（冪等性がAPI・DB制約・ワーカーにまたがる等）は
一つのファイルの子に押し込めない。IDと参照があれば十分で、グラフDBは要らない。
ファイル形式と置き場所は自由（YAML一枚で足りる）。

### 項目の形

```yaml
id: D-014
scope: {ref: "app/services/sync.rb:40-85", version: "a1b2c3d"}
layer: 境界             # 構造 | 境界 | 手続き | 細部
origin: deviation       # deviation | impact | counterexample | asked
question: なぜこの形    # 無いと何が壊れる | なぜこの形 | どの前提 | 誰の要求 | どう反証
current_answer: テスト時の差し替えのために中間層を置いている
grounding: []
evidence: []
gap: 差し替えは現状どこからも利用されていない
resolution:
  action: remove_or_align   # narrow | investigate | change | remove_or_align | defer
  reason: 独立した責務が確認できず、維持の利点が弱い
verification:
  status: pending           # pending | done
  plan: 公開契約と既存の利用経路に影響がないことを確認する
  result: null
  artifact_version: null
final_answer: null
admitted_limit: null        # {limit, revisit_condition}
depends_on: [D-009]
```

### 項目の規則

- `verification.status: pending` の間、`final_answer` は null のまま。ここが台帳を飾りにしない一点
- `verification.status: done` の記録は `artifact_version` を含み、`scope.version` と一致する
- 項目の `resolution` が変わったら、`depends_on` で辿れる全項目の `verification.status` を pending に戻す
- 全項目が `origin` を持つ。入口に到達していない項目は作らない（木の先行生成をしない）
- 全項目が「根拠が1つ以上」「`freedom` の宣言」「`admitted_limit`」のいずれかを持つ
- 必須フィールドのみで20行以内に収める

### 層 (layer)

| 層 | コード | 設計文書 |
|---|---|---|
| 構造 | 何を置くか（モジュール、依存） | 構成 |
| 境界 | 何を公開するか（シグネチャ、契約） | コンポーネント間インターフェース |
| 手続き | どう流すか（制御、アルゴリズム） | 処理シーケンス |
| 細部 | 定数、分岐、エラー処理 | パラメータ |

同一scope内で、下位層の `resolution` は上位層の `resolution` 確定後にのみ確定する。
質問は任意の順で到着してよく、記録はいつでもする。確定だけを上から行う。
定数を磨いたモジュールをあとで消すのは無駄だから。

## 質問の入口

台帳の項目は四つの入口からしか生まれない。

### 1. 逸脱駆動 (deviation) — 退屈版との差分

同じ課題の「そのプロジェクトで普通とされる実装」を用意し、成果物とdiffを取る。
差分が出た箇所が「決定」で、説明が要るのはそこ。
一致した箇所の理屈は「既定値、逸脱理由なし」で済む。
レビュアーが突くのは驚いた箇所で、驚きとは期待からのずれ、期待の近似が退屈版——だからこれでスケールする。

退屈版の参照順序:

1. 明示された規約（lint設定、CONTRIBUTING、設計ガイド）
2. 同種の既存実装（隣のAPI、隣のジョブ）
3. 採用フレームワークの標準形
4. それでも足りない箇所だけ、生成した最小案

LLMが思う一般的コードより、プロジェクト内の慣行を優先する。
「同じAPI群と同じエラー形式に揃えた」は `existing_contract` という根拠になる。独自の思想は要らない。

退屈版は質問を見つける道具であって、採用の免罪符ではない。
複数回生成して多数決を取る手もあるが、測れるのは「そのモデルがよく選ぶ形」であり、必須にしない。
各層の退屈版は、上の層で実際に採られた決定を前提に生成する（「このキュー構成を前提にした一番ありきたりなenqueue」）。

### 2. 影響駆動 (impact) — 普通の実装でも成立するか

退屈版と一致した箇所を無検査にしない。
影響領域に該当するscopeは、退屈版一致でも `origin: impact` の項目を最低1つ持つ。

影響領域は成果物の外から供給する。成果物を見て決めると「驚いた箇所」に戻ってしまう。
案件ごとの一覧が無ければ、次の初期一覧から該当を拾い、案件固有の項目を足す。

```
認可・認証の前提 / データの保存期間と削除 / 障害時・部分失敗時の挙動 /
冪等性・重複実行 / 金銭・課金に触れる計算 / 個人情報の経路 /
外部サービスへの副作用 / 時刻・タイムゾーン / 並行実行 / 移行・後方互換
```

この入口が実務で一番落ちる。逸脱駆動はdiffが自動で出すが、影響領域は誰かが持ち込むしかない。
無ければ静かに省略される。

#### バックエンド向けの知識索引

バックエンドを対象とする場合は、[impact-profileの共通手順](references/impact-profiles/README.md)と
[バックエンド索引の入口一覧](references/impact-profiles/backend.md)を読み、該当・不明の分野だけ展開する。
各行は適用場面・知識へのanchors・外せない問いを持つ。anchorsは想起/検索の入口であり、根拠や証拠ではない。
案件の要求・契約・運用条件も参照し、コードに痕跡がないだけで非該当にしない。
同じ対象・契約・解決にまとまる問いは束ね、任意の `impact_refs` にIDを保持できる。
不明は調査し、未検証はpendingに残す。対処済みと確認できた問いは閉じる。
索引から新しい必須要件・抽象化・本番操作の許可を勝手に導かない。

### 3. 反例駆動 (counterexample) — 敵対的再生成

「この説明に従っているように見えるのに、実際には困る実装」を作らせる。

```
説明: 失敗した要求を自動で再試行する
反例: 同じ副作用を二重に発生させる実装（説明には従えてしまう）
欠けていた条件: 何を再試行してよいか／成功したか不明な場合の扱い
```

反例は差分ではなく反例なので、分類の労働が要らない。
各反例はそのまま `origin: counterexample`、`question: どう反証` の項目として台帳に入る。
説明が「何をしてよいか」だけ書いて「何をしてはいけないか」を書いていない箇所——仕様の境界——に最もよく刺さる。

普通の再生成（理屈だけから成果物を再生成してdiff）は補助にとどめる。
差分ゼロは完全性の証明ではない。同じ判断から複数の妥当な実装ができるし、
元のコードを散文で言い換えた台帳は再現しやすいだけで、説明にはなっていない。
使うなら差分を「許容された自由度／説明に欠けていた判断／再生成側の条件違反」に
分類する労働を引き受けること。

### 4. 実問 (asked) — 実際に来た質問

レビュアーや同僚が実際に投げた質問。そのまま項目にする。
台帳の形は実際の尋問の履歴を写す。

想定問答はその前倒し。詰めてくる相手が特定できるなら、その人の質問傾向で模擬尋問をかけて先に掘る。
生身の相手がいない一発生成では、この成果物を一番厳しく見るレビュアーを想定して同じことをする。
相手がいないことは、この工程を飛ばす理由にならない。

## 尋問の五問

各項目は五問のうちどれかに答える。層に依存しない。

1. 無いと何が壊れる？（削除探針で実行できる）
2. なぜこの形で、隣の形じゃない？
3. どの前提を焼き込んでいる？
4. 誰の要求に遡れる？
5. どうすれば反証できる？（反例駆動で実行できる）

## 削除探針 — 「無いと何が壊れる」の実行

実際に消してテストを回す。ただし結論は三分岐を記録してから出す。

```
1. 削った領域はテストで実行されていたか？
   → 実行されていない: 実験は何も言っていない。カバレッジの穴として記録し、探針を保留
2. 実行されていて、振る舞いは変わったか？
   → 変わらない: 冗長。remove_or_align
3. 振る舞いが変わったのに、テストは落ちたか？
   → 落ちない: その振る舞いは要らないか、要るなら「現在値」ではなく「必要」を
     符号化するテストが欠けている。前者なら削除、後者なら根拠を先に書き、証拠は後
```

「消して壊れない」は三つの意味を持ち、機械では内訳が確定しない
（変異の等価性は一般に判定不能）。分岐2の判定には人の目が残る。
設計文書では「どの要求が満たせなくなるか」に読み替える。

## 改修 (refit)

根拠の無い決定には、理由を発明せず成果物を変える。
発明した理由は、問い詰められるまさにその瞬間に負債になる。

五つの対応。最小のものを選ぶ。

| action | 何をするか |
|---|---|
| narrow | 説明を限定する。「許容範囲内で既存設定に合わせた」等、主張を弱めて成立させる |
| investigate | 根拠を調べる。計測、要求の確認、既存契約の確認 |
| change | 実装を変えて、根拠を持てる形にする |
| remove_or_align | 削る、または退屈版・既存方式に寄せて根拠を継承させる |
| defer | 変更リスク未評価として特性化テストで挙動を固定し、「今回は保存」と範囲付きで判断する |

- `defer` は永久凍結ではない。`admitted_limit` に見直し条件を書く
- 説明の木を整えるためだけに関数・層・interfaceを増やさない。台帳は行範囲や論理ブロックを指せる。
  独立に変わる判断が一つの関数に絡み合っているなら切り出しは正当で、その理由は他の決定と同じ資格で台帳に載る
- 説明の都合で新しい抽象化を足したら本末転倒

## ダイヤル

粒度は三軸で指定する。混ぜない。

| 軸 | 値 | 意味 |
|---|---|---|
| scope | node_id / path / PR全体 | どの部分木を対象にするか |
| granularity | 構造 / 境界 / 手続き / 細部 | どの層まで確定させるか |
| strength | 資料確認 / テスト実行 / 計測 / 障害実験 | どれだけ強く検証するか |

「細部まで説明した」と「強く検証した」は別のこと。強さは granularity とは独立に指定する。

相手別の目安:

- 上司・PM: scope=PR全体, granularity=構造, 重視する問い=誰の要求
- コードレビュアー: scope=変更範囲, granularity=細部, 重視する問い=なぜこの形／どの前提
- 監査・セキュリティ: scope=影響領域, granularity=要求ごとに指定, strength=テスト実行以上

木は最初から全部作らない。構造層だけ作って、質問が落ちた節を掘る。
退屈版の生成も反例駆動も、gap の残る項目のscopeにだけ当てる。成果物全体には回さない。

## 出力

台帳は一つ。見せ方は相手ごとに三段階で生成する。

```
1. その場の回答            — 上位層（構造・境界）は台帳IDや参照なしで言える文。3文以内
2. 深掘りされたときの根拠  — grounding と evidence への参照
3. 認める限界と見直す条件  — admitted_limit の一覧
```

相手によって変えるのは長さと用語だけ。採用理由・未確認事項・認める限界の内容は変えない。
同じ台帳から生成する意味はそこにある。

三段目が弁明の強さを決める。詰める側が見つける弱点を先に自分で列挙してあれば、
その弱点は攻撃ではなく合意事項になる。

## 人間側の条件

口頭試問に合格させる道具ではない。必要なのは次の三つ。

- 上位層の決定は自分の言葉で話せる
- 下位層は、聞かれたら何を見れば答えられるか分かっている
- 専門外の前提は、誰の判断に依存しているか分かっている

署名には `scope / granularity / strength` を明記する。
粗い層が全部妥当でも葉が正しいとは限らない。定数の採用理由にも要求・計測・既存契約・規約・許容範囲が必要で、テストはその条件への適合を確認する証拠にとどまる。

## 終了条件

`gap` を持つ全項目が、次のどちらかになったら終わり。

- `resolution` 確定かつ `verification.status: done`
- `admitted_limit` に見直し条件付きで列挙されている

反例は無限に作れる。この条件が無いとループが終わらない。

## ワークフロー

```
1. 入力を受ける: 成果物、要求、規約の所在、影響領域一覧（無ければ初期一覧＋案件固有）、ダイヤル
2. 構造層の項目だけ作る（逸脱駆動＋影響駆動）
3. gap のある項目ごとに:
   質問 → 現在の回答と足りない根拠 → 対応候補 → 最小の対応を選ぶ → 再検証 → 記録
4. 上位層の resolution が確定したら、質問が落ちている下位層を掘る
5. 反例駆動を境界層に当てる。出た反例を項目にして 3 へ
6. 終了条件を確認する
7. 相手別に三段階出力を生成する。署名にダイヤル値を記す
```

各ループの記録は「何を変え、何と答えられるようになったか」。質問票ではなく、質問を解消する変更単位。

初版の構成要素は四つで足りる: この skill、参照付きの台帳、コード差分、短い説明資料。

## Deny

- 根拠を持たない項目に `final_answer` を書く（理由の発明）
- 「検討した結果」等、存在しない審議史を語る文
- 現在値を主張するテストを根拠に置く
- `freedom` のみを根拠とする値に唯一性・最適性を主張する
- 根拠が空または `freedom` のみの、関数・層・interfaceの新規追加
- 再生成の差分ゼロを完全性の証明として扱う
- 根拠と証拠を単一の強さ順で並べる
- 相手によって根拠・gap・認める限界の内容を変える
- 手続き・細部層に参照なしの即答を要求する
- `verification.status: pending` の項目を検証済みとして弁明する（`final_answer` は null。限界と見直し条件を明示した未確認事項の報告は可）
- 影響領域内で、退屈版一致を唯一の根拠にする
- 成果物を生成する（このskillは後工程。生成は別の工程）

## 例: 一項目の一周

```yaml
# 入口: 逸脱駆動。隣接サービスにこの中間層は無い
id: D-014
scope: {ref: "app/services/sync.rb:40-85", version: "b4c5d6e"}
layer: 境界
origin: deviation
question: なぜこの形
current_answer: テスト時の差し替えのために中間層を置いている
gap: 差し替えは現状どこからも利用されていない
resolution: {action: remove_or_align, reason: 独立した責務が確認できず、維持の利点が弱い}
verification:
  status: done
  plan: 公開契約と既存の利用経路の確認
  result: 呼び出し側2箇所、契約変更なし、spec緑
  artifact_version: b4c5d6e
grounding: [{existing_contract: "sync系サービスの呼び出し規約（直接呼び出し）"}]
evidence: [{test: "spec/services/sync_spec.rb"}]
final_answer: 隣接サービスと同じ直接呼び出しに揃えた。差し替えが必要になった時点で境界を切る
admitted_limit: {limit: 差し替え需要を予測していない, revisit_condition: モック以外の実装が2つ目に現れたとき}
```

三段階出力:

1. その場の回答: 「隣のサービスと同じ直接呼び出しに揃えました。差し替えが要る段階になったら境界を切ります。」
2. 深掘り: 呼び出し規約、`spec/services/sync_spec.rb`、呼び出し側2箇所
3. 限界: 二つ目の実装が現れたら見直す
