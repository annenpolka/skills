# 委譲と引き継ぎ

利用可能なモデル指定付きsubagent機能を使う。Lunaには `gpt-5.6-luna` と通常 `medium` のreasoningを指定する。ユーザーの指定を優先し、実行環境が対応する引数と呼出し条件に従う。

`collaboration.spawn_agent` が利用できる場合の形:

```json
{
  "task_name": "implement_change",
  "model": "gpt-5.6-luna",
  "reasoning_effort": "medium",
  "fork_turns": "none",
  "message": "下記の依頼について、調査・実装・確認を担当してください。…"
}
```

モデルを指定する場合は新しいcontextを使い、必要な情報を `message` に含める。親はworkerと重ならない必要作業を担当する。指定したモデルや委譲機能が使えない場合は制約を伝え、利用可能な経路で進める。

## 依頼書

```text
依頼: <ユーザーが求める変更と重要な条件>
作業場所: <絶対path>
制約: <repo指示の場所、編集範囲、維持する既存変更>
入口: <既知の関連path。未確認の部分は担当者が探索する>
完成条件: <利用者から見える動作、互換性、既知の検証コマンド>

担当範囲の調査・実装・確認を進めてください。
追加の担当者が必要になった場合は親へ伝えてください。
同じ失敗が局所修正後も続く場合は、試したこと、証拠、
残った判断を返してください。
返答は変更ファイル、動作、確認コマンドと結果、未解決点を短く。
```

複数workerを使う場合は、それぞれの所有ファイルや変更境界を明記する。親はユーザーの要件を保持し、実装方法の選択を担当者に任せる。

## 再開と昇格

局所修正は同じagent IDへ `followup_task` で返す。

```text
<コマンド> が <失敗の要点> で失敗しました。<ログpathまたは短い抜粋>。
現在の差分を保ち、この不一致を修正して関連する確認を実行してください。
```

Astraへの引き継ぎには、元の依頼と制約、候補の場所、調査済みの事実、失敗の証拠、残る問いを含める。親がAstraならその問いを親で処理する。助言専任の担当者には、編集を行わず判断と根拠を返すよう指定する。

実行中はagent通知・waitで完了を待ち、返された結果と候補の場所を次の処理に使う。
