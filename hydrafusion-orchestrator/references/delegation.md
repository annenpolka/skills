# 実際の委譲

利用できるnative subagent機能を優先する。tool schemaにmodel指定があることを確認し、軽量workerには `gpt-5.6-luna` を明示する。reasoningは通常 `medium`。ユーザーの指定があればそれに従う。対応していない引数を作らず、明示指定が拒否されたモデルを別モデルに黙って置換しない。

このCodex環境の `collaboration.spawn_agent` では、短い依頼書を `message` に入れ、`fork_turns: "none"` とモデル指定を使える。全履歴forkにmodel overrideを併用しない。親自身が必要情報を依頼書に移す。会話全体、評価レポート、無関係な技能一覧の再送は不要。

子を呼べるのは、親側に独立して進められる必要作業がある場合。親は成果の受入条件や統合先の状態など、workerと重ならない部分を確認する。委譲のために仕事を捏造しない。利用中のruntimeが直列委譲に対応しないときは、その制約に従って直接進める。

呼出しの形（値は実際の依頼と作業場所から作る）:

```json
{
  "task_name": "implement_change",
  "model": "gpt-5.6-luna",
  "reasoning_effort": "medium",
  "fork_turns": "none",
  "message": "下記の依頼を、必要な調査・実装・確認まで担当してください。…"
}
```

## 最初の依頼書

```text
依頼: <ユーザーが求める変更。重要な条件は原文を保持>
作業場所: <絶対path>
守る条件: <repo指示の場所、編集範囲、既存変更で保つ部分>
入口: <既知の関連pathだけ。未知なら必要箇所を探索してよい>
完成条件: <利用者から見える動作、互換性、必要な検証コマンド>

関連コードの調査から実装・確認まで進めてください。
別workerへの再委譲や、独立した比較候補の作成は不要です。
親との共有ファイルを同時編集しないでください。
具体的な不具合は続きから修正し、同じ失敗が続くときは、
試したことと証拠、残った判断を返してください。
返答は変更ファイル、動作、確認コマンドと結果、未解決点を短く。
```

repo指示と要求は省略してよい文脈ではない。一方、親が推測した解法を正解として押し付けない。複数workerを使う場合は、それぞれの所有ファイルや変更境界を依頼書に記す。

## 差分だけで続ける

同じLunaで直すときは、新しい子や全履歴forkを作らず、実際のagent IDへ `followup_task` を送る。例:

```text
<コマンド> が <失敗の要点> で失敗しました。<ログpathまたは短い抜粋>。
現在の差分を保ち、この不一致を修正して関連する確認を実行してください。
```

Astraが必要なら、元の依頼と制約、候補の場所、調査済みの事実、失敗の証拠、残る問いを渡す。親がAstraならその問いを親で処理する。助言専任なら「この判断と根拠を返し、ファイルは編集しない」と指定する。共有filesystemではこれは担当範囲の指示であり、OSの読取専用制約を作るものではない。

待機にはagent通知・waitを使う。待機が返っただけで同じ仕事を再起動しない。モデル指定付きnative委譲がなければ、既存の設定済み実行経路がある場合だけ利用する。効率化の依頼を、新しいrunnerを構築する仕事に変えない。

モデルを役割に割り当てる一般的な設定は [公式Subagents文書](https://learn.chatgpt.com/docs/agent-configuration/subagents) を参照。ここでの呼出し例はこの環境のtool schemaに基づくもので、全環境共通のAPIとは扱わない。
