# HydraFusion Orchestrator

依頼された修正・機能追加・調査を完成させながら、Codexの購読枠・クレジット消費を抑える。軽量側は `gpt-5.6-luna`、難しい判断の支援側は `gpt-6-astra`。ユーザーが今回指定したモデル・利用制限を優先する。時間短縮より、重複した推論と不要なモデル呼出しを減らす。

## まず作業を渡す

親はユーザーの依頼、適用されるrepo指示、作業中の変更、対象のおおまかな入口を確認する。実装方針を解き切る前にLunaへ渡し、詳細調査・実装・必要な確認まで任せる。委譲を準備するための全体調査や、依頼文の長い仕様書への書き換えをしない。

- 既に答えが分かり、その場で短く完了する編集は親が直接行う。委譲の準備の方が大きい場合に子を増やさない。
- 通常はLuna一人がまとまった作業を担当する。今の実行役がLunaならそのまま進め、同じ仕事の子を作らない。
- 設計上の衝突や難しいアルゴリズムが入口で明らかなら、その判断だけを先にAstraで解き、実装をLunaへ渡す。親がAstraなら親自身が担当し、もう一人のAstraを起動しない。
- 親はLunaと同じ箇所を並行して調査・実装しない。独立した必要作業だけを進める。並列化は仕事が明確に分かれ、重複した文脈や統合の負担に見合う場合に使う。

渡すのは依頼、守る制約、作業場所、関連する入口、完成時に確認する振る舞い。未知の箇所は未知のまま渡して調査を任せる。既知の検証コマンドがあれば添える。呼出しと短い依頼書は [delegation.md](references/delegation.md) を使う。

## 進行中に使う経路

| 状況 | 行動 |
| --- | --- |
| Lunaが成果物と必要な確認を揃えた | 親が差分と証拠を確認して完成させる |
| 原因の明確な局所的な不具合が残った | 同じLunaへ失敗箇所だけ返し、続きから直す |
| 同じ失敗が局所修正後も残る、または具体的な設計判断で詰まった | 調査済みの事実・差分・失敗・未解決の問いだけをAstraへ渡す |
| 権限・依存環境・サービス停止で実行できない | 環境側の問題を処理する。モデル交代で解決しようとしない |
| ユーザーの選好が必要で仕様を決められない | 必要な一点をユーザーに確認し、独立した作業を進める |

Astraには、既存の成果を引き継いで未解決部分を解くよう求める。局所的な助言で済めば元のLunaに返す。Astraがすぐ修正を完了できるなら、そのまま仕上げて往復を増やさない。全体を新規に解き直す並列候補や、同じ失敗の盲目的な再試行を作らない。昇格は通常一度とし、その後も新しい根拠なしにモデル間を往復しない。

独立criticは常設しない。ユーザーがreviewを求めたとき、または確認後も残る具体的な懸念を別視点で判断する必要があるときだけ、その論点に絞って使う。「念のため」全件をAstraで再審査しない。判断が変わる条件と根拠を返してもらい、問題がなければrevisionを増やさない。

## 品質を保って仕上げる

省くのは重複作業。依頼された振る舞い、互換性、repo必須チェックは維持する。既存テストの成功だけで新しい要求を満たしたことにせず、変更した動作を確認する。小さな可逆編集に試験基盤を新設しない。

親は実際の差分と未追跡ファイル、要件への対応、実行した確認の結果を読む。同じ最終状態に対する利用可能な実行証拠が十分なら、全調査・全テストを繰り返さない。証拠が自己申告だけ、検証後に変更がある、懸念が残る場合は、その確認を実行する。repoや委譲先skillが求める独立検証は実施する。

通常は対象checkoutを一人のwriterで編集する。親は同じファイルを同時に変更しない。既存のユーザー変更や同時作業との衝突がある場合は別worktree等で分け、成果を取り込んで確認する。全作業に使い捨て環境やDockerを作る必要はない。

最終回答は成果物、確認結果、残る問題を中心にする。経路は「Lunaで完了」「Luna → Astraの設計助言 → Lunaで完了」程度に短く示す。取得できたusageは使ってよいが、計測のために作業を止めない。未測定の節約率や、料金不明のモデルを無料とする主張はしない。

## 条件付きの経路

- OpenCodeの利用を指定された場合だけ [opencode-work.md](references/opencode-work.md) を読む。過去に試した期限付きDeepSeekモデルを、以後の既定値へ固定しない。
- このskill自体の改善を求められたら、実際の委譲で増えた往復・二重調査・不要な昇格をもとに指示を直す。比較測定を行う `autoresearch-loop` は開発時の道具であり、通常のタスク実行にbenchmark、料金表調査、実験台帳を要求しない。

このskillは実行役への指示であり、現在の親モデルそのものを自動変更する設定ではない。利用可能なモデル指定付き委譲を使い、対応していない環境ではその制約を短く伝えて、可能な経路で依頼を進める。
