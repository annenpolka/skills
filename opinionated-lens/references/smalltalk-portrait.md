# 全員がそこにいる言語

> 目標品質の参照。散文出力のベンチマーク。
> thinkingで設計した骨格が出力に溶けている例。

## thinking（出力には含まれない設計骨格）

- **宣言:** Smalltalkの閉世界には、開世界が代替できていない性質がある
- **賭け金:** 観察-変更距離ゼロは閉世界でしか成立しない（反証可能）
- **着地:** 「代替できたと確認した人間もいない」（問いとして開く）
- **レンズ:** 閉世界/開世界。観察-変更距離という軸
- **Generous Knife核心原理:** Smalltalkの濃密さ（長所）こそが外界との断絶の条件（攻撃の前提）
- **再認:** 「edit-build-runのサイクル」「console.logと書くとき」——読者が体験した場面
- **命名:** 「観察-変更距離」「即時可観測性」「閉世界/開世界」
- **Load-bearing:** 「部屋」の像が全編を貫通。除去すると全段落の前提が崩壊

## 出力（読者が見るもの）

```smalltalk
Transcript show: 'hello'.
```

Smalltalkのコードを初めて読む人のために最低限だけ言うと、これは`Transcript`というオブジェクトに`show:`というメッセージを送っている。ドットは文の終わり。それだけ。

ただし、この一文が成立するためには前提がある。`Transcript`がすでにどこかに存在していなければならない。ファイルの中にではない。今、動いているシステムの中に。Smalltalkの実行環境は「イメージ」と呼ばれる一つの生きたメモリ空間で、全てのオブジェクトがその中に同居している。`Transcript`はその部屋の住人の一人であって、あなたのコードはその住人に声をかけている。

現代の開発者が`console.log`と書くとき、consoleがどこにいるかなんて考えない。それはAPIであり、関数であり、呼べば動く機能だ。Smalltalkの`Transcript show:`はそうじゃない。あなたと`Transcript`は同じ空間にいて、声が届く距離にいる。

## 全員が同じ部屋にいるとき何が起こるか

Smalltalkの開発では、エディタで.rbを開いてターミナルで`ruby`を叩く——あの edit-build-run のサイクルとはまったく別の感覚になる。あなたはイメージの中にいて、オブジェクトたちと一緒にいて、Inspectorで任意の住人の中身を覗き、Workspaceでその場でコードを実行して結果を見る。

これはREPLとは違う。irbは窓の外から命令を投げ込む装置。Smalltalkのイメージはあなたが中にいる。隣にいるオブジェクトの肩を叩いて、「中身見せて」と頼むと見せてくれる。その場で振る舞いを書き換えると、次の瞬間からシステム全体がその変更を反映している。イメージの保存はシステム全体のスナップショットであって、ファイルの保存とは意味が違う。

ここで起きていることを設計語彙に落とすと、二つの特性になる。一つは即時可観測性——任意のオブジェクトの内部状態を、実行を止めずに、外部ツールを経由せずに覗ける。Inspectorはデバッガではない。デバッガは「止めて覗く」、Inspectorは「動いたまま隣に座って見る」。もう一つは観察-変更距離のゼロ化——見たものをその場で書き換え、変わった結果が即座にシステム全体に伝播する。この二つは、コードを書く空間とコードが走る空間が同一であるときにだけ成立する。

## 知らないメッセージにも返事がある

```smalltalk
Object subclass: #Ghost
  instanceVariableNames: 'memory'.

Ghost >> doesNotUnderstand: aMessage
  ^ 'I forgot how to ', aMessage selector
```

`Ghost new fly`と送ると、`'I forgot how to fly'`が返る。`doesNotUnderstand:`は未知のメッセージに対するフックで、Rubyの`method_missing`の直系の先祖にあたる。

これがエラーハンドラではなく**応答**として設計されている点に、閉世界の性格が出ている。全員が同じ部屋にいるなら、「知らない」は会話の終わりではなく会話の一形態になる。門前払いは閉世界では起こりえない——相手はそこにいるのだから。「わからない」も立派な返事であって、無視や拒否とは違う。

Goのコンパイルエラーは閉世界を前提としていない。ソースファイルは分散していて、コンパイラは外部の審判として振る舞う。「その型にそのメソッドはない」は、同じ部屋にいる相手の返事ではなく、入場を拒否する門番の判定。この差は構文の差ではなく、世界モデルの差だ。

## become: ——同じ部屋にいることの暴力

```smalltalk
a := 'hello'.
b := a.
a become: 'world'.
Transcript show: b.  "=> 'world'"
```

`become:`はオブジェクトの同一性そのものを別のオブジェクトに置き換える。ポインタの差し替えではない。`'hello'`が存在していた場所に`'world'`が来る。`a`も`b`も、システム中のあらゆる参照が、新しいオブジェクトを指すようになる。

普通の言語で`a = "world"`と書いたら、`a`という矢印が別の場所を指すだけで、`b`は元の`"hello"`に触れたまま。`become:`はそうじゃない。矢印の先にある実体そのものが入れ替わる。SmalltalkのVMがオブジェクトテーブルという間接参照の層を持っていて、全ての参照がこのテーブルを経由するからこそ可能な操作。

`become:`は観察-変更距離ゼロの極限形であり、同時に閉世界でなければ成立しない機構でもある。全てのオブジェクトが一つのイメージの中にいて、全ての参照がVMの管理下にあるから、「全参照先の一括差し替え」ができる。分散環境では原理的に不可能だ。別のプロセスが同じオブジェクトを参照していたら？別のマシンが？

そしてこの全能性は危険だった。あなたが握っている`b`が、あなたの知らないところで別の存在に変わる。`become:`はSmalltalk-80に存在したが、実際のアプリケーションコードで使われることは稀だった。同じ部屋にいるということは、誰かがあなたの持ち物を書き換えられるということでもある。閉世界の濃密さは親密さと暴力の両方を含んでいる。

## 部屋の外

Smalltalkの閉世界が最も明確に限界を見せたのは、Unixとの接触面だった。

Unixは開世界の設計。小さなプログラムがテキストストリームをパイプで流し合い、各プログラムは互いの内部を知らない。ファイルシステムという共有の棚があって、そこに置いたものを別のプログラムが拾う。誰も同じ部屋にいる必要はない。

Smalltalkのイメージはこの棚に載らなかった。イメージはバイナリの塊で、gitで差分を取れない。シェルスクリプトから中のオブジェクトに触れない。他の言語で書いたプログラムと協調するには、イメージの壁に穴を開ける必要があった。

結果としてSmalltalkはニッチに留まった。原因はもちろんこれだけではない——性能、普及経路、教育コスト、採用市場、既存資産との接続、どれも効いている。だが最も構造的な要因は、閉世界が開世界と接続するための設計を持っていなかったことだと思う。内側の濃密さが高すぎて、外側とのプロトコルを持たなかった。

Rubyはこの歴史から巧妙に学んでいる。message passingの思想を盗み、`method_missing`を持ち込み、オブジェクトが会話する感覚を残しつつ、ファイルシステムの住人として振る舞える形にパッケージし直した。Smalltalkの部屋の空気を、Unixの道端で吸えるようにした。密室の思想を露天に持ち出したとき、濃度は下がる。でも息ができるようになる。

## 開世界が代替できていないもの

```go
ch := make(chan string)
go func() { ch <- "who sent this?" }()
msg := <-ch
```

Goのgoroutineは名前を持たない。channelも、変数名というラベルを除けば自己同定の手段がない。Smalltalkの全てのオブジェクトは`yourself`というメッセージに答えられた。自分が誰であるかを常に知っていた。goroutineは自分が誰かを知らないし、知る必要がない。

これはCSPの設計思想の忠実な実装で、GoはSmalltalkの逆を正確にやっている。同じ部屋にいないことを前提とし、匿名のチャネルだけで協調する。結合度は下がり、合成可能性は上がり、10万のgoroutineがひとつのプロセスの中で動ける。

現代のソフトウェアはどこまでも開世界に向かっている。マイクロサービス、コンテナ、サーバレス、イベント駆動。それは正しい。スケールする。デプロイできる。壊れても他を巻き込まない。その代わり、観察にはログ基盤とメトリクス収集と分散トレーシングが要る。変更にはビルドとデプロイパイプラインが要る。観察と変更の間に組織と時間が挟まる。Smalltalkではゼロだったその距離に、現代のインフラの大半が住んでいる。

閉世界を知らない世代が増えていったとき、「全員がそこにいる」濃密さの記憶は設計語彙から消える。消えたものは要求されない。要求されないものは作られない。Smalltalkの部屋はもう誰も住んでいないが、あの部屋で可能だったことの全てを、開世界が代替できたと確認した人間もいない。
