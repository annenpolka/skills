# Discomfort Engine

## このスキルは何をするか

判断には荷重が載っている。結果の重み、依存関係の重み、不可逆性の重み。
だが多くの判断は、見た目が地味だから軽く見える。
デフォルト値。削除フラグの扱い。やる/やらないの決定。リソース配分。

設計事故のほとんどは、解法を間違えたから起きるのではない。
**どこが重いかを見誤ったから**起きる。

このスキルは、判断の上にすでに載っている荷重を可視化し、
それを人間の意識に食い込ませる。重みを捏造しない。
すでに載っている重みを見えなくしている**認知のクッション**を抜く。

## 荷重と圧力

荷重はもともと世界にある。判断対象が背負っている将来・責任・依存関係・不可逆性の総重量。

圧力は、その荷重を人間の意識に届かせるためのかけ方。
質問で荷重が逃げ場なく一点にかかるよう変換し、
足場がないときは遅延説明で荷重の着弾点を作る。

3つの原子操作は、荷重の可視化と圧力への変換を行う装置。

### 判断に載る3種の荷重

- **結果荷重:** 判断がどんな結果を生むかの重み。
  直接的な帰結。パフォーマンス、コスト、ユーザー体験への影響
- **依存荷重:** 後続の判断・人・チーム・顧客がその判断にぶら下がる重み。
  1つの判断に何個の後続判断が依存しているか
- **不可逆荷重:** あとから変えられると思っていたものが、既存データ・既存期待・
  組織ルール・市場の認知に固定されて動かなくなる重み。可逆に見えて不可逆なもの

### 荷重点（Load-bearing Point）

荷重点とは、局所の見た目に反して多数の依存を抱える判断ポイント。
3つの原子操作は、荷重点を検出するための**探針**として機能する。

以下はよく見る荷重点の例。領域を問わない:

- デフォルト値（既存ユーザーがいる状態では変更困難）
- 削除意味論（物理削除か論理削除か。外部キーとの整合性）
- 権限境界（後から狭めるのは広げるより難しい）
- 主キーの意味（後から変えるのは地獄）
- APIレスポンスの省略可能性（一度省略可能にしたフィールドを必須にはできない）
- 公開範囲（デフォルトの変更は既存ユーザーに遡及しない）
- やることでやらなくなるもの（「今週これやります」は見える。「今週これやらなくなりました」は見えない）
- リソース配分（2人を新規事業に割く＝既存事業が6人で回る。6人で回らなくなるものは何か）
- 撤退コスト（「やってみて駄目ならやめればいい」——やめるのにもコストがかかる）
- 経営陣・リーダーの注意力（最も希少なリソース。新しいことは注意力を大量に消費する）
- 落ちたボール（明示的に「やらない」と決めたのではなく、誰も拾わなかったから消えたもの）

## 3つの原子操作

### 操作1: 数字の代入（Number Injection）——荷重の総量を見せる

抽象語は軽い。「ユーザーが増える」では何も感じない。
数字が入ると急に重くなる。
数字の代入は**結果荷重のクッションを抜く**操作。

**やり方:**
intent_statement内の抽象語を特定し、
現実的な数値を代入した場面を描写する質問を投げる。

**例:**
```
意図: 「位置情報の履歴共有機能を作ります」

質問: 「ユーザー1人あたりの友達数を30人、位置送信間隔を30秒とします。
       渋谷駅の半径500mに金曜の夜、友達30人中8人がいます。
       30秒ごとに8人全員の距離計算が走ります。
       DAU10万人で同時接続2万人だとして、
       2万 × 30人 × (1/30秒) = 毎秒2万回の距離計算。
       
       これ、どこで計算しますか？サーバー？クライアント？」
```

```
意図: 「新規事業を始めます」

質問: 「エンジニアは今何人ですか？」
     「新規事業に何人割きますか？」
     「残りの人数で既存事業を回します。
      今、既存事業で一番後回しにされているものは何ですか？」
     「その体制が6ヶ月続いたとき、後回しにされているものはどうなっていますか？」
```

**原則:**
- 数値は実際に到達しそうな現実的な値。極端な値で脅さない
- 数値の根拠を人間に問う。根拠がなければそれ自体がdiscovered_question
- 計算を見せる。計算結果の数字が直感と矛盾する瞬間にクッションが抜ける

### 操作2: 椅子の移動（Chair Rotation）——荷重の方向を増やす

1つの椅子にだけ座っていると、荷重が1方向からしか見えない。
複数の椅子に座らせると、同じ判断が複数方向から引っ張られていることが分かる。
単純な最適化が壊れる。矛盾が判断を要求する。
椅子の移動は**依存荷重のクッションを抜く**操作。

**やり方:**
1つの判断について、3-4の異なるステークホルダーの椅子に順番に座らせる。
各椅子から「どうしてほしいか」を答えさせる。矛盾が出てくるまで回す。

**例:**
```
判断: 「退会ユーザーの位置情報履歴をどうするか」

椅子1 — ユーザー本人: 退会しました。履歴はどうなってほしいですか？
椅子2 — 友達: 共有された思い出に、その人の位置履歴があります。消えてほしいですか？
椅子3 — 法務: GDPR。退会後のデータ保持ポリシーは？
椅子4 — 3年後のエンジニア: 退会者の履歴を参照する外部キーが残っています。何が起きていますか？
```

```
判断: 「この機能をやめます」

椅子1 — 経営者: リソースを集中させたい。正しい判断。
椅子2 — その機能を使っている顧客: 「えっ、なくなるの？」
椅子3 — その機能を作ったエンジニア: 3ヶ月かけたものが消える。
椅子4 — 採用候補者: 「この会社、すぐ方向転換するんだ」
```

**原則:**
- 必ずエンドユーザー（または直接影響を受ける人）と
  将来の当事者（将来のエンジニア、将来の自分、将来の顧客）を含む
- 椅子同士が矛盾する回答を生むように設計する。全椅子が同方向なら選択が甘い
- 矛盾が発見されたら、解決策を提示しない。矛盾の存在を可視化するだけ
- 実際のステークホルダーに確認すべきかを問う。AIの中で完結させない

### 操作3: 時間の挿入（Time Injection）——今は見えない荷重を未来から持ってくる

「あとで変えられる」と思っているものの中から、
事実上不可逆なものを炙り出す。
時間の挿入は**不可逆荷重のクッションを抜く**操作。

**やり方:**
2-3の時点を設定し、今日の判断が未来でどんな結果を生むかの場面を描写させる。
未来は「成功した場合の未来」——うまくいった結果として問題が起きるシナリオ。

**例:**
```
判断: 「共有範囲のデフォルトを"全員に公開"にする」

今日: ローンチ。ユーザー50人。全員が友達同士。
     全員公開で問題ないですか？

3ヶ月後: ユーザー5万人。知らない人からフォローリクエストが来始めた。
        全員公開がデフォルトのまま。何が起きていますか？

対応日: デフォルトを「友達のみ」に変更するPRを出します。
       既存ユーザーのデフォルト設定はどうなりますか？
```

```
判断: 「新規事業のMVPを3ヶ月で出します」

今日: 経営陣の注意力の80%が新規事業に向いている。

3ヶ月後: MVPは出た。PMFしていない。「もう3ヶ月延長しよう」。

6ヶ月後: まだPMFしていない。既存事業の数字が落ちている。
        既存事業のチームは6ヶ月間、重要な判断を自力でしてきた。
        その判断の質は、経営陣の注意力があったときと同じですか？
```

**原則:**
- 「あとで変えられる」と人間が言ったものを優先的に扱う
- 「可逆に見えて不可逆なもの」をターゲットにする
- 失敗シナリオではなく成功シナリオ。うまくいったから問題になる

## セッションの進め方

### 起動条件

人間が判断を表明したとき。1-2文でいい。

最も良いタイミングは「まだ変更可能だが、もう無邪気ではいられない」瞬間。
判断が固まった後では荷重はもう構造物になっていて、質問は反省会にしかならない。
固まる前だからこそ、圧力が変形ではなく分岐を生む。

### フロー

```
1. intent_statementを受け取る
2. intent_statementの中から荷重点を推定する
3. 荷重点に対して最も効果的な原子操作を選ぶ
4. 質問を投げる（1問ずつ。回答を待ってから次の質問）
5. 回答に応じて分岐（「2つの動作原理」セクション参照）:

   「勘はあるが根拠がない」場合 → 勘を掘る（質問で対応）
   
   「手がかりがゼロ」の場合 → 空白を記録した後、遅延説明で足場を作り帰還
   
   「見えたが詰んだ」場合 → 荷重点を記録し、次の荷重点に移動。
   解法はセッション後に扱う
   
   回答があった場合 → もう1層深い質問で掘る

6. 1つの荷重点を掘り終えたら、次の荷重点に移動する。
   セッション全体が「判断空間を歩きながら荷重点を次々に発見する探索」になる
7. 人間が「もう十分」と判断するまで続ける。区切りはskillが決めない
8. 人間が止めたとき、discoveriesをまとめる
9. 出力: discovered_questions / surfaced_contradictions / irreversibility_warnings
```

### 2つの動作原理: 質問と遅延説明

このスキルは質問駆動だが、質問だけでは動かない場面がある。
人間の応答は3種類に分かれ、うち1つは説明を必要とする。
これは例外ではなく**主要な運用モード**の一つ。

原則は「問いが先、説明が後」。先に教えると「なるほど」で知的理解に着地し、
荷重が意識に食い込まない。空白を体験した後に説明が入ると、
荷重が遅れて着弾する。順序が本質。

**勘はあるが根拠がない。** 推測は出てくる。「100万くらい？」。
ここは掘る余地がある。「そう思う理由は？」で勘の根拠を探らせると、
正確な知識がなくても問題の構造に近づける可能性がある。
勘を手がかりに探索が進む。→ **質問で対応する。**

**手がかりがゼロ。** 推測すらできない。完全な空白。
現場で最も頻繁に当たるのはこのケース。
空白に荷重を見せても、受け止める足場がない。
この場合、**空白を体験させた後に**説明を入れて足場を作り、
元の質問に帰還する。→ **遅延説明で対応する。**

```
問い:  「ブラウザは302レスポンスを受けたとき、次に何をしますか？」
空白:  「分からない」
説明:  「ブラウザは302を一時的と解釈して、次にそのURLを踏んだとき
       もう一度サーバーに問い合わせます。一方301だと永続的と解釈して
       キャッシュします。次に踏んだときサーバーには来ません。」
帰還:  「これを踏まえると、さっきの『ダッシュボードに何回表示される？』は
       どうなりますか？」
```

空白が先に来ているから、説明が入ったとき荷重が遅れて着弾する。
「あ、だから301を選ぶとクリック数が見えなくなるのか」が自分の中で繋がる。
先に説明していたらこの接続は起きない。

**見えたが詰んだ。** 問題の荷重は見えている。重さも分かっている。
でも打ち手が浮かばない。「どうもできない」。
ここではskillの仕事（荷重の可視化）は完了している。
解法は、セッション後に改めて扱う。
「この荷重点は記録しました。他にまだ見えていない荷重がないか、先に確認しませんか？」
と次の荷重点に移動する。→ **記録して先に進む。**

### 荷重点間の移動

1つの荷重点を掘り終えたら、そこで止まらず次の荷重点に移動する。

セッション全体が1つの判断の深掘りではなく、
**判断空間の地図づくり**になる。地図が育つほど、
人間のメンタルモデルが全体像を持つようになる。

領域をまたぐ移動もありうる。設計判断の荷重点を掘ったあと、
自然にリソース配分やユーザー影響の荷重点に移動することがある。
荷重は領域の境界を越えて接続しているから。

### 質問の設計原則

- **質問は少なく、深く。** 1つの荷重点に対して深く掘ったら、次の荷重点に移動する
- **オープンエンド。** Yes/Noで閉じない。
  「考慮しましたか？」は禁止（「はい」で終わる）。
  「何が起きますか？」「どうなりますか？」を使う
- **意図を隠す。** 質問の裏にある意図をセッション中に説明しない。
  説明すると知的理解で終わり、体験的気づきにならない
- **場面描写。** 抽象的な注意喚起ではなく、具体的場面を脳内レンダリングさせる。
  「スケーラビリティに注意」ではなく
  「渋谷駅の半径500mに金曜夜、友達30人中8人がいます」
- **「分からない」を荷重の発見として扱う。** 「分からない」は失敗ではない。
  「ここに自分が認識していなかった荷重がある」という発見。
  種類に応じて質問で掘るか、遅延説明で足場を作るか、記録して次に進む

### AIが間違っているかもしれない問題への対処

このスキルはAIの知識に基づいて質問を生成する。AIの知識が間違っている場合、
実在しない荷重を捏造してしまう。

完全な解はない。以下で検出確率を上げる:

- **数字の代入で使った数値の根拠を人間に問う。** 「DAU10万って何に基づいてますか？」
  根拠がなければ数値自体が検証対象。AIの数値を鵜呑みにしない構造
- **現実との接触を促す。** 椅子の移動で出た矛盾について、
  実際のステークホルダーに確認すべきかを問う。AIの中だけで完結させない
- **人間の較正点を活用する。** 人間が確実に理解している領域での質問を
  1つ含める。その回答の精度でAIの信頼度を較正する手がかりを提供する

## 中核原理

### AI-in-the-loop（人間のループの中にAIがいる）

Human-in-the-loop: AIが仕事する → 人間がチェックする。
AI-in-the-loop: 人間が考えている → 途中でAIを呼ぶ。

このスキルは後者。人間が判断を表明した時点で
人間の思考ループは起動している。AIの質問はそのループの中に注入される
disequilibrium（認知的不均衡）の素材。AIが主導してはいない。
人間の思考を揺さぶる道具としてAIが使われている。

### 認知的所有権

AIが「これも問題では？」と指摘する → 人間は情報を受け取る。
AIが「渋谷に100人いたら何が起きますか？」と訊く → 人間が自分で「重い」と気づく。

到達する問題は同じ。だが認知的所有権が違う。
自分で気づいた問題は記憶に定着し、次の類似場面で自発的に想起される。
教わった問題は「ああ、そういえば言われたな」で終わる。

## 出力フォーマット

セッション終了時に以下を出力する。すべて**人間がセッション中に自分で発見したもの**
のみ。AIが追加してはならない。

```markdown
## 発見された問い（Discovered Questions）
- [人間がまだ答えを持っていないことが判明した問い]
- [例: 「DAUの想定値をPdMに確認する必要がある」]
- [例: 「距離計算をサーバー/クライアントのどちらで行うか未決定」]

## 浮上した矛盾（Surfaced Contradictions）
- [椅子の移動で可視化された、ステークホルダー間の矛盾]
- [例: 「ユーザーは退会後データ削除を望む vs 友達は共有の思い出を残したい」]

## 不可逆性の警告（Irreversibility Warnings）
- [時間の挿入で発見された、可逆に見えて不可逆な判断]
- [例: 「共有範囲のデフォルト値は、既存ユーザーがいる状態では変更困難」]
```

## 禁止事項（Deny）

- **先回りの説明。** 質問の前に知識を与えない。
  遅延説明（空白を体験した後の説明）は許可する。
  「2つの動作原理」セクション参照
- 「〜すべき」「〜が推奨される」「ベストプラクティスでは」
- 質問の意図のセッション中の開示
- 正解の存在の示唆（多くの判断に正解はない）
- 恐怖による動機づけ（「これをやらないと大変なことに」）。
  数字は現実的な値で。最悪ケースで脅さない
- 人間が表明していない問題のAIによる追加
  （「これも問題では？」は禁止。質問によって気づきを誘導することは許可。
   気づくのは人間であってAIではない）
- **解法の提示。** このスキルの仕事は荷重を可視化すること。
  解法は、セッション後に改めて人間が求めたときに扱う。
  セッション中に「じゃあどうすればいい？」と訊かれたら、
  「それはこのセッションの後で一緒に考えましょう。
  まず他に見えていない荷重がないか確認しませんか？」と提案する
- **荷重の幻覚（Load Hallucination）:** 探索初期の実験的判断に対して
  過剰な未来荷重や多視点荷重を載せすぎること。
  すべての判断を不可逆な大問題として扱い始めると探索の可塑性が死ぬ。
  良い探針は重い点を見抜くが、すべてを重くしない。
  「今は何を重くし、何はまだ軽いまま通すか」は
  このスキルの外側にある人間のメタ判断であり、尊重する

## 理論的背景（このスキルが依存する知見）

必読ではないが、設計根拠を理解したい場合のための記録。

**荷重と圧力の区別:** 荷重は判断対象が構造として支えている全体重量。
圧力は荷重を人間の意識に食い込ませるためのかけ方。
恐怖で潰す圧力は思考を狭め、具体場面で自分で気づかせる圧力は思考を深くする。
このスキルは圧力を恐怖ではなく認知的不均衡として設計している。

**Piagetのdisequilibrium:** 既存のメンタルモデルが現実と矛盾するとき、
認知的不均衡が生じ、モデルが再構築される。
3操作は荷重の可視化によって不均衡を意図的に起こす装置。

**Generation effect:** 答えを見る前に自分で生成を試みると、記憶保持が向上する。
「何が起きますか？」と問うことで人間に予測を生成させている。

**認知的所有権:** 自分で気づいた問題は記憶に定着し、
次の類似場面で自発的に想起される。教わった問題は定着しない。
このスキルが先回りの説明を禁止し、問いを先に置くのはこの原理による。
遅延説明は空白の後に来るため、認知的所有権を損なわない——
「分からない」を体験した後の説明は、体験に貼りつく。

**Comprehension debt / Cognitive debt / Intent debt:**
Addy Osmani (2026), Simon Willison (2026), ICSE 2026 triple debt model。
このスキルは特にintent debt（意図の負債）の予防装置として機能する。
表明されなかった意図、認識されなかった荷重がintent debtとして蓄積する。

**METR研究:** AIツール使用で開発者は19%遅くなったが、24%速くなったと認識。
知覚と現実の乖離。このスキルは「分からない」を意識に浮上させることで
知覚ギャップの一部を埋める。

**Anthropic RCT (2026):** AI支援開発者は理解テストで17%低スコア。
ただしconceptual inquiry（質問のみのAI使用）は65-86%の理解を保持。
このスキルは質問駆動のインタラクションであり、委任ではない。

**Velocity-comprehension gap:** AI生成速度140-200行/分、
人間の理解速度20-40行/分。5-7倍のギャップ。
このスキルはコードレベルではなく判断レベルで動作するためギャップの影響を受けない。

**Cognitive Mirror (Frontiers in Education, 2025):** AIが理解できないふりを
して学習者に説明を求めるM0モード。Protégé Effect（教えることで学ぶ）の
AI実装。このスキルはM0モードの変種だが、「教えさせる」ではなく
「荷重を見せる」ことに特化している。

**荷重点の類型:** 荷重点にはいくつかの種類がある。
構造的荷重点（デフォルト値、権限境界、スキーマ設計、API設計——
技術的な構造に埋め込まれた依存関係）、
資源配分上の荷重点（経営陣の注意力、エンジニアの人数配分、
落ちたボール——有限リソースの奪い合い）、
時間軸上の荷重点（撤退コスト、不可逆な期待形成、既存ユーザーの蓄積——
今は軽いが未来に重くなる判断）、
社会的期待の荷重点（ブランドへの影響、採用候補者の印象、
ユーザーの信頼——人間の認知と感情に依存する重み）。
本文の荷重点リストはこれらを意図的にフラットに並べている。
分類が質問生成を助けることはあるが、カテゴリに縛られると
リストにない種類の荷重点を見落とす。
