# Question Forge — 255問で目的に向かう探索Skill

Version: 0.1.0  
Date: 2026-09-18  
Status: 設計提案。Phase 0 runtimeを `scripts/qforge.py` に実装（2026-09-18）  
Working name: `question-forge` / `qforge`

> 大量の質問に答えることを目的にしない。大量の質問によって、設計・仮説・検証・次の行動を変える。

この文書は、Jevを用いて多数の型付き質問を評価する仕組みの新規設計である。掲載するCLI名、内部型、モジュール分割は提案であり、既存APIや実装済み機能ではない。付属JSONは架空の仕様を対象とした入力例で、Jevの回答や実測結果は含まない。有料API呼び出し、対象リポジトリへの変更、コミットは実施していない。

## 1. 結論

初版は **Skill主体＋極小の決定論的runtime** とする。主役は最初から255問を展開する `saturate-255`。段階的に質問を追加する `adaptive-255` は比較対象とし、最初から少数質問へ絞ることを前提にしない。

Skillが目的の読解、資料探索、仮説と質問の生成、追加調査、設計の再構成、文章化を担う。runtimeは入出力契約、送信するstateの制御、バッチング、API接続、予算計上、結果の保存を担う。Jevは局所的な意味判定を担う。テストや形式的な検証は、それを実行できる外部ツールが担う。

最終出力は255件のQ&Aではなく、根拠を追跡できる**判断・改訂案・検証計画・残した未決事項**である。255回答の一覧は、その出力を監査する台帳として保存する。

質問を小さくするが、探索範囲を小さくしない。既存案の検査だけでなく、新しい仮説、別の問題分解、制約の解釈、代替案を生む方向にも質問予算を使う。

## 2. 事実 — 現在のJevと参照実装

以下は2026-09-18に確認した資料の記述であり、この構想の実測ではない。

### 2.1 多数の質問は本来の利用パターン

TypeSafeの公式資料は、同一stateに対する複数の質問を一つのリクエストへまとめ、独立・並列に評価する使い方を説明している。条件によって不要になる質問も先に評価し、使う回答をコードで選ぶ `Speculative fan-out` を明示的に推奨する。[S1][S2]

ここでの「独立」は、質問同士が相互の回答を入力として参照しないという実行上の性質である。異なる質問の誤りが統計的に独立であることを意味しない。

### 2.2 255はAPIの質問数上限ではない

公式Choice資料の255は**一つのChoiceに与える選択肢の上限**である。質問数についてはPrimitives資料がトークン予算による制約を説明している。したがって、本設計の255は意図的に大きく設定した探索単位であり、APIの質問数上限を写したものではない。[S1][S3]

### 2.3 トークン制約は提供経路ごとに確認する

Models資料の `jev-1.13.0` の記載は、リクエスト全体が64k tokens、state＋最長の一問が32k tokens。一方、Primitivesの概説は約32,000 tokensの共有予算、Cloudflareのモデルページは32,000 tokensのcontext windowと記載している。概説と詳細、提供経路間に粒度の差がある。[S1][S4][S5]

新規runtimeでは、これらを一つの不変定数へ潰さない。provider profileに「どの経路の、いつ確認した、何を数える上限か」を保持する。境界のcontract testが終わるまでは保守的にパッキングし、directの64kをCloudflareにも適用しない。

### 2.4 出力型とconfidence

公式direct APIは `noul / choice / score` を使う。Noulはyesの確率を返す。ChoiceとScoreの `confidence` は確率分布から導く統計量であり、最大確率そのものと同一視しない。Scoreは2〜10個の記述的なレベルを使い、その位置と分布を返す。[S3][S6][S7]

参照した `gril-jev` はAI SDK経由の `boolean / choice / score` を使い、独自の `confidence` を最大確率として計算している。これは参照ランナーの定義であって、direct APIの定義ではない。[S9][S10]

### 2.5 数を増やしても残る制約

公式の既知問題には、数値計算、間接的な推論、無関係な内容が多いstate、敵対的な内容、質問間の構造的整合性、文字列生成に関する制約が挙げられている。正確な算術や証明をJevに移管しない。意味判定の結果にも原文・実行・検証へ戻る経路を残す。[S8]

### 2.6 引き継ぐ方針

既存のqlint構想で分けていた、静的契約検査と意味判定、falseと情報不足・対象外・障害、質問とstateの契約、宣言と実際の強制境界という区別は維持する。本設計はその上位の探索ワークフローであって、qlintの責務を目的関数や最終意思決定まで拡張するものではない。

## 3. 推測（示唆）— なぜこの構造にするか

### 3.1 255人の投票ではなく、255個の観測点

同じ主張の言い換えを多数作って同意を集めても、独立した証拠は増えない。一方、前提、例外、対象、時点、失敗条件、反例、代替案を変えた質問は、現在の問題の捉え方がどこで壊れるかを探れる。

したがって、中心に置くのは多数決ではなく**異なる条件によって判断を区別すること**である。255問は255票ではなく、目的に関係する空間に置く255個の観測点として扱う。

### 3.2 問いの出力先は「理解」だけでなく「行動」

各質問には、その答えによって何が変わり得るかを持たせる。設計案の採用・棄却だけでなく、追加取得する資料、書くテスト、生成する代替案、明文化する仕様、維持する未決事項も対象になる。

すべての質問に即時の実装変更を要求しない。未知の判断軸を見つける探索質問も認める。ただし「何の理解を広げ、目的へのどの経路を開くか」は記述する。

### 3.3 Jevを最後の採点者だけにしない

Feature Compiler内部でもJevを使える。原文に含まれる意味関係を分類する、候補となる規則の適用範囲を読む、テストがどの要求に関係するかを照合する、といった意味変換を行う。

これらは `model_interpretation` としてTyped IRへ入る。原文や実測と同じ証拠格にはしない。Compiler内部の意味判定と、最終的な候補評価は別のパスとして記録する。

### 3.4 単発の解答より、探索状態の変化を成果にする

一回の実行で最終解に到達しない場合でも、「根拠付きで一案を除外した」「重要な反例を実行で再現した」「未決を具体的な選択肢にした」「次の実験が決まった」なら進捗である。

質問数や高confidence回答数を進捗としない。目的に向けた判断・候補・検証状態がどう変わったかを記録する。

## 4. 入力と成果物

### 4.1 Goal Contract

入力の中心は質問リストではなくGoal Contractである。

```yaml
id: cache-update-design
objective: 更新成功後の古い読取りを防ぐ仕様を、実装と検証へ渡せる形にする
requested_artifacts:
  - design_delta
  - verification_plan
  - unresolved_decisions
success_conditions:
  - 成功応答の意味と読取り保証の適用範囲が記述される
  - 障害時の扱いが候補または明示的な未決として残る
  - 重要な要求に対応する検証方法が示される
hard_constraints:
  - 本番データや本番設定を変更しない
preferences:
  - 複雑さを抑える
  - ただし保証を黙って弱めない
sources:
  - versioned_spec
  - relevant_implementation
  - relevant_tests
authority:
  propose_design: true
  adopt_design: false
  run_registered_local_checks: false
execution:
  mode: saturate-255
  domain_probe_target: 255
  max_waves: 1
  paid_execution_authorized: false
```

これは入力例であり、ユーザーの実在するプロジェクトの要件ではない。未提供の数値SLOや規範を常識で補完しない。好みと必須条件を分ける。

### 4.2 Answer Contract

開始時に「最後に何を書くか」を固定する。仕様確定なら設計差分、障害調査なら仮説と識別実験、選定なら条件付きの比較と判断、実装依頼なら許可された変更と検証結果となる。

最終出力には、今回進んだこと、根拠、未決、次の最小行動、調査範囲と未探索範囲を含める。要求された成果物を大量の質問一覧で置き換えない。

### 4.3 Decision Card

各重要判断を次の形で残す。

```text
判断: 何を採る／何を保留するか
状態: 提案 / 委譲範囲で採用 / 人間が承認 / 棄却 / 未決
適用範囲: 対象・時点・条件・版
根拠: 原文・実測・検証への参照
モデルの寄与: どの質問が何を指摘したか
代替案: 何を残し、何を除外したか
反転条件: 何が分かればこの判断を変えるか
次の行動: 最小の追加調査・テスト・修正
```

Jevは説明文を生成しない。理由の文章はSkillによる根拠付きの再構成であり、Jevが語った理由として表示しない。AIが起草したADRを人間の承認済み決定として保存しない。

## 5. 全体アーキテクチャ

```text
Goal + sources + authority + budgets
                  |
                  v
Skill: evidence acquisition / candidate generation
                  |
                  v
Feature Compiler
  deterministic extraction
  + optional Jev semantic passes
  -> typed, provenance-linked working model
                  |
                  v
Question expansion + qlint-compatible screening
                  |
                  v
Logical wave: up to 255 domain probes
                  |
                  v
Runtime: safe projections / packing / provider / ledger
                  |
                  v
Raw answers -> normalized observations
                  |
                  v
Relation checking + decisive evidence/experiment selection
                  |
       +----------+------------------+
       |                             |
       v                             v
Further read/test/new hypothesis     Synthesis
       |                             |
       +-> new version / next wave   v
                              Requested artifact
```

`255 domain probes` は論理的なwaveであり、必ず一つのHTTPリクエストに詰めるという意味ではない。同じstateを安全に共有でき、トークン制約内なら一括する。異なる証拠境界を持つ質問は別packetにする。

### 5.1 Skillの責務

資料を読む、問題の分解を変える、質問を生成する、新しい仮説や案を生成する、回答を解釈する、必要な調査を選ぶ、成果物を書く。複雑な推論が必要な部分を「Jevしか答えてはいけない」と縛らない。

### 5.2 runtimeの責務

JSONの型・参照・版・予算・認可された送信範囲を検査し、providerへ問い合わせ、応答を検査して記録する。意味の正しさや設計の採否は決めない。

### 5.3 既存部品との境界

| 部品 | 担うこと | 担わないこと |
|---|---|---|
| Feature Compiler | 資料を型付きの意味表現へ変換する | 未確認の解釈を事実へ昇格する |
| qlint | 質問・state・bindingの契約と意味上の懸念を検査する | 最終目的への質問の有用性を万能に決める |
| specprobe | 仕様の具体的なシナリオ、空白、境界を探索する | 意図的に開かれた仕様を必ず一意化する |
| relation checker | claim↔evidence、spec↔behavior、requirement↔test等を照合する | 確率を受入判定や証明へ変換する |
| qforge | それらを目的へ向けて配置し、探索と成果物を統合する | Wardenの認可・停止・commit等を代行する |

既存部品を利用できない段階では、同じ責務を薄い契約で実現する。「連携済み」とは呼ばない。

## 6. 255問の作り方

### 6.1 質問より先に、判断点と仮説を作る

Goalから、候補案、重要な判断点、ユーザーから与えられた制約、観測できていること、未検証の仮定を抽出する。この段階の分解も仮説であり、後から変更できる。

次に、各判断点へ異なるprobe operatorを当てる。例えば対象を変える、時点をずらす、障害を挿入する、順序を交換する、成功の定義を分解する、例外を具体化する、代替案を比較する、といった操作である。

同じ内容の言い換えは通常のcoverageへ加算しない。言い換えの安定性を調べる場合に限り、同じclusterに属する感度試験として残す。

### 6.2 初回waveの配分例

以下は仕様・設計向けの初期値であり、最適な比率という主張ではない。業務や対象が異なれば再配分する。

| 質問群 | 数 | 目的 |
|---|---:|---|
| 意味・前提・適用範囲 | 96 | 用語、保証、責務、対象、時点、暗黙の仮定を読む |
| 境界・反例・最小対比 | 64 | 現案が破綻する条件や、区別が必要なケースを探す |
| 代替案・問題の捉え直し | 48 | 現案以外を評価し、別の分解や構成を開く |
| 関係・証拠・検証 | 32 | 要求と実装・テスト・主張の関係を照合する |
| 目的への効き方・次の調査 | 15 | 与えられた候補実験や判断の重要性を評価する |
| **合計** | **255** | |

これは同一wave内の分類であり、順番に実行する5フェーズではない。最後の15問も元のstateから作れる質問とする。先行回答を見ないと作れない質問は次waveに送る。

### 6.3 質問生成の複数パス

最初の案の擁護、失敗シナリオ、利用者と運用者、要求の捉え直し、証拠と検証という視点を分けて生成する。同じLLMの別パスでもよい。別モデルの利用は任意であり、それだけで誤りが独立になるとは考えない。

一つの共有された「望ましい最終回答」を全生成パスへ渡さない。目的と制約は共有するが、支持する結論を質問文に混ぜない。賛成と反対を機械的に同数へ揃えることも要求しない。

原案を書いた者が問いも書くと、原案を支持する方向へ問いが偏る。ユーザーが委譲を許すなら、生成パスを別の書き手（サブエージェント等）に分け、原案の推しや暫定の結論を渡さずに書かせる。独立性を得るのが目的であり、速さは副次的である。分担の単位は質問群（意味・前提、境界・反例、代替案）を既定とし、観測と判断の全体を見る必要がある関係・検証と目的・次の観測は統合する側が書く。分担しても、意味上の重複の除去、outcomeUseの確認、送信は統合する側が行う。手順はSKILL.md §4.5〜4.6。

### 6.3.1 答えが実行で決まる問いをJevへ回さない

架空のECテーブル設計での試走（2026-09-18、255問）では、「この表でこの状態を記録できるか」「この制約はこの操作を拒否するか」という構造の問いで、Jevの値と導出が5件食い違った。実行で決着した4件（うち3件はwave後に追加した実行、1件はwave前の観測）は、いずれも実行の結果が、Jevが最も高い確率を付けた選択肢と異なった（3件は逆の結論、1件は隣の選択肢）。残る1件は、PostgreSQLでの並行実行が未実施のため未決着である。一方、要件の文の意味や、要件どうしの関係についての問いは、成果物の未決の切り出しに使えた。

この一例だけで一般化はしないが、生成の段階で「答えが実行・計算・静的な照合で決まるか」を先に判定し、決まるものは実行して観測をstateへ入れる。Jevにはその観測と要求の意味の関係だけを聞く。

同じ試走では、対象の要件もスキーマも生成側が書いていたので、「要件は〜を定めているか」型の問いの否定（32件）は、書き手が書かなかったことの測定でもあった。自作の資料に対するこの型の問いは、判断を分ける空白に絞り、割合を限界として記録する。

### 6.4 スクリーニングは探索を殺さない

構文不正、参照不正、契約違反、送信禁止データ、決定論的に対象外と判定された質問は実行前に除外・修正する。

一方、回答が割れそう、発生頻度が低そう、まだ有用性が読めないという理由だけでは探索質問を落とさない。稀な重大事象のprobeや、まだ中心にない仮説を残す。

「答えに必要な情報がない」場合は、資料を取得する、証拠の十分性を問う質問へ変更する、明示的な仮定を置いた別世界の質問にする、または未実行として記録する。何も分からない質問を投げて高い確率で埋めることはしない。

255問を有効に構成できなかったときは、欠けた数と理由を報告する。番号を埋めるための同義反復は追加しない。

### 6.5 初版で「質問の質」を機械的に過剰最適化しない

安い質問を事前審査するために、それ以上の費用と時間を使う逆転を避ける。静的検査は常時実行する。Jevによる質問そのものの意味検査は、境界や影響の大きいもの、静的検査で疑義が出たもの、または明示したサンプルを中心にする。

meta-questionもJevの評価回数に含める。255個のdomain probeに対して二問ずつ審査すれば、それだけで510個の追加評価になる。無料の検査という扱いにしない。

## 7. Probeと観測の契約

詳細は `references/contracts.md` に定義する。中心となる項目は次の通り。

```text
Probe
  id / revision
  decisionRefs
  scenarioRef
  questionSpecRef + bindingRef
  semanticRole
  sourceRefs / assumptionRefs
  outcomeUse
  clusterId / contrastGroup
  executionDependencies
  relevanceGates
```

### 7.1 「何を聞くか」と「何に使うか」を分ける

`QuestionSpec` は判定する命題、適用範囲、参照する情報、出力型を持つ。`outcomeUse` は、回答の違いがどの判断や次の行動に効くかを持つ。

モデルへ渡すのは、その局所判定に必要な指示とstateだけである。例えば「yesなら案Aを採用できる」という期待を、claimとevidenceの照合に不要なら送らない。

### 7.2 出力statusをtrue/falseに押し込まない

正規化した観測は、`not_run / answered / abstained / not_applicable / error` を区別する。

`false` は「適用可能で必要な情報がある状態で、命題を否定した内容上の値」である。`abstained` は判断材料や利用条件が足りない。`not_applicable` は定義した対象外。`error` は通信や応答契約等の障害。未実施の検査は `not_run` である。

Noulの0.5をunknown専用コードにしない。Choiceのotherを情報不足へ流用しない。Scoreの最下位レベルに不明を混ぜない。

### 7.3 分布を保持する

Choiceは各候補の分布、providerのconfidence、ローカルで計算した最大確率・marginを別フィールドで保持する。Scoreは元の分布と期待位置を保持し、単に四捨五入したラベルだけを残さない。Noulはyesの確率とローカルの判定方針を分離する。

高confidenceは調査の優先度や操作上の扱いを決める補助材料である。契約への適合、実行テストの成功、人間の承認、真実の証明の代用にはしない。

### 7.4 出典と世界を保持する

観測は、原文、実行結果、要求・方針、仮説、モデル解釈を区別する。仮説を含むstateにはworld IDと仮定を持たせる。仮想worldでの回答を実worldへ無条件で移さない。

原文が述べていることと、原文の主張が現実に正しいことも別である。設計文書の「安全」という文言は、安全性の実測ではない。

## 8. 実行計画 — 横幅と深さを分ける

### 8.1 saturate-255：最初に広く聞く

同一snapshotを対象に、255個のdomain probeを先に定義する。静的検査と必要な投影を行い、安全に共有できるstateごとのpacketへ分け、各packetを評価する。初版の標準モードはこれとする。

「255問なら段階的に減らすべき」という前提を置かない。広く聞いた結果のうち不要だったものを捨てることも、有効な設計選択である。回答前に有用性を完全に予測しようとしない。

このモードの評価が終わっても、追加の有料waveを自動的に始めない。許可された範囲で原文照合や統合を行い、次waveに必要な質問・資料を成果物へ残す。

### 8.2 adaptive-255：質問を使う順序を変える

同じ255個の新規domain probe予算を、例えば96＋96＋63に分ける。後続waveでは前waveの回答、取得した新資料、実行したテスト、新しく生成された候補を使う。割当数は比較用の初期値であり固定法則ではない。

未知の論点へ辿り着ける可能性がある一方、最初の分解に引っ張られる可能性もある。どちらが良いかは、同じ目的・初期証拠・資源条件で比較する。

### 8.3 campaign：255問を一waveとして反復する

より大きな探索では、waveごとに255問を使う構成を認める。ただしこれは「合計255問」ではない。例えば3waveなら最大765個の新規domain probeになる。wave数、全評価回数、費用、外部ツールの権限をrun開始時の予算に明記する。

初版で複雑な自律campaignを先に実装しない。saturateとadaptiveで得た失敗例から必要な制御を増やす。

### 8.4 二種類の依存を混同しない

**relevance gate** は、その回答を使う条件である。例えば「障害報告だった場合だけseverityを使う」。severityの質問とstateを事前に作れるなら、分類と同時に聞ける。gateがfalseならseverityのraw answerは保存しつつ、判断には使わない。gateが未解決なら採用保留とする。

**data dependency** は、質問やstateを作るための先行結果である。上位候補の全文を取得する、回答から新しい仮説を生成する、構造化したblockへ次の質問を作る、といった場合はこちらになる。これはwaveを分ける。[S1]

第三の **logical relation** は、命題同士の関係であり、実行順序を自動的に要求するものではない。これらをすべて `dependsOn` 一種類で扱わない。

### 8.5 stateを大きくしすぎない

packetに含めるのは、それぞれの質問が参照を許可された資料の投影である。同じpacketの質問は同じstateを見るため、異なる情報境界を持つ質問を混ぜない。ある質問にとって未来のラベルや評価者の結論となる情報を、別質問が使うという理由だけで共有stateへ加えない。

類似した資料を使う質問のまとめ直しは可能だが、unionされたstateのすべてが全質問に許可されていることを確認する。単に「この質問ではこの欄を見ないで」と書くことを物理的な情報遮断の代わりにしない。

packetにはsnapshot hash、projection hash、source references、world ID、質問の版、provider profileを付ける。字数をトークン数と同一視せず、推定値しかない場合は推定と記録する。

## 9. 回答から次の一手を選ぶ

### 9.1 entropyではなく判断への影響を優先する

回答が0.5に近いという理由だけで追跡しない。結論に影響しない曖昧さを精密に測っても、目的は進まない。一方、高confidenceの回答でも、その一件が全体の採否を支えるなら反証確認の価値がある。

v0.1では、厳密な情報利得を計算できたことにせず、次の順序を基本とする。

1. 必須条件に関係し、判断を反転させ得る未決・矛盾候補。
2. 現案の採用を支える少数の重要な前提。
3. 残った候補を識別でき、取得・実行可能な証拠。
4. まだ探索していない目的上の重要領域。
5. その他の説明改善や重複解消。

これは探索ヒューリスティックである。較正されたvalue of informationや最適方策とは呼ばない。

### 9.2 次の行動は「もっと聞く」とは限らない

探索手は、`ask / retrieve / run_check / generate_hypothesis / revise_model / synthesize / stop` から選ぶ。

情報が足りなければ取得する。挙動が争点なら実行する。選択肢の外に解がありそうなら新しい案を生成する。人の価値判断が未提供なら条件付きの案を残す。質問を言い換えて気に入る回答が出るまで再実行することはしない。

### 9.3 閉じた選択肢から脱出する

Choiceを使うことと、探索全体を固定候補集合に閉じ込めることは別である。

各候補は仮説として版管理する。どれも成立しない、比較軸が不適切、候補を組み合わせるべき、前提を改めるべき、といった信号を受けたら生成モデルが新しい候補を作る。次waveでその候補を局所的に評価する。

`other` や `none` は候補集合の不足を示す選択肢として使えるが、欠けた候補の内容まではJevから生成されない。別案の生成はSkillへ戻す。

### 9.4 counterfactualは別worldとして評価する

一つの条件だけを変えたworldを作り、回答がどう変わるかを見る。例えば、更新イベントが届く場合と失われる場合、成功応答前の読取りと後の読取り、利用者が同じ場合と別の場合を分ける。

現実に到達可能なシナリオか、意図的な仮想条件かを明記する。変換によって意味が保存された／一軸だけが変わったという判断も未検証なら仮説である。結果の差をそのまま因果効果やモデルの欠陥の証明にしない。

## 10. Relation Checker — 整合性を保つが、正解を捏造しない

### 10.1 まず範囲を揃える

claim↔evidence、specification↔behavior、requirement↔testを優先する。対象、時点、quantifier、条件、world、版が一致しているかを先に調べる。

「証拠が不足している」と「暫定案Aを選ぶ」は、必ずしも論理矛盾ではない。採用の権限や可逆性、意思決定ルールが異なる可能性がある。自然言語で似ている二問を安易に含意で結ばない。

### 10.2 関係自体にも根拠を持たせる

関係の起源を、`declared / deterministic_derivation / model_proposed` として保存する。model_proposedの関係は検査候補であり、即座にハード制約として使わない。

照合結果は、必要に応じて `explicit / derived / assumed / ambiguous / absent / conflicting` を区別する。これと証拠の十分性を同じ尺度にしない。例えば明示的な記述があることと、その記述で運用上の安全性を説明できることは別である。

### 10.3 論理的な整合性と確率の一致を分ける

既知の宣言や形式モデルに対する矛盾は、コードやsolverで検出できる場合がある。一方、別々に尋ねた命題とその否定の確率が足して1にならないことだけで、現実の仕様が矛盾しているとは結論しない。公式も質問間のその種の構造的整合性を保証していない。[S8]

確率を都合よく変更して「整合した答え」を作らない。raw answersは保持し、関係に基づく解釈は別の派生結果として保存する。欠損をfalseへ埋めて制約を満たしたことにしない。

### 10.4 多数決しない

同じclusterの質問が多数同じ回答を返しても、独立票として加算しない。モデル評価をそのまま乗算して「全体正解確率」を作らない。

採否は、与えられた必須条件、候補ごとの根拠、検証結果、残余の未決を使って決める。選好の重みが未提供なら、恣意的な総合点を作るより、複数候補と条件別の優劣を残す。

## 11. 外部検証と形式手法

Jevには、要求とテストの意味的対応、反例候補の関係、追加検証の重要性などを局所的に読ませる。実際の実行、算術、到達可能性や不変条件の検査は適切な外部ツールへ渡す。

接続する単位は `CheckRequest` とする。

```text
対象claim / snapshot / world
検証したいproperty
使用するモデル・実装・入力範囲
仮定と未決方針
期待する観測
許可されたtoolと実行予算
原文への対応表
```

有限状態機械、SMT、Quint等のアダプターは必要になったものから追加する。生成したモデルが元の要求と一致することも別の検証対象であり、未規定な値を勝手にfalseや既定動作へ埋めない。

結果は、実行された範囲の `passed / failed / inconclusive / not_run` として記録する。boundedな検査の成功を無制限の証明にしない。モデル内の反例と実システムで再現した反例を区別する。

自動生成した任意のコマンドをJevの判定だけで実行しない。実行側は既存の権限・sandbox・登録済み操作を尊重する。qforgeが安全境界の所有者にはならない。

## 12. 収束と終了

### 12.1 収束は質問数ではなく成果物で判定する

終了条件は、要求された成果物を書けるか、重要な判断点に根拠または明示的な未決があるか、必要な調査範囲を説明できるかで定める。適応モードでは、次に実施可能な探索が目的にどの差を生むかを説明できない場合も停止候補とする。

saturateモードは原則として定義した初回waveを実行する。early stopは予算、契約違反、入力不足等の理由に限定し、255問を少数へ勝手に縮めない。ただし有効な質問が足りないときは水増ししない。

### 12.2 終了状態

| 状態 | 意味 |
|---|---|
| complete | 当該runが要求した成果物と検査範囲を満たした。世界全体の完全性ではない |
| provisional | 条件付きの判断や案を出した。明示した未決が残る |
| blocked | 目的に重要な、取得不能な証拠・権限・価値判断等が残る |
| budget_exhausted | 予算に達した。残した候補と次の一手を返す |
| degraded | backend障害や未検証の互換性等で予定した評価を完了できなかった |

### 12.3 Progress Record

waveごとに、新規判断点、解消した未決、その根拠、新しい候補、除外した候補と理由、未実施の検証を記録する。問題を細分化しただけなら、それを「解決」と数えない。

## 13. 予算、費用、信頼境界

### 13.1 数える単位

`domain_probe_target=255` は新規の意味上異なるdomain probeを255個作る目標である。課金される評価回数とは分ける。

| カウンター | 内容 |
|---|---|
| domain_probe_specs | 新規domain probeの数。改訂や対比版は関係も記録 |
| jev_evaluations | question×state×実行試行。meta検査・gate・再試行・再評価を含む |
| jev_requests | 実際に送信したHTTPリクエスト数 |
| generator_calls / tokens | 質問生成、意味モデル化、統合等の生成モデル使用 |
| tool_runs | 検索、テスト、solver等の実行 |
| cost | 見積、予約、観測額、確定額、不明分を分ける |

リトライは同じdomain probeでも追加の評価試行である。cache hitは新しいAPI送信ではない。意味上のdomain数と実行上の費用を同じメーターにしない。

### 13.2 費用の見方

TypeSafe directのModels資料にある入力単価は$0.042/100万tokens、出力tokensは無料である。[S4] 仮に一つのリクエストの課金入力が40,000 tokensなら、Jev入力部分の計算例は$0.00168となる。

これは課金計算の例であり、255問の実測費用ではない。実際にはstate、質問、criteria、provider経路、再実行で変わる。生成LLM、資料取得、検証、保管の費用は別である。Cloudflare等の単価はその経路の最新情報で確認する。

255問の生成が全体の支配的なコストになる可能性がある。まずJevを細かく節約するより、生成パス数、再生成、重複する全文読解、回答の再要約を観測する。

### 13.3 送信と保存

秘密検査はstateだけでなく、title、instructions、criteria、metadata、エラー、保存する説明文を含む全送信・保存境界で行う。検出したが処理できていない値を「マスク済み」と表示しない。マスクで判定対象の意味を失った場合はabstainか質問の再構成にする。

APIキーは環境変数や既存credential brokerから取得し、state、プロンプト、結果、ADRに書かない。raw sourceや機微な観測は既存のアクセス境界に置き、公開用成果物へ自動転記しない。

state内の文章が命令でない旨は明示するが、それだけで敵対的入力から保護されたとはみなさない。権限、予算、provider設定、実行可能toolは入力データから変更できない。

### 13.4 障害とcache

応答はID集合、型、候補・level集合、有限数、0〜1の範囲、確率和、Choiceのargmax整合性、Scoreの範囲を検査する。丸めに対する許容誤差はprovider profileで明示する。モデルが型安全でもtransportやadapterの不具合は別に検査する。

timeoutで費用が不明なら0円としない。予約を保留し、照合できなければ不明分として残す。自動リトライは上限と予約に従う。異なるproviderやモデルへの透過的fallbackは行わず、別経路であることを明示する。

cache keyには、provider、要求モデルと解決モデル、adapter版、質問全体、投影state、schema版、評価設定を含める。別モデルへのalias変更を無視して古い結果を混ぜない。cache replayは過去の記録の再現であり、モデルの再実行が同一結果になるという保証ではない。

## 14. 検証計画 — 255に意味があったか

### 14.1 比較する条件

同じタスク集合で、通常の生成LLMによるレビュー、生成LLMによる255問の生成・回答、Jevによる少数probe、`saturate-255`、`adaptive-255`を比較する。追加でrelation checkerや対比質問を外すablationを行う。

初期証拠、成果物の要求、実行権限を揃える。質問数を揃えた比較と、総費用・所要時間を揃えた比較を分ける。追加検索や追加テストを行った条件は、その差を隠さず記録する。

### 14.2 何を測るか

主指標は、外部の原文・実行・人によって確認できた重要な発見や判断の改善である。仕様の欠陥検出なら、用意した正解だけでなく新規発見を別途確認し、精度、見逃し、誤警報、確認作業量を測る。

補助指標として、質問clusterの多様性、明示したシナリオへのcoverage、入力不足率、未実行率、API障害率、決定までのwave数、総費用、所要時間を残す。answeredだけを分母にして良い数字を作らない。

255個のモデル信号を255個の独立した検出事例として評価しない。同じ元タスクや元シナリオに由来する派生caseをgroupとして扱う。探索に使った例と最後に評価する未使用例を分ける。

### 14.3 自己改善

質問・operator・state projection・候補生成方針を版管理し、改善候補をshadowで比較する。自身の高confidenceや同じJevの賛成だけを成功ラベルにしない。権限、予算上限、受入基準を探索ループが自動的に緩めない。

公式Autoresearch feature discoveryには、生成モデルで質問を提案し、その回答を下流予測モデルの特徴へ変え、観測誤差を使って改訂する例がある。[S11] 本設計でも「良い質問か」を目的側の結果で確かめる構造は参考になる。ただし、教師ラベルのある予測問題の成功を、そのまま仕様探索の品質保証として転用しない。

## 15. 実装順

### Phase 0 — まず255問の実験を成立させる

Skill、versioned input/output契約、TypeSafe direct用の一つのadapter、送信前の全payload検査、packet化、response validation、ledger保存を作る。日本語原文を保持し、実際のタスクで255問の入力と結果を観察する。

Jev unavailable時に別LLMが回答したことをJev結果として記録しない。未実行の実験は未実行と残す。

### Phase 1 — 回答が役に立つ形へ統合する

Decision Card、source trace、cluster重複表示、relevance gate、sufficiencyの扱いを加える。255回答からどの判断がどう変わったかを説明できることを優先する。

### Phase 2 — adaptive比較と探索手の拡張

追加取得、登録済みの検証、新仮説生成、worldの対比、限定的なrelation checkingを加える。saturateとadaptiveを同じタスクで比較する。

### Phase 3 — 必要な箇所だけを汎用化

Cloudflare等のprovider adapter、既存qlintやrelation checkerとの実接続、形式検証adapterを追加する。複数用途で同じ処理を繰り返すと分かった箇所をコードへ移す。

初手で常駐daemon、独自agent framework、graph database、汎用planner、独自の確率推論エンジンは作らない。255問の結果を見る前に巨大な機械を完成させない。

### Phase 0の受入条件

- 同一の論理waveに255個のdomain probeが入り、意味上の重複・対比版を識別でき、実際の送信packetとの対応が追える。
- 非同期性に頼らず、同じstateで聞ける質問を不要に直列化していない。
- 情報境界が異なる質問を共有stateへ混ぜない。
- 未実行、対象外、情報不足、障害、内容上の否定を別に残す。
- confidenceと最大確率を混同せず、生の分布を保持する。
- 追加評価と不明な課金を含めて予算が記録される。
- 最終成果物の主張をsource、probe、観測、検証へ遡れる。
- 読んだ範囲で指摘がなかったことを、仕様全体に欠陥がない証明として表示しない。

## 16. 最終的な位置づけ

qforgeはレビュー用のチェックリストではなく、**目的に合わせて観測点を生成し、意味判定の結果によって調べる対象や解の候補を更新するSkill**である。

Jevの速度を「LLMの最終回答を早く出す」ためだけに使わない。これまでなら質問する前に諦めていた数の可能性を先に問い、その後で重要なものを選べるようにする。

ただし、問いの数によって権威を作らない。255問の価値は255個答えが並ぶことではなく、その中から目的を前へ進める区別が見つかることにある。
