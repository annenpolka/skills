# Probe operators — 質問を増やすための操作

同じ主張の言い換えではなく、条件を変えることで必要な区別を増やす。以下は質問生成の道具箱であり、全タスクへ機械的に全項目を適用するチェックリストではない。

## 1. 一つの判断から広げる17の操作

例として「更新後にキャッシュを無効化する」という架空の記述を使う。ここから実際のプロジェクトの仕様を推測しない。

| 操作 | 区別するもの | 質問候補 |
|---|---|---|
| 用語の分解 | 同じ語の異なる意味 | ここでの『更新後』はDB commit後か、API応答後か |
| 主体の変更 | 誰に対する保証か | 別プロセス経由の読取りにも同じ保証が適用されるか |
| 対象の変更 | 何が含まれるか | 集計値と詳細値の両方が同じ無効化対象として記述されるか |
| 時点の移動 | 境界の前後 | 更新成功応答の前に開始した読取りを、この要求は規制するか |
| 順序の交換 | イベントの順序 | 旧値のcache fillが無効化後に到着するシナリオは、記述した方式で扱われているか |
| 同時実行 | 単独時と競合時 | 二更新が競合したケースのルールが、この仕様の範囲で定まるか |
| 障害の挿入 | 通常と部分故障 | 無効化通知が失われたとき、元の保証を維持する規則が記述されているか |
| 再試行・重複 | 一回と二回以上 | 同じ更新イベントの重複配送が、候補の説明上で別の結果を生むか |
| 不在・欠損 | あることを前提にしたデータ | versionが得られない場合の規則は明示されるか |
| 境界・極端 | 通常値と端の条件 | TTL境界直前の読取りと直後の読取りを要求は区別するか |
| 責務の移動 | 誰が判断するか | 成功応答を返す責務と全ノードの無効化確認の責務が対応しているか |
| 最小反例 | 主張を壊す具体的な経路 | この短い仮想traceは、要求と候補方式の不一致を示す候補か |
| 支持証拠 | 主張を何が支えるか | 提示したテストは、全プロセスという適用範囲を扱っているか |
| 反証証拠 | 何が主張と合わないか | このログの読みは、成功応答後の古い値を禁止する主張と衝突するか |
| 代替構成 | 方式を変えた場合 | version照合を行う案は、提示した障害条件を判別する情報を持つか |
| 目的の再解釈 | そもそもの要求の妥当性 | 強い整合性と『誤った値で次の操作をしない』は、この利用場面で同じ要件か |
| 観測・取り消し | どう確認し、どう戻すか | この追加テストの観測項目は、残っている二案を識別できるか |

複雑な因果推論や正確な算術が必要な問いは、traceや計算結果を先に生成・確認し、Jevへは局所的な関係だけを渡す。到達不能なtraceを現実に起こり得る反例として提示しない。

## 2. 四種類の生成パス

**Source-led**: 原文の名詞、状態、動詞、条件、例外、保証を出発点にする。原文へ強く接続できるが、書かれていない観点は弱くなり得る。

**Scenario-led**: 具体的な利用・障害・競合・移行シナリオを先に作る。仕様の空白を探りやすいが、存在しない要件や到達不能な状態を発明しないようworldと仮定を示す。

**Alternative-led**: 現案を最小化する、責務を移す、別の保証を選ぶ、構成を組み替える。固定された候補内の順位付けだけに閉じない。

**Evidence-led**: 何が観測され、何が未実行か、どのテストがどの要求を区別できるかを見る。確認できる証拠の範囲と、要求の規範的な正当性を混同しない。

## 3. 問いの書き換え例

### 悪い：判断が一つに見えて複数入っている

> この設計は安全で高速で保守しやすいか。

### 良い：結果が別の判断へ接続される

> `requirements.read_guarantee`は、成功応答後に開始した別ノードの読取りへ適用されるか。

> `candidate_a.description`には、通知が失われた場合にも旧値を識別する仕組みが記述されているか。

> `test_cases.cross_node_read`は、書込みノードと読取りノードを区別するケースを含むか。

速度については「p95が100ms以内か」とJevに推測させず、測定条件と観測値を用意してコードで比較する。実測がない段階では、追加同期通信が記述されているかといった局所的な特徴に分ける。

### 悪い：答えを埋め込んでいる

> この非同期案は古い値を返して危険なので、捨てるべきか。

### 良い：候補traceを評価対象として切り離す

> `hypothetical_trace`の読取りが返す値は、`requirements.read_guarantee`が認める範囲に入るか。traceは未実行の仮想例であり、ここでは要求との対応だけを判定する。

### 悪い：unknownを否定に混ぜる

> 安全性を証明できるならtrue、証拠が足りないか危険ならfalse。

### 良い：何を測っているかを分ける

> 提示した資料は、この命題を判定するために必要とした範囲を含むか。

そのgateを満たした場合だけ、本体の命題の評価を利用する。必要な範囲そのものが未定なら、それを先に作業モデルの未決として残す。

## 4. 生成の指示書

以下は問いの書き手（自分の別パス、または分担したサブエージェント）へ渡す作業指示の型であり、Jevへそのまま渡す質問ではない。`<...>` を埋め、担当しない部分は消す。SKILL.md §4.5の「渡さない」ものは書かない。

```text
# 目的と成果物
<objective>。成果物は<requested artifacts>。hard constraint: <...>。

# 生成キット（変えない）
- evidenceとstate path: <path to evidence file>
- 判断と候補: <D1..Dn と cand.* の一覧>
- 仮想シナリオとworld: <scen.* と world の一覧>
- 書式: <DSL の場所と例>。IDとsourceRefsはbuildが付けるので書かない。
- 読んでよい資料: <範囲>。これ以外は開かない。

# 担当
群: <意味・前提 | 境界・反例 | 代替案>。判断: <D..>。目標: <N>問。
目標に届かなければ、不足数と理由を返す。言い換えで埋めない。

# 書き方
- 1問に1つの局所命題。対象・条件・時点・worldを特定する。
- 答えの値ごとに、変わる判断IDと成果物の節・行動をoutcomeUseに書く。
- 質問文に望ましい回答や推したい案を入れない。原案を不要にする構成や、
  候補にない解へ開く問いも含める。
- 答えが実行・計算・静的な照合で決まる問い（表せるか、制約が拒否するか、
  値・件数・列の有無）は問いにしない。「実行案」として別に返す。
- 資料が定めていないことを問う場合は、成果物の判断を分ける空白に限る。
- 同じ区別を別の言い方で問わない。行列で作るときは、セルごとに答えが
  変わりうる組合せだけにする。
- 答えが割れそう、低頻度そうというだけで落とさない。
- 最初から作れる条件付きの問いは同じwaveに置く。先行回答がないと作れない
  問いは「次wave候補」として分けて返す。

# 返すもの
1. probeの下書き（書式どおりのファイル）
2. 実行案（何を実行すれば何が分かるか）
3. 不足数と理由、迷った問いとその理由
plan・send・外部への送信はしない。
```

## 5. 言い換えや反転を使うときの注意

肯定文と否定文を別々に聞いた確率が正確に相補になるとは仮定しない。ChoiceとNoulを同じ閾値で混ぜない。candidate集合を変更したChoiceの確率が元の集合と同じになるとも仮定しない。

感度を観測することと、どちらが正しいかを決めることは別である。高confidenceになる言い方だけを採用すると、質問の改善ではなく回答の誘導になる可能性がある。
